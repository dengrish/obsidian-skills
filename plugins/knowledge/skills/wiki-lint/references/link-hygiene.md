# Link hygiene — the full rules (Task 2)

**Read this when Task 2 runs — before applying or rejecting a backfill candidate, pruning a link, or resolving a dangling target.** It owns the closeness bar, removal triggers, and dangling-link protocol. Do not perform those operations from the [entrypoint summary](../SKILL.md#task-2--link-hygiene) alone.

**wiki-lint owns retrospective and vault-wide link editing** ([ownership split](../../../shared/CONVENTIONS.md#why-the-split-is-drawn-here)). Task 2 covers eligible bare mentions, weak links, and genuine dangling targets across the requested maintenance scope, including entries untouched by a recent source run.

## Task 2 — Link hygiene

Two directions: **backfill** links that could not exist when an earlier entry was written, and **prune** duplicate or weak links. Task 2 judges whether a link is added, kept, or removed, including for a [user issue](../SKILL.md#user-issues) about a link, which it judges under the same bar. Task 1 may separately correct the spelling of an existing, unambiguous link or footer without changing its destination or meaning.

Existing MOC navigation links are outside this entity-link mechanism. Preserve
qualified `[[MOCs/<discipline>-moc]]` / `[[MOCs/misc-moc]]` links and recognized legacy MOC links; inspect
the MOC inventory when their target is missing or ambiguous. Unexpected
legacy vault-root MOCs (`<vault>/<discipline>-moc.md`) are preserved and
reported outside routine generated ownership. A MOC outside `Wiki/` is not
a missing entity to unlink. Do not add MOC links as entity backfill candidates
or strip a valid `MOCs/` or disambiguating `Wiki/` prefix. `item10/moc` names
an unknown bare or explicit MOC target, or a missing/unsafe explicit MOC
target: preserve its original destination without automatic qualification
and route it to authorized Task 3 work.

### Backfill (add missing links)

Surfaces claimed by multiple entries are omitted from backfill candidates; resolve their ownership before linking them. A destination whose canonical slug is in the scanner's designated common-noun set stays excluded through every title, plural, or alias surface. A surface that is itself in that set, or its plural, is excluded too. Other single lowercase aliases of qualified destinations are emitted with the `bare_noun_alias` flag described below; the flag requests stricter review, not automatic rejection. An `Organism` may also contribute a local common-name surface when its description or opening sentence directly equates that surface with the Organism's canonical title. Such candidates carry `organism_common_name: true`: the flag establishes a permissible display label only, never a global alias or an automatic link. The surface is the complete bound phrase (plus its natural inflection), never an unbound head extracted from it: `fruit fly` does not make every bare `fly` a Drosophila candidate. A candidate whose target is a discipline root carries `discipline_root: true`; batch-judge those under the [discipline-roots rule](#the-closeness-bar), which rejects a field named only as a setting or genus. The scanner already omits a root title directly after a modifier word ("cell biology", "summary statistics"), which names a subfield or a different sense, or named only as a setting ("in/for/within/across …") or genus ("a … system"). A parenthetical title's base term ("outlier" for Outlier (statistics)) is a surface too, carrying `base_term: true`. The scanner offers it only when the base term is not a cross-domain floor term, and never when an existing body link already uses that surface as the display label of a different target. It treats a base surface as an alias of its entry, so a single-word one is also flagged `bare_noun_alias`. Judge each base-term candidate under the closeness bar like any other.

Step 0's **backfill candidates** are the worklist: it has already scanned every entry's prose for bare-text mentions of other entries' titles/aliases (and their plurals) plus directly bound Organism common names, excluding designated common-noun surfaces/destinations and targets already linked in that entry. Task 1b's [term audit](../../wiki-build/references/writing.md#editorial-reread) adds to it each first mention of an entry's concept that no claimed surface names; judge each under the closeness bar and the [label rules](../../wiki-build/references/writing.md#display-label-casing) like any candidate. Walk that list and, for each candidate that clears both surface identity and the closeness bar below, wrap the **first eligible body-prose occurrence** (the row's `line`) using the supplied destination in `[[target|Display]]` (bare only when display exactly equals target), preserving any required path such as `Wiki/statistics` beside a previous-layout MOC. When that occurrence uses the word in another sense, it is not eligible: wrap the target's first later mention in the entry that names it, and reject the row only when none does. The display label preserves the entry's wording (alias mentions keep the source surface form — "Lambda Rank" → `[[lambdarank|Lambda Rank]]`). For `organism_common_name: true`, verify that the mention really names that organism in context and is close enough to link; do not copy the surface into `aliases:`. Then curate `**Related:**` under the footer rule: add the target only when it is one of the entry's most useful navigation choices, rather than copying every accepted body link into the footer. Use the same supplied target, including required qualification, with the canonical piped footer label. Only one occurrence is wrapped; every other mention stays bare text.

**Late first links.** `item10/late-link` reports an entry whose first body link to a target follows an earlier plain prose mention of the target's title, alias, plural, or that link's own label. When the earlier mention names the same entity, move the link there: wrap it with the existing destination, including any path or anchor, under a label that keeps its wording, and unwrap the later link to its visible label. Possessive, partitive, and modifier uses still name the entity under the builder's [first-eligible-occurrence rule](../../wiki-build/references/writing.md#link-form). That includes a modifier inside an open compound built on the target (`the percentile interval` for Percentile), unless that compound is itself another entry's title or alias ([compounds that name an entry](#the-closeness-bar)). Leave the placement unchanged when the earlier word has a different sense, another meaning of the same word (a linear model's bias term is not statistical bias); when it is a word the entry defines in italics from its own title, a facet other entries link to this entry, or a later use of that facet word (Bias/variance trade-off's *Variance* bullet and its "high variance", which Decision tree links as `[[bias-variance-trade-off|variance]]`); or when the target is a discipline root that the earlier passage names only as a setting; the discipline-roots rule below makes only a passage about the field eligible. Re-scan after moving links, as for backfill.

A [same-surface-form pair](../../wiki-build/references/special-titles.md#same-surface-form-different-technique) lists each other in Related even without a bare mention: when one entry's footer names its counterpart, add the missing reciprocal item to the counterpart's footer under its canonical piped label.

**Thin footers.** A footer with fewer than three links may gain neighbors the body does not mention, chosen in the [footer priority](../../wiki-build/references/writing.md#the-related-footer) and each clearing the [closeness bar](#the-closeness-bar).

Hidden HTML/Obsidian comments, escaped wikilink examples, headings, inline Markdown image syntax and alt text, captions, table cells, code/listings, LaTeX math, Markdown link-reference definitions, inline/full/collapsed/shortcut Markdown-link labels resolved by those definitions, bare URLs/autolinks, and Obsidian links/embeds are not new wikilink surfaces. The scanner masks them so an unwritable first occurrence cannot hide a later eligible prose occurrence; the executing agent must not reconstruct a candidate from one of those masked zones during semantic review.

When a selected surface is italicized or bolded, remove those surrounding emphasis markers as part of linking it: `*mean squared error*` becomes `[[mean-squared-error|mean squared error]]`, never `*[[mean-squared-error|mean squared error]]*`. Leave code spans and listings untouched, and count an existing link with a heading, block anchor, path, or `.md` suffix as already linking its target. After the edits, re-scan to catch any formatting or duplicate-link defect introduced by the backfill itself.

#### The closeness bar

**The bar is strict and conceptual.** "Should A link to B?" is judged on how closely related the two entities are, not on whether some source discussed both, and not on whether the mention unambiguously *refers* to the entity. Items 1–2 are the ordinary test; item 3 clears that test automatically, while item 4 remains a rejection floor:

1. **The reader would genuinely benefit from jumping there** — the entity is a *node worth visiting from this passage*, not merely a name that happens to have a file.
2. **The relationship is conceptual**, not incidental co-occurrence: B explains, contrasts with, composes, generalizes, or is a mechanism of what A's passage is saying.
3. **Positive trigger:** a paragraph that attributes mechanism, architecture, or method to a named entity ("X works by…", "X introduced…", "X uses [technique]") with enough mechanism-level detail for a self-contained atomic entry clears the bar automatically.
4. **Reject** passing mentions, glancing references, and bare name-drops **even when the slug exists and the reference is unambiguous**. Correctly identifying which entity a word refers to is a *precondition* for linking, never a reason to link.

**Discipline roots.** A `Wiki/<discipline>` root is already each member's hierarchy ancestor through `parents:` and the MOC. A body link to a root clears the bar only when the passage discusses the field itself, such as its scope, methods, or how the entry's subject fits within it. Naming the field as a setting or genus ("in machine learning, …", "a machine learning model") is a passing mention. A field name inside a compound or a different sense ("molecular biology", "summary statistics") is not a mention of the root and fails surface identity. The weak-link prune applies this bar to an existing body link to a root and its Related item; a Related-only link to the entry's own root is a parent-concept neighbor under the [footer rule](../../wiki-build/references/writing.md#the-related-footer), not a weak link on this ground.

**Compounds that name an entry.** An open compound, or its plural, that is another entry's title or alias names that entry ("messenger RNA" for Messenger RNA). No word inside it, head ("RNA") or modifier, is a mention of that word's own entry, so a link on that word fails surface identity. The scanner's leftmost-longest surface match already reads the compound this way for backfill and late-link rows. An existing link of this shape (`messenger [[rna|RNAs]] ([[messenger-rna|mRNAs]])`) fails the bar, so the weak-link prune unwraps it and itemizes it; a Related item for that word's entry stays when the footer rule selects it on its own merits. If the entry does not link the compound's own entry, link the whole compound (`[[messenger-rna|messenger RNAs]]`). A compound with no entry of its own keeps the modifier rule (`the [[percentile]] interval`).

**When in doubt, do not link — over-linking is the failure mode.**

**This bar is wiki-lint's own.** Apply it consistently to additions and removals.

**Cross-domain bare-term rule (do not violate).** Never auto-link a bare common noun to a bare slug. A body's bare "entropy" is linked only with the qualified target and the source's wording — `[[information-entropy|entropy]]` in an ML context, `[[thermodynamic-entropy|entropy]]` in thermodynamics — never `[[entropy]]`. If the intended sense is ambiguous, leave it as plain text and flag it in the report. The corpus of bare terms this covers is wiki-build's — *Cross-domain term disambiguation* in `wiki-build/references/special-titles.md`, which also carries the never-an-alias rule ("the bare term is not added as an alias to any entry"; the builder's [aliases field](../../wiki-build/references/writing.md#aliases) restates it under its redundant-alias rules). The scanner and wiki-build's `lint_entry.py` share a working subset in `COMMON_NOUNS`, with its short phrases in `CROSS_DOMAIN_PHRASES`. It suppresses a surface in that set or its plural, and every surface whose destination slug is in that set; this is a mechanical floor, while wiki-build's corpus remains the authority. A different shape, a single all-lowercase alias outside that set of a **qualified** destination (`covariate` on a Feature entry), may still be emitted as `bare_noun_alias: true`. Judge those candidates as one batch: they nearly always fail the closeness bar (a `base_term: true` row excepted, since that word is its target's running-prose name, so judge it individually), and a rejection is [settled](#settled-decisions) rather than re-judged on every run, but a qualified-target link using a bare surface can be legal when the sense and relationship are clear. An alias that is itself a bare cross-domain word breaks the never-an-alias rule; `item18/cross-domain-alias` reports it as a semantic-invalid alias, which Task 1b removes through the [alias-removal protocol](refactors.md#remove-a-semantic-invalid-alias) under [QC finding actions](qc-items.md#finding-actions). The target's body may keep introducing the word in italics, which lets a link use it as a context-resolved label (`[[label-machine-learning|target]]`).

### Prune links within the requested scope

The executing agent applies exactly these three removal triggers without separate sign-off:

1. **Remove self-links.** An entry never links to itself through its canonical slug, a path/`.md`/case spelling, or one of its own aliases. Render an ordinary body mention as plain text and remove the Related item. If an anchored body link provides real within-note navigation, preserve that function by rewriting it as a local `[[#Heading]]` or `[[^block]]` link instead; preserve an explicit label as `[[#Heading|Display]]` or `[[^block|Display]]`. (Scanner: `item10/self`.)
2. **De-duplicate.** wiki-build wraps only the first occurrence; if an entry links the same resolved entry twice or more in its body, unwrap the 2nd+ occurrence(s) to bare display text, keeping the first. Path/`.md`/case/Unicode spellings and an unambiguous alias beside the canonical slug still resolve to one entry when the inventory identifies one owner; a file outranks an alias. If several Wiki or MOC files share a basename, distinct qualified paths stay distinct, and repeated bare or ambiguous-alias links remain report-only until ownership is resolved. (Scanner: `item10/dup`.)
3. **Drop weak links.** Unwrap a body wikilink, and remove the corresponding `**Related:**` entry, when the link fails the strict closeness bar above — a tangential name-drop that got linked. Dropping a body link to bare text and pruning it from Related are done together so the two stay consistent. A `hub_footer` row names footers that list a heavily shared target outside the entry's parent, children, siblings and the target's own Related footer. Remove that item from the footer alone when the target is general vocabulary there rather than a neighbor the footer priority selects (Training set in Cost function goes; Overfitting in Early stopping stays). A kept item is [settled](#settled-decisions): later scans omit it until its footer line changes.

**Never** prune via this mechanism: `tags:`, `sources:`, `parents:` (each has its own rules; and `tags:` are `#`-tags, not wikilinks, so they're not even in the link-pruning domain). Pruning operates on body-prose wikilinks and Related-footer entries only. Itemize every prune in the run report (entry, target, reason) for traceability; this is post-action reporting, not an approval or review gate. **Backfill ⇄ prune do not oscillate on unchanged evidence.** A link pruned as weak returns as a backfill candidate on the re-scan; apply the same closeness bar and reject it, and the [settled ledger](#settled-decisions) records that rejection so later scans omit it until its sentence changes.

### Settled decisions

A rejected backfill candidate and a kept `hub_footer` item are settled on unchanged evidence. wiki-lint records them in `<vault>/Reviews/.wiki-lint-settled.json`, its private run state rather than a suggestion log, and Step 0 passes that file to the scanner with [`--settled`](scanner.md#cli). Each `backfill_candidates` row carries a `settle_key`, and each `hub_footer` row one per listed entry in `settle_keys`: the exact record to store, holding the entry, the target, the surface for a backfill candidate, and `context`, the SHA-1 of the whitespace-collapsed sentence holding the candidate occurrence or of the footer line. A backfill row also carries `settle_keys`: its own `settle_key`, then the key of each later unsettled sentence that holds an eligible occurrence of its target. The file is one JSON object, `{"version": 2, "backfill": [...], "hub_footer": [...]}`, whose lists hold those records exactly as the scanner emits them, with no other keys or fields; any other shape is malformed. A backfill row whose occurrence's key matches a record falls back to the target's next eligible occurrence in another sentence, under that sentence's key, and is omitted only when every such occurrence is settled. A `hub_footer` item whose key matches a record is omitted. Any edit to a settled sentence or footer line brings its row back for judgment, and so does a new sentence that mentions the target. The ledger suppresses only these two row kinds, never a `problems` finding. A missing ledger is empty; an unreadable or malformed one suppresses nothing and is reported. A `"version": 1` ledger has the same shape, but each of its backfill records settles its entry and target while it matches the target's first eligible sentence. The scan's `settled.upgrade` lists the records of that target's other sentences.

At closeout, an apply-capable run that performed Task 2 rewrites the ledger under the shared [safe-write protocol](../SKILL.md#publishing): it records the ledger with `publish_files.py snapshot` before Step 0's scan reads it and publishes the rewrite against that record. The new ledger keeps every record of the ledger the run read except the `stale` records of the run's last scan, made after its last edit. From that last scan it adds every `settle_keys` record of each candidate this run rejected, the `settle_key` of every `hub_footer` item it kept, and the `settled.upgrade` records, so each record matches the sentence or footer line as the run left it. A rejected candidate or kept `hub_footer` item that this last scan no longer lists gets no record. A rejection covers every mention of the target in the entry: the closeness bar judges the entity, and a wrong-sense occurrence is rejected only when no later mention names the target. Write `"version": 2`, or keep `"version": 1` when `settled.upgrade` is `null`, since that scan's alias ownership was incomplete and it could not list them. Sort each list by `context`, then `entry`, then `surface` (backfill only), then `target`, comparing strings by code point. Keep the top-level keys in the order `version`, `backfill`, `hub_footer` and each record's fields in the scanner's order. Write the file as UTF-8 JSON with a two-space indent, non-ASCII characters unescaped and a final newline (Python's `json.dumps(ledger, indent=2, ensure_ascii=False)` plus `"\n"`). A run that reads a version-2 ledger and adds and drops no record then rewrites it byte for byte. A report-only run reads the ledger but never writes it.

### Dangling links (target missing)

If a QC message says **“Alias inventory is incomplete”**, unreadable or unparsed metadata could own an otherwise missing or apparently unique alias. The scan suppresses dangling and alias-dependent repair findings and backfill candidates; their absence is not a clean result. Preserve unresolved links and defer alias canonicalization, alias-based duplicate/self-link removal, and backfill until the affected metadata/readability is safely corrected and a fresh scan restores complete ownership. Direct-filename checks remain usable. This is a dependency gate, not a separate approval requirement.

`item10/ambiguous` is report-only: several files share the basename or several entries claim the alias. An exact or unique-suffix qualified path can identify one same-basename file; a qualified path matching none remains ambiguous while several owners coexist, rather than becoming a destructive dangling-link instruction. Preserve the entire link until its destination is resolved. On an unambiguous `item10/alias` or `item10/case` repair, change only the destination spelling and preserve existing heading/block anchors and any explicit display label.

Resolve explicit `./` and `../` targets from their owning note's directory,
including in parents and MOCs. Such a path names one location; never reinterpret
a missing relative destination as a matching basename or shortest suffix elsewhere.

An entity-valued body or Related-footer wikilink whose target names no real vault file, after excluding MOC navigation as above. **First make sure it really is one:** the scanner separates these from four look-alikes that are not genuine missing-target findings. **`item10/unparsed`** names a file that is in `Wiki/` but did not parse as an entry (no frontmatter, `item1`; or unreadable bytes, `item0`). The file is real; **creating a replacement would overwrite the user's file.** Repair that file under its own `item0`/`item1` finding. **`item10/case`** has one existing owner after the plugin's case/Unicode-normalization fold. Rewrite the target to that owner's exact on-disk spelling on every host; never create a competing variant, because some filesystems alias the spellings while others store both. **`item10/alias`** names another entry's unambiguous alias, which Obsidian resolves as an alternative slug. Rewrite it to the piped `[[owner|Alias]]` form the finding gives, **never create a competing file**: a file outranks an alias, so a new file at the alias name would steal those links from their owner. **`item10/non-entry`** names a real vault note outside `Wiki/` and `MOCs/`, such as an `Articles/` reading note or the user's own `People/` note. Obsidian opens it, so preserve the link, its path, anchor and display text: never drop it, retarget it to an entry or alias, or create an entry for it. If a dangler list was built by hand rather than from the scan, apply the same four checks before dropping anything.

**A link to a missing root waits for Task 3.** A dangling target is not a genuine dangler either when its slug, under the plugin's case/Unicode fold, has a `missing-discipline-root` finding in the current scan's [`hierarchy_diagnostic`](scanner.md#hierarchy-diagnostics) (the refreshed scan when Task 1 or 1b changed entries): Task 3's [root prerequisite](hierarchy.md#establish-discipline-roots) creates that root. Task 2 rewrites a variant spelling to the root's slug, keeping the displayed text as its label, and leaves the link in place unless it fails the [discipline-roots rule](#the-closeness-bar) as a link to an existing root would; Task 3's completion rescan confirms a kept link resolves. When the run does not create that root (Task 3 does not run, skips that closure or is blocked), closeout drops the link under this protocol, keeping the entry's dates and `read:` as Task 2 does, publishes it under the [safe-write guard](../SKILL.md#publishing), re-scans, and reports it with that reason.

**Resolving genuine danglers is wiki-lint's job, vault-wide, and nothing has swept ahead of it.** wiki-build's orphan audit reaches only the entries it created or merged on its own run, so every other dangler in the vault survives until Task 2 finds it. Never skip an `item10/dangling` finding on the assumption that a builder run already handled it. **When Task 1b runs, it settles each dangler first** under its [dangler hand-off](refactors.md#dangling-link-hand-off): a target whose concept already has one entry is matched to it, a real knowledge gap that meets the [missing-entry rule](refactors.md#create-a-missing-entry) gets its entry, and a term whose sentence needs its meaning gets a gloss. Task 2 then points each link to a matched or new entry at it, keeping its label, and backfills the bare mentions. **Resolve every other genuine dangler by dropping the link to bare text** — replace `[[slug|Display]]` with the display text, and remove the matching Related-footer item. A passing-mention dangler is just dropped and itemized like any prune; a dropped target that still looks like a gap is named as a **missing-entry candidate** in the [run report](backlogs.md#run-report). In a run that skips Task 1b, the run report also names each dropped term whose sentence needs its meaning as a self-containment gap for the next Task 1b run; it is not logged, since an ordinary run [repairs it](backlogs.md#proposing-note-improvements).

`tags:` cannot dangle because they are discipline tags, not wikilinks. Image embeds and note transclusions are outside entry-link detection and are never replaced or dropped here; `item12/missing-image` reports an embed absent from the supplied image inventory without authorizing deletion. A `[[…]]` inside a hidden HTML/Obsidian comment, an escaped wikilink example, or a fenced, indented, or inline code listing is not a rendered link and never reaches this protocol. Preserve these annotations and samples. A list item's indented continuation is ordinary prose and remains checked.
