# Link hygiene — the full rules (Task 2)

**Read this when Task 2 runs — before applying or rejecting a single backfill candidate, before pruning any link, and before resolving any dangling target.** It holds the closeness bar in full, the two removal triggers, and the dangling-link protocol. Task 2 is the only destructive operation in the skill, so do not work from the summary in `SKILL.md` alone.

**wiki-linter is the only skill that links across entries.** wiki-builder wikilinks *inside* the entries it writes — and within a merged entry, only inside the prose it wrote on that run — builds their `**Related:**` footers, and links only targets that exist (it creates no stubs; neither skill does any more); it stops there, it has no back-fill audit, and its orphan sweep covers only the entries it created or merged on that run. Everything retroactive, cross-entry or vault-wide is Task 2's: the bare mention in an entry nobody has revisited — including one left standing inside an entry a later source merged — the weak link that should come out, and the dangling target left behind by a run that never reached it.

## Task 2 — Link hygiene

Two directions: **backfill** the links that couldn't exist when an earlier entry was written, and **prune** duplicate or weak links. This is the only place wiki-linter modifies body-prose wikilinks and the Related footer, and the only **destructive** operation in the skill.

### Backfill (add missing links)

Step 0's **backfill candidates** are the worklist: it has already scanned every full entry's prose for bare-text mentions of other entries' titles/aliases (and their plurals), excluding bare common nouns and targets already linked in that entry. Walk that list and, for each candidate that clears the closeness bar below, wrap the **first body-prose occurrence** in the piped form `[[slug|Display]]` (bare when display = slug), the display label preserving the entry's wording (alias mentions keep the source surface form — "Lambda Rank" → `[[lambdarank|Lambda Rank]]`). Add newly-linked targets to the `**Related:**` footer per the footer format. Only the first occurrence is wrapped; later mentions stay bare text.

#### The closeness bar

When a selected surface is italicized or bolded, remove those surrounding emphasis markers as part of linking it: `*mean squared error*` becomes `[[mean-squared-error|mean squared error]]`, never `*[[mean-squared-error|mean squared error]]*`. Leave code spans and listings untouched, and count an existing link with a heading, block anchor, path, or `.md` suffix as already linking its target. After the edits, re-scan to catch any formatting or duplicate-link defect introduced by the backfill itself.

**The bar is strict and conceptual.** "Should A link to B?" is judged on how closely related the two entities are, not on whether some source discussed both, and not on whether the mention unambiguously *refers* to the entity. Stated in full, a mention earns a link when **all** of these hold:

1. **The reader would genuinely benefit from jumping there** — the entity is a *node worth visiting from this passage*, not merely a name that happens to have a file.
2. **The relationship is conceptual**, not incidental co-occurrence: B explains, contrasts with, composes, generalizes, or is a mechanism of what A's passage is saying.
3. **Positive trigger:** a paragraph that attributes mechanism/architecture/method to a named entity ("X works by…", "X introduced…", "X uses [technique]") with more than one sentence of *how* clears the bar automatically.
4. **Reject** passing mentions, glancing references, and bare name-drops **even when the slug exists and the reference is unambiguous**. Correctly identifying which entity a word refers to is a *precondition* for linking, never a reason to link.

**When in doubt, do not link — over-linking is the failure mode.**

**This bar is wiki-linter's own, and it is the only one operating across entries.** It used to be stated as a bar *shared* with wiki-builder, because both skills linked vault-wide and a marginal mention was otherwise added by one and pruned by the other on alternating runs — churning `updated:` with nothing to show for it. That conflict can no longer arise: wiki-builder links only inside the entries it writes, so nothing else is judging the cross-entry mentions Task 2 judges. **Calibrate the bar on what the vault needs, not on matching another skill's threshold.** (The bar itself is unchanged — the criteria above are exactly as strict as they were; what went away is the obligation to keep them in lockstep with someone else's.)

**Cross-domain bare-term rule (do not violate).** Never auto-link a bare common noun to a bare slug. A body's bare "entropy" is linked only with the qualified target and the source's wording — `[[information-entropy|entropy]]` in an ML context, `[[thermodynamic-entropy|entropy]]` in thermodynamics — never `[[entropy]]`. If the intended sense is ambiguous, leave it as plain text and flag it in the report. The corpus of bare terms this covers is wiki-builder's — *Cross-domain term disambiguation* in `wiki-builder/references/writing.md` (§3), which also carries the never-an-alias rule ("the bare term is not added as an alias to any entry"; the `aliases` field definition in §1 restates it under its redundant-alias rules). The scanner keeps its own working subset in the `COMMON_NOUNS` constant in `scripts/scan_vault.py` (it uses it to suppress bare-common-noun backfill candidates); that list is a floor for the scan, not the authority — wiki-builder's corpus is. Alias-mediated bare-noun surfaces (`attribute`, `target`, `predictor` — a single all-lowercase word reached only through an alias) are **not** suppressed, but arrive tagged `bare_noun_alias: true`: judge them as one batch, since they nearly always fail the closeness bar and re-surfaced for identical re-judgment every run, while a qualified-target link to a bare term stays legal in principle.

### Prune (remove links) — the destructive operation

Two removal triggers only (both signed off):

1. **De-duplicate.** wiki-builder wraps only the first occurrence; if an entry has the same target wikilinked twice or more in its body, unwrap the 2nd+ occurrence(s) to bare display text, keeping the first. (Surfaced by the scanner's `item10/dup` findings.)
2. **Drop weak links.** Unwrap a body wikilink, and remove the corresponding `**Related:**` entry, when the link fails the strict closeness bar above — a tangential name-drop that got linked. Dropping a body link to bare text and pruning it from Related are done together so the two stay consistent.

**Never** prune via this mechanism: `tags:`, `sources:`, `parents:` (each has its own rules; and `tags:` are `#`-tags, not wikilinks, so they're not even in the link-pruning domain). Pruning operates on body-prose wikilinks and Related-footer entries only. Because pruning is destructive and irreversible in a single pass, every prune is itemized in the run report (entry, target, reason) so the user can review. **Backfill ⇄ prune do not oscillate.** Step 0's backfill candidates have no memory of past prunes, so a link pruned as weak on an earlier run *will* re-appear as a candidate — apply the same closeness bar and reject it again. The judgment is stable because it is a property of the two entities, not of run history. **Nothing outside this skill re-adds a pruned cross-entry link:** wiki-builder links only within the entries it writes, and within a merged entry only the prose it wrote on that run — a bare mention already in the body is not a candidate for its interlink sweep, and earns no `**Related:**` line either (`wiki-builder/references/merge.md` item 7; `CONVENTIONS.md` §9). **So a prune here is final.** The rule used to concede one exception — *unless a later source causes that entry to be rewritten* — and that exception was the leak: the merge re-wrapped the pruned mention and put its footer line back, this pass pruned it again, and `updated:` moved on both passes with nothing to show for it. With it gone, a pruned mention returning on the next scan is Step 0's missing memory and nothing more.

### Dangling links (target missing)

`item10/ambiguous` is report-only: several files share the basename or several entries claim the alias. Preserve the entire link until its destination is resolved. On an unambiguous `item10/alias` or `item10/case` repair, change only the destination spelling and preserve existing heading/block anchors and any explicit display label.

A body or Related-footer wikilink whose target is not a real file in `Wiki/`. **First make sure it really is one:** the scanner separates these from THREE look-alikes that are not danglers at all — each *resolves* in Obsidian, so dropping one destroys a working link, and the retired stub remedy did worse (the warnings below stand as the record of why). **`item10/unparsed`** — the target names a file that IS in `Wiki/` but did not parse as an entry (no frontmatter, `item1`; or unreadable bytes, `item0`). The link resolves in Obsidian; the file is real; **stubbing it writes a one-line stub over the user's file.** The fix is to repair that file, which its own `item0`/`item1` finding describes. And from `item10/case` — a target that matches an existing entry once case and Unicode normalization are ignored, which *resolves* in Obsidian on the vault's case-insensitive APFS volume and is fixed by rewriting the link's spelling, never by stubbing (a stub written at the variant spelling opens the existing entry on that volume and overwrites it). And **`item10/alias`** — a target that is not an entry at all but another entry's **alias**, which Obsidian resolves as an alternative slug, so the link works. It is fixed by rewriting it to the piped `[[owner|Alias]]` form the finding gives, **never by stubbing**: a stub at the alias's own name creates a *file*, a file outranks an alias, and every `[[Alias]]` in the vault silently stops resolving to the entry that owns it and starts resolving to the new one-line stub — which nothing afterwards reports as an item-18 clash, so the theft is permanent and invisible. This is the look-alike whose *documented* remedy used to be the damage: the target was reported as `item10/dangling`, and stubbing a dangler is exactly what steals the alias. If you are working a dangler list built by hand rather than from the scan, apply the same look-alike test before dropping anything. **Resolving genuine danglers is wiki-linter's job, vault-wide, and nothing has swept ahead of it.** wiki-builder's orphan audit reaches only the entries it created or merged on its own run, so every other dangler in the vault — including ones inherited from runs made before that narrowing, and ones in entries no recent run touched — survives until Task 2 finds it. Never skip an `item10/dangling` finding on the assumption that a builder run already handled it, and expect the first lint after this change to surface a backlog of them. **Resolve every genuine dangler by dropping the link to bare text** — replace `[[slug|Display]]` with the display text, and remove the matching Related-footer item. **Stubs are never created** — stub creation is retired plugin-wide, because a one-sentence placeholder is exactly the clutter the vault's owner asked to stop accumulating. When the dangling target looks like a *real gap* — a concept several entries lean on, a heavily-referenced name — drop the link all the same, and surface the concept as a **missing-entry candidate** in the run report and `wiki-notes-suggestions.md`, so the user can feed a source through wiki-builder and create it properly; a passing-mention dangler is just dropped and itemized like any prune. **`tags:` cannot dangle** — they are `#`-prefixed discipline slugs, not wikilinks, so they reference no note and are never part of dangling detection or stub creation (unlike the old `roots:`, which was a wikilink and could dangle into a discipline stub — discipline stubs no longer exist). **`![[…]]` image embeds and note transclusions are not dangling links either** — an embed points at `Sources/Images/`, not an entry, so it is excluded from dangling detection; never stub or drop one. Their own check is item 12's `item12/missing-image`, which runs when Step 0 was given `--images` and reports an embed naming a file that is not in `Sources/Images/` — report-only, and never resolved by deleting the embed. **A `[[…]]` inside any LISTING is not a link either** — a fenced block (``` or `~~~`), an indented code block (4 spaces or a tab), or an inline code span — and none of them reaches this protocol: each renders as literal text, so treating one as a dangler would prescribe an edit for a sample of link syntax. A list item's indented **continuation** is not a listing, and a link there is real and still checked.
