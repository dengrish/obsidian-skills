# Link hygiene — the full rules (Task 2)

**Read this when Task 2 runs — before applying or rejecting a backfill candidate, pruning a link, or resolving a dangling target.** It owns the closeness bar, removal triggers, and dangling-link protocol. Do not perform those operations from the [entrypoint summary](../SKILL.md#task-2--link-hygiene) alone.

**wiki-linter owns retrospective and vault-wide link editing.** Builder links only within entries it writes, and on merge only when the active source introduces the target or contributes a substantive relationship to it; rewriting a carried-over sentence is not link provenance. Task 2 covers eligible bare mentions, weak links, and genuine dangling targets across the requested maintenance scope, including entries untouched by a recent source run. Neither skill creates stubs.

## Task 2 — Link hygiene

Two directions: **backfill** links that could not exist when an earlier entry was written, and **prune** duplicate or weak links. Task 2 judges whether a link is added, kept, or removed. Task 1 may separately correct the spelling of an existing, unambiguous link or footer without changing its destination or meaning.

### Backfill (add missing links)

Surfaces claimed by multiple entries are omitted from backfill candidates; resolve their ownership before linking them. A destination whose canonical slug is in the scanner's designated common-noun set stays excluded through every title, plural, or alias surface. A surface that is itself in that set is excluded too. Other single lowercase aliases of qualified destinations are emitted with the `bare_noun_alias` flag described below; the flag requests stricter review, not automatic rejection. An `Organism` may also contribute a local common-name surface when its description or opening sentence directly equates that surface with the Organism's canonical title. Such candidates carry `organism_common_name: true`: the flag establishes a permissible display label only, never a global alias or an automatic link. The surface is the complete bound phrase (plus its natural inflection), never an unbound head extracted from it: `fruit fly` does not make every bare `fly` a Drosophila candidate.

Step 0's **backfill candidates** are the worklist: it has already scanned every full entry's prose for bare-text mentions of other entries' titles/aliases (and their plurals) plus directly bound Organism common names, excluding designated common-noun surfaces/destinations and targets already linked in that entry. Walk that list and, for each candidate that clears both surface identity and the closeness bar below, wrap the **first body-prose occurrence** in the piped form `[[slug|Display]]` (bare when display = slug), the display label preserving the entry's wording (alias mentions keep the source surface form — "Lambda Rank" → `[[lambdarank|Lambda Rank]]`). For `organism_common_name: true`, verify that the mention really names that organism in context and is close enough to link; do not copy the surface into `aliases:`. Then curate `**Related:**` under the footer rule: add the target only when it is one of the entry's most useful navigation choices, rather than copying every accepted body link into the footer. Only the first body occurrence is wrapped; later mentions stay bare text.

Hidden HTML/Obsidian comments, escaped wikilink examples, headings, inline Markdown image syntax and alt text, captions, table cells, code/listings, Markdown link-reference definitions, inline/full/collapsed/shortcut Markdown-link labels resolved by those definitions, bare URLs/autolinks, and Obsidian links/embeds are not new wikilink surfaces. The scanner masks them so an unwritable first occurrence cannot hide a later eligible prose occurrence; the executing agent must not reconstruct a candidate from one of those masked zones during semantic review.

#### The closeness bar

When a selected surface is italicized or bolded, remove those surrounding emphasis markers as part of linking it: `*mean squared error*` becomes `[[mean-squared-error|mean squared error]]`, never `*[[mean-squared-error|mean squared error]]*`. Leave code spans and listings untouched, and count an existing link with a heading, block anchor, path, or `.md` suffix as already linking its target. After the edits, re-scan to catch any formatting or duplicate-link defect introduced by the backfill itself.

**The bar is strict and conceptual.** "Should A link to B?" is judged on how closely related the two entities are, not on whether some source discussed both, and not on whether the mention unambiguously *refers* to the entity. Items 1–2 are the ordinary test; item 3 clears that test automatically, while item 4 remains a rejection floor:

1. **The reader would genuinely benefit from jumping there** — the entity is a *node worth visiting from this passage*, not merely a name that happens to have a file.
2. **The relationship is conceptual**, not incidental co-occurrence: B explains, contrasts with, composes, generalizes, or is a mechanism of what A's passage is saying.
3. **Positive trigger:** a paragraph that attributes mechanism, architecture, or method to a named entity ("X works by…", "X introduced…", "X uses [technique]") with enough mechanism-level detail for a self-contained atomic entry clears the bar automatically.
4. **Reject** passing mentions, glancing references, and bare name-drops **even when the slug exists and the reference is unambiguous**. Correctly identifying which entity a word refers to is a *precondition* for linking, never a reason to link.

**When in doubt, do not link — over-linking is the failure mode.**

**This bar is wiki-linter's own.** Apply it consistently to additions and removals. Builder's separate source-run scope does not authorize rewrapping a carried-over mention this pass deliberately pruned merely because its sentence was rewritten. A later source may supply a genuinely new substantive relationship to the same target; builder may link that source-backed contribution and report it, and this task then judges the new relationship under the same bar.

**Cross-domain bare-term rule (do not violate).** Never auto-link a bare common noun to a bare slug. A body's bare "entropy" is linked only with the qualified target and the source's wording — `[[information-entropy|entropy]]` in an ML context, `[[thermodynamic-entropy|entropy]]` in thermodynamics — never `[[entropy]]`. If the intended sense is ambiguous, leave it as plain text and flag it in the report. The corpus of bare terms this covers is wiki-builder's — *Cross-domain term disambiguation* in `wiki-builder/references/writing.md` (§3), which also carries the never-an-alias rule ("the bare term is not added as an alias to any entry"; the `aliases` field definition in §1 restates it under its redundant-alias rules). The scanner keeps a working subset in `COMMON_NOUNS`. It suppresses both a surface in that set and every surface whose destination slug is in that set; this is a mechanical floor, while wiki-builder's corpus remains the authority. A different shape, a single all-lowercase alias of a **qualified** destination (`attribute`, `target`, `predictor`), may still be emitted as `bare_noun_alias: true`. Judge those candidates as one batch: they nearly always fail the closeness bar and otherwise resurface for identical re-judgment, but a qualified-target link using a bare surface can be legal when the sense and relationship are clear.

### Prune links within the requested scope

The executing agent applies exactly these three removal triggers without separate sign-off:

1. **Remove self-links.** An entry never links to itself through its canonical slug, a path/`.md`/case spelling, or one of its own aliases. Render an ordinary body mention as plain text and remove the Related item. If an anchored body link provides real within-note navigation, preserve that function by rewriting it as a local `[[#Heading]]` or `[[^block]]` link instead; preserve an explicit label as `[[#Heading|Display]]` or `[[^block|Display]]`. (Scanner: `item10/self`.)
2. **De-duplicate.** wiki-builder wraps only the first occurrence; if an entry links the same resolved entry twice or more in its body, unwrap the 2nd+ occurrence(s) to bare display text, keeping the first. Path/`.md`/case/Unicode spellings and an unambiguous alias beside the canonical slug still resolve to one entry when the inventory identifies one owner; a file outranks an alias. If several files share a basename, distinct qualified paths stay distinct, and repeated bare or ambiguous-alias links remain report-only until ownership is resolved. (Scanner: `item10/dup`.)
3. **Drop weak links.** Unwrap a body wikilink, and remove the corresponding `**Related:**` entry, when the link fails the strict closeness bar above — a tangential name-drop that got linked. Dropping a body link to bare text and pruning it from Related are done together so the two stay consistent.

**Never** prune via this mechanism: `tags:`, `sources:`, `parents:` (each has its own rules; and `tags:` are `#`-tags, not wikilinks, so they're not even in the link-pruning domain). Pruning operates on body-prose wikilinks and Related-footer entries only. Itemize every prune in the run report (entry, target, reason) for traceability; this is post-action reporting, not an approval or review gate. **Backfill ⇄ prune do not oscillate on unchanged evidence.** Step 0's backfill candidates have no memory of past prunes, so a link pruned as weak on an earlier run *will* re-appear as a candidate — apply the same closeness bar and reject it again. wiki-builder does not restore it from a carried-over claim, even if integration rewrites that sentence; target and relationship provenance comes from the active source, not edit history (`wiki-builder/references/merge.md` item 7; `CONVENTIONS.md` §9). A later source can genuinely add a new substantive relationship to the same target. That is new evidence rather than oscillation: builder may link and report it, and this task reassesses that relationship on the next pass. Without such evidence, a returning candidate is Step 0's missing memory and nothing more.

### Dangling links (target missing)

`item10/ambiguous` is report-only: several files share the basename or several entries claim the alias. An exact or unique-suffix qualified path can identify one same-basename file; a qualified path matching none remains ambiguous while several owners coexist, rather than becoming a destructive dangling-link instruction. Preserve the entire link until its destination is resolved. On an unambiguous `item10/alias` or `item10/case` repair, change only the destination spelling and preserve existing heading/block anchors and any explicit display label.

A body or Related-footer wikilink whose target is not a real file in `Wiki/`. **First make sure it really is one:** the scanner separates these from three look-alikes that are not genuine missing-target findings. **`item10/unparsed`** names a file that is in `Wiki/` but did not parse as an entry (no frontmatter, `item1`; or unreadable bytes, `item0`). The file is real; **stubbing it would overwrite the user's file.** Repair that file under its own `item0`/`item1` finding. **`item10/case`** has one existing owner after the plugin's case/Unicode-normalization fold. Rewrite the target to that owner's exact on-disk spelling on every host; never create a competing variant, because some filesystems alias the spellings while others store both. **`item10/alias`** names another entry's unambiguous alias, which Obsidian resolves as an alternative slug. Rewrite it to the piped `[[owner|Alias]]` form the finding gives, **never stub it**: a file outranks an alias, so a new file at the alias name would steal those links from their owner. If a dangler list was built by hand rather than from the scan, apply the same three checks before dropping anything.

**Resolving genuine danglers is wiki-linter's job, vault-wide, and nothing has swept ahead of it.** wiki-builder's orphan audit reaches only the entries it created or merged on its own run, so every other dangler in the vault survives until Task 2 finds it. Never skip an `item10/dangling` finding on the assumption that a builder run already handled it. **Resolve every genuine dangler by dropping the link to bare text** — replace `[[slug|Display]]` with the display text, and remove the matching Related-footer item. **Stubs are never created.** When the target looks like a real knowledge gap, drop the link all the same and surface a **missing-entry candidate** in the run report and `wiki-notes-suggestions.md`, so a supporting source can go through wiki-builder; a passing-mention dangler is just dropped and itemized like any prune.

`tags:` cannot dangle because they are discipline tags, not wikilinks. Image embeds and note transclusions are outside entry-link detection and are never stubbed or dropped here; `item12/missing-image` reports an embed absent from the supplied image inventory without authorizing deletion. A `[[…]]` inside a hidden HTML/Obsidian comment, an escaped wikilink example, or a fenced, indented, or inline code listing is not a rendered link and never reaches this protocol. Preserve these annotations and samples. A list item's indented continuation is ordinary prose and remains checked.
