# Edge cases

**Read this when the run hits one of these** — a discipline whose entries are all stubs, a full entry with blank `tags:`, a discipline's root, a discipline with no entry for the discipline itself, a re-run on an already-clean vault, hand-edited entries, a retitle that would collide, a suspected idempotency break, or a user-narrowed scope.

- **A discipline whose entries are all stubs** — no MOC (nothing non-stub to list); report it.
- **An entry with blank `tags:`** — valid on a full entry (no discipline genuinely applies); no MOC placement, no `parents:` forced (it has no tree, so it is not a root and is not self-parented either — `parents:` stays empty, written `parents: []`); list under *unplaced entries*. (Blank `tags:` on a *stub* is **not** valid — see item 8.)
- **A discipline's root** — always that discipline's **MOC note**, `[[<discipline-slug>-moc]]` (`[[machine-learning-moc]]` for `#machine-learning`). It is not chosen and never has to be found: wiki-linter writes the file in Task 3, its name comes straight off the tag, and it is a real note so the wikilink resolves. Top-level branches take it as their parent; everything below points at its nearest broader full entry. **No entry is ever its own parent.** Any self-parented slug is stale `parents:` from a pre-MOC-root run, interruption, or hand edit. Task 3 overwrites it only when its transitive discipline closure is authorized; otherwise preserve and report it. The correct in-closure count after a completed pass is zero. See *Populate `parents:`*.
- **A discipline with no entry for the discipline itself** — the normal case, not an edge case: wiki-builder only writes entries for entities a source covers substantively, so `machine-learning.md` typically does not exist and wiki-linter may not mint it. Nothing special is needed — the MOC is the root, and the tree's top-level bullets are the field's broadest branches. If such an entry *does* exist, it is the single top-level bullet with the branches nested under it; the root is the MOC either way.
- **A re-run on an already-clean vault** — the churn-avoidance contract makes this close to a no-op: Step 0 runs, finds nothing actionable, and the report says so. MOCs are regenerated only if the tree changed.
- **Hand-edited entries** — the linter touches only what violates a rule or needs a link/parent; it does not rewrite conforming prose, so hand-edits that conform survive. A hand-edit that itself violates a rule (e.g. an added unbolded-should-be-italic term) will be corrected — same as wiki-builder. **A `read: true` the user has ticked is not a hand-edit to correct**: the field is theirs, the linter never writes it, and an entry whose `read:` key is missing entirely is reported rather than filled in — see *Dates* and item 2.
- **A retitle that would collide** with an existing slug — don't rename into a collision; report both entries as an unresolved duplicate/disambiguation proposal. The current lint run still completes.
- **Idempotency** — running the linter twice in a row produces no second-pass changes (the first pass made everything conform). This now includes the MOC: a second pass on unchanged content must **not** reshuffle a structure that already fits — the no-op guard keeps it — so re-deriving a different-but-equivalent layout is a bug, the same as finding a phantom new violation. If a second pass changes anything, surface it.
- **User narrows to one task** — still run Step 0; skip the other tasks; the report covers only what ran.
- **User narrows to selected entries** — Task 1 and Task 2 stay within that entry set. For Task 3, seed with those full entries and their tags; add all full entries and the MOC for each included discipline, then every other tag on included multi-tagged entries, repeated until stable. A selected untagged full entry stays in the closure so its parents can become `[]`. Skip Task 3 for the connected set and report that exact closure unless the request already covers it or the user explicitly authorizes expansion. The scan itself never supplies authorization.
- **Task 3 is interrupted** — rerun the same authorized closed set from current files, re-deriving every included MOC and complete parent union. Multi-file edits are not transactional, so continuing at the next filename can preserve a mixed old/new rendering. Do not declare completion until the scoped postconditions pass.
- **Legacy MOC without any generated-region marker** — preserve every MOC and `parents:` value in its connected closure. Do not guess which adjacent bullets are generated or user-authored. Report the exact file and prepare the proposed marked tree; migrate only after the user identifies or approves the legacy tree span, preserving every line outside it.
- **Malformed MOC markers** — a missing counterpart, duplicate, reversed, indented, or nested marker state is ambiguous current ownership, not an unmarked legacy migration. Preserve every MOC and `parents:` value in the connected closure, report the exact condition, and repair only after the user approves the intended region or marker correction. See the hierarchy reference's marker protocol.
