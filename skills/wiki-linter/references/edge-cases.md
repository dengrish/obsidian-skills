# Edge cases

**Read this when the run hits one of these** — a discipline whose entries are all stubs, a full entry with blank `tags:`, a discipline's root, a discipline with no entry for the discipline itself, a re-run on an already-clean vault, hand-edited entries, a retitle that would collide, a suspected idempotency break, or a user-narrowed scope.

- **A discipline whose entries are all stubs** — no MOC (nothing non-stub to list); report it.
- **An entry with blank `tags:`** — valid on a full entry (no discipline genuinely applies); no MOC placement, no `parents:` forced (it has no tree, so it is not a root and is not self-parented either — `parents:` stays empty, written `parents: []`); list under *unplaced entries*. (Blank `tags:` on a *stub* is **not** valid — see item 8.)
- **A discipline's root** — always that discipline's **MOC note**, `[[<discipline-slug>-moc]]` (`[[machine-learning-moc]]` for `#machine-learning`). It is not chosen and never has to be found: wiki-linter writes the file in Task 3, its name comes straight off the tag, and it is a real note so the wikilink resolves. Top-level branches take it as their parent; everything below points at its nearest broader full entry. **No entry is ever its own parent** — self-parenting is not rare now, it is *gone*, so the correct count in `hierarchy_diagnostic.self_parented` is **zero**. Any self-parented slug the scanner reports is stale `parents:` from a pre-MOC-root run (or a hand-edit); this run overwrites it, so `check_rooting: true` clears itself with no intervention. This keeps every placed entry's `parents:` populated and distinguishes a placed entry from an unplaced one (`parents: []`). See *Populate `parents:`*.
- **A discipline with no entry for the discipline itself** — the normal case, not an edge case: wiki-builder only writes entries for entities a source covers substantively, so `machine-learning.md` typically does not exist and wiki-linter may not mint it. Nothing special is needed — the MOC is the root, and the tree's top-level bullets are the field's broadest branches. If such an entry *does* exist, it is the single top-level bullet with the branches nested under it; the root is the MOC either way.
- **A re-run on an already-clean vault** — the churn-avoidance contract makes this close to a no-op: Step 0 runs, finds nothing actionable, and the report says so. MOCs are regenerated only if the tree changed.
- **Hand-edited entries** — the linter touches only what violates a rule or needs a link/parent; it does not rewrite conforming prose, so hand-edits that conform survive. A hand-edit that itself violates a rule (e.g. an added unbolded-should-be-italic term) will be corrected — same as wiki-builder. **A `read: true` the user has ticked is not a hand-edit to correct**: the field is theirs, the linter never writes it, and an entry whose `read:` key is missing entirely is reported rather than filled in — see *Dates* and item 2.
- **A retitle that would collide** with an existing slug — don't rename into a collision; flag both entries for the user (likely a genuine duplicate or a disambiguation need).
- **Idempotency** — running the linter twice in a row produces no second-pass changes (the first pass made everything conform). This now includes the MOC: a second pass on unchanged content must **not** reshuffle a structure that already fits — the no-op guard keeps it — so re-deriving a different-but-equivalent layout is a bug, the same as finding a phantom new violation. If a second pass changes anything, surface it.
- **User narrows to one task** — still run Step 0; skip the other tasks; the report covers only what ran.
