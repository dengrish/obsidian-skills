# The scanner — CLI, output contract, and what it does not check

**Read this when any of three conditions holds — each checkable before you open the file:**

1. **The scan JSON contains an `item16` or `item18` finding.** `grep -cE '"item16"|"item18"' '/tmp/wiki-scan-<run-id>.json'` (ERE with a plain `|` — the BRE `\|` spelling is a GNU extension that macOS grep reads as a literal pipe and never matches) — those two are the only checks in the scanner that are *deliberately* loose, and *Before you call a finding a false positive* below is why. If neither fires, no finding in this scan has a documented reason to be overridden.
2. **You need a JSON field the Step 0 table in `SKILL.md` does not list** — `wiki_path`, `item0`, the sub-keys of `problems` / `problem_tally` / `collision_candidates` / `hierarchy_diagnostic`, or the exclusion rules behind `backfill_candidates`. The *Output contract* below is the full schema.
3. **The scan exited non-zero or crashed** — exit `2` is a usage error (see *CLI*); anything else is execution friction worth reporting.

For a routine run none of these holds, and the Step 0 table is enough. (The old trigger was "when a finding looks wrong, before you override it" — a judgment you can only make *after* reading, which made this a mandatory read in practice. The three conditions above are what that judgment actually resolves to.)

The scanner is `scripts/scan_vault.py` — stdlib-only Python 3, no install step. It is the *only* place the deterministic checks live; `SKILL.md` and `references/qc-items.md` say what to do with what it finds, never how it finds it.

## CLI

```
python3 scripts/scan_vault.py WIKI [--images DIR] [--out FILE] [--indent N]
```

- `WIKI` — the vault's **`Wiki/` folder**, not the vault root. MOCs (`*-moc.md`) and the three suggestion logs (`*-suggestions.md`) live in the root, which is why they are never linted and never listed inside a MOC: the scanner never walks them.
- `--images DIR` — the vault's flat **`Sources/Images/`** folder. With it, every `![[…png]]` embed in every entry is checked to name a file that is really there, emitted as `item12/missing-image`. **Pass it on every real run.** `CONVENTIONS.md` §1 makes this skill that folder's embed validator and nothing else in the plugin walks `Wiki/`, so without the argument that check silently does not run at all and an entry embedding a figure that is not on disk — the state §1a's rename hazard leaves behind — scans clean. It turns on one check and changes nothing else in the output. Matched on the **basename**, case- and normalization-folded (Obsidian resolves an embed by basename, and the documented vault's volume is insensitive to both), so a path-qualified `![[Sources/Images/X.png]]` and a case variant both resolve. Embeds inside fenced code are skipped: a listing showing embed syntax is not an embed.
- `--out FILE` — write the JSON to `FILE` instead of stdout. Use this on any real vault and read the file in slices (filter by `item`, by slug, by key) rather than pulling the whole object into context.
- `--indent N` — JSON indent, default `2`; `--indent 0` emits one compact line.
- Exit status `2` with a usage error if `WIKI` is not a directory, or if `--images` is given and is not a directory. The second guard is deliberate: a mistyped image folder that read as "empty" would report **every** embed in the vault as naming a missing file, and nothing in the output would distinguish that from a genuinely broken vault. Every other failure is a genuine crash worth reporting as execution friction (SKILL.md, *Closing the loop*).

The scanner **never writes to the vault.** It reads `Wiki/*.md` and prints; every fix, MOC, `parents:` value, and log append is the model's own edit.

## Output contract

One JSON object with these keys.

| key | type | contents |
| --- | --- | --- |
| `run_timestamp` | string | `YYYY-MM-DD HH:MM` at scan time. This is the stamp for the suggestion-log dated blocks — use it, do not re-derive a time. |
| `wiki_path` | string | absolute path actually scanned (confirms an overridden path took effect) |
| `inventory` | object | `entries`, `full`, `stubs` (counts) and `full_slugs`, `stub_slugs` (sorted slug lists). A slug is the filename without `.md`. |
| `discipline_tags` | object | valid enum slug → `{"full": N, "stub": N}`. The keys are the disciplines **in use** — exactly the MOCs Task 3 builds (a discipline needs ≥1 **non-stub** entry, so a key whose `full` is `0` gets no MOC). |
| `off_enum_tags` | object | malformed / off-enum tag slug → the entries carrying it. Every one of these is an item-8 finding too; this key groups them by bad slug so a vault-wide pattern is visible at a glance. |
| `untagged_full` | array | full entries whose `tags:` key is present but empty. **Not a violation** — they are *unplaced*: no MOC, no `parents:`. |
| `problems` | array | `{"slug", "item", "message"}`, sorted. The deterministic violations. See *Item keys* below. |
| `problem_tally` | array | per item: `{"item", "entries", "pct_of_full", "issues"}`, ranked by entries affected. `pct_of_full` is the share of **full** entries touched — the recurrence evidence a wiki-builder proposal cites. |
| `collision_candidates` | array | `{"a", "b", "probe", "detail"}` — two slugs the item-5 probes matched. `probe` ∈ `exact`, `plural`, `hyphenation`, `word-order`, `word-order-singular`, `µ-variant`; `detail` is the two colliding identifiers. `word-order-singular` sorts the tokens *after* singularising each one, which is what catches `weight-tying` against `tying-weights` — a pair a raw token sort misses on `weights` ≠ `weight`. It has to be here because wiki-builder runs the same two-key probe on every candidate (`wiki-builder/SKILL.md`, step 3 probe (e)) and CONVENTIONS §9 makes whole-vault dedup detection this skill's alone: a pair already sitting in the vault is seen by nothing else. Unordered pairs, de-duplicated per probe. **Review only — never merged.** wiki-builder's create-time probe (g), token-superset, is deliberately **not** mirrored in this vault-wide sweep — qualified-vs-base pairs (`feature-machine-learning` beside `machine-learning`) are exactly what the disambiguation rules produce on purpose, so a whole-vault pass would flood on legitimate pairs; its absence from this probe list is by design (`wiki-builder/SKILL.md`, step 3). |
| `rename_candidates` | array | `{"slug", "new_slug", "inbound_links", "target_exists"}` — entries whose filename ≠ `slug(title)`. `inbound_links` is how many wikilinks a rename would have to rewrite; `target_exists: true` means the destination is already taken — either an existing file **(whether or not it parsed as an entry: a file with no frontmatter is absent from `inventory` and still occupies its name, and the approved `mv` would destroy it)**, **or a second candidate in this same list proposing the same `new_slug`** — so this is a likely duplicate/disambiguation and must **not** be renamed into (applying both of a colliding pair in sequence would have the second silently overwrite the first). `new_slug` is never empty: a title that reduces to the empty slug (CJK, all-symbol) is reported as an `item5` problem instead, because renaming to it would produce a file literally called `.md`. **Propose for approval — never auto-applied.** |
| `backfill_candidates` | array | `{"slug", "target", "surface"}` — a bare-text mention of `target`'s title/alias (or its plural) found in `slug`'s prose. Existing links, embeds, bare common nouns, and targets already linked in that entry are excluded, and stubs are not scanned. **Three line kinds are masked out** for one reason — the worklist proposes linking the *first* occurrence, so a first occurrence somewhere a link may not be written is both un-actionable and *hides* the linkable occurrence below it: whole-line **italic captions** (item 12 forbids links in captions), **markdown table rows** (item 10 forbids links in table cells), and **fenced code blocks** (a listing is shown, not asserted, and `[[…]]` inside one renders literally). The plural form is the title with its **head token** inflected, so an irregular (`Confusion matrix` → `Confusion matrices`, `Hypothesis` → `Hypotheses`) is matched — inflecting the whole title matched no irregular in `plurals.py`'s table and produced `Confusion matrixes`. **`bare_noun_alias`** (bool) tags a candidate whose matched surface is a single all-lowercase word reached only through an alias (`attribute`, `target`) — these flooded the worklist with identical re-judgments every run; batch them in the report. A worklist, not a decision: each one still has to clear the closeness bar, tagged or not. |
| `hierarchy_diagnostic` | object | `full_entries`, `self_parented` (slugs whose existing `parents:` points at themselves), `parent_cycles` (cycles of length ≥ 2 in `parents:` — `[["ping", "pong"]]` for two entries parenting each other — each listed once and rotated to start at its alphabetically first slug; a self-parent is the 1-cycle and stays in `self_parented`. An entry in a cycle has **no path to a MOC root**, so Task 3 breaks the cycle before placing either end; the correct value is `[]`), and `per_discipline`: `{"discipline", "self_parent", "full", "check_rooting"}`. `check_rooting` is `true` at ≥1 self-parent in one discipline. **`per_discipline` lists only disciplines with ≥1 self-parented full entry — a discipline absent from it has zero, not "unknown"**, so a discipline whose `parents:` are all empty simply does not appear; that is the expected state on a never-linted vault and is not itself a finding. Note this reflects the `parents:` **from the last run**, not the tree you are building. **Its meaning changed with the MOC-root rule** (`references/hierarchy.md`): trees are now rooted at the discipline's MOC note, so no entry self-parents and the correct value of `self_parented` is `[]`. Every slug it lists is therefore **stale `parents:`** — written by a pre-MOC-root run or hand-edited — which this run overwrites; `check_rooting: true` is expected on the first run after the change and clears itself. The threshold moved with the rule — it was `≥3`, the old model's tolerance for ~1 legitimate root per discipline, and is now `≥1`, because after a run any non-empty `self_parented` at all is a defect. |

### Item keys in `problems`

`item1` … `item19` map to wiki-builder's Quality Checklist item of that number; `references/qc-items.md` is the per-item enforcement detail. (There is no `item20`: the checklist's old last item, *Importance*, was retired with the `importance:` field. It was the final item, so nothing was renumbered and no gap was left.) **Thirteen keys are compound** (`itemN/qualifier`) and route differently from a plain `itemN`:

- **`item2/read-missing`** — the `read:` key is absent. **Report-only**, and for the same reason as `item3/user-action`: `read:` is the user's review checkbox and the linter never writes it, so the only value it could supply — `read: false` — would mark an entry the user had already read as unread, destroying the one state the field carries. Goes to *Notes for the user*, never fixed.
- **`item2/read-null`** — `read:` is present but carries **no value**: a bare `read:`, `read: null` (any case), or `read: ~`, all of which are YAML null. **Report-only, and it must never be routed to a fix.** This is the *same class* as `item2/read-missing`, not a variant of `item2/read-type`, and the line between them is whether a fix would invent anything: a null holds no answer to preserve, so writing `false` supplies the user's review state rather than correcting its spelling — the exact harm `item2/read-missing` is report-only to prevent. (It was an `item2/read-type` finding until it turned out to route a valueless key to *fix in place* under the instruction "preserve which one it means", with nothing there to preserve. Do not re-file it as a fixable finding.) Goes to *Notes for the user* with the spelling found. Note the contrast with **`item2/parents-null`** below, which looks identical and *is* fixed: `parents: []` re-spells a value that is already empty and changes nothing.
- **`item2/read-type`** — `read:` is present, carries an answer, and merely spells it wrong: `"false"` quoted, `yes`/`no`, `0`/`1`. An **ordinary fix in place**: which boolean is meant is unambiguous, so rewrite the value to bare `true`/`false` and keep the sense. A quoted `"false"` is a non-empty string, which Obsidian's checkbox renders as permanently checked. The three `read` keys are separate findings because they route two different ways: only this one is fixed in place — `item2/read-missing` and `item2/read-null` never are, because neither has a value to keep.
- **`item2/parents-null`** — `parents:` is present but bare, i.e. YAML null rather than the empty list `[]`. An **ordinary fix in place**: write `parents: []`. The vault pins the property as `multitext`, so a bare key renders as an empty *text* field and disagrees with the declared type; `parents:` is wiki-linter's own field, so the spelling is its to normalize.
- **`item3/user-action`** — `created > updated`. Report-only; the linter cannot write either date. Goes to *Notes for the user*, never fixed.
- **`item2/obsidian-key`** — a frontmatter key that is **Obsidian's own** rather than this schema's: `cssclasses`, `cssclass`, `publish`, `permalink`, `cover`, `image`, `banner`, `icon`. **Report-only, and not a violation.** It is filed separately from a plain `item2` unexpected key because item 2 is a class-1 *fix in place*, and the only determinate reading of "fix an unexpected key in place" is to **delete** it — which throws away appearance or publish configuration the *user* set, in a field no skill here writes and nothing can reconstruct. Mention it under *Notes for the user*; never delete or reorder it. A genuinely off-schema key (`mood:`, a stacked-merge scar) is still a plain `item2`.
- **`item12/remote-image`** — a `![](http…)` embed. **Report-only, and not a violation**: wiki-builder mandates markdown image syntax for a remote URL, because a wikilink cannot address one. Rewriting it to `![[…]]` breaks the image and loses the URL. Report it as a candidate for localizing by re-running clipping-processor on the source clipping; never edit the entry for it.
- **`item12/missing-image`** — an `![[…]]` image embed naming a file that is **not in `Sources/Images/`**. Emitted **only when `--images` was given**; without it the check does not run and no such key appears, which is not the same as a clean vault. Obsidian renders an unresolvable embed as plain text, so the reader silently gets no picture and nothing else in the plugin looks: `CONVENTIONS.md` §1 assigns these embeds to this skill, and paper-summarizer's `note_lint.py --images` only ever sees an `Articles/` note. **Report-only, and never routed to a fix that touches the entry** — deleting the embed and its caption is the only thing "fix in place" could mean, and it destroys the one record of which figure belongs there. Both repairs are elsewhere: the figure was never extracted (run pdf-figure-extractor over that source), or an approved source rename renamed it with its source (§1a), in which case the embed is rewritten to the new stem once the user has confirmed the new name. This is the detector §1a's rename hazard relies on for `Wiki/`.
- **`item10/dangling`** — a wikilink target that does not resolve. Handled in Task 2 (`references/link-hygiene.md`), not as an ordinary QC fix: dropped to bare text (stubs are never created), with real gaps surfaced as missing-entry candidates.
- **`item10/case`** — a wikilink target that matches an entry **only case- or normalization-insensitively** (`[[roc-curve]]` against `ROC-curve.md`, or an NFC link against an NFD filename). The link *resolves* in Obsidian — the documented vault sits on case- and normalization-insensitive APFS — so this is **not** a dangler and must never be routed to the dangler protocol: dropping it destroys a working link, and on that filesystem, writing a "stub" at the link's spelling (the retired remedy) opens the existing entry and **overwrites it**. It is an ordinary fix in place — rewrite the link target to the on-disk slug the message names, exactly.
- **`item10/unparsed`** — a wikilink target naming a file that **is on disk but did not parse** as an entry: no frontmatter (`item1`) or unreadable (`item0`) — the two ways a file the walk reached can fail to parse (the walk is recursive and follows symlinks, so a subfolder is not a way to be missed). The link *resolves* in Obsidian, so this is **not** a dangler, and the dangler remedy is destructive twice over — a stub written at `Wiki/<target>.md` opens that very file and replaces it with one line. **Never stub it, and never drop the link.** There is nothing to fix in the linking entry; the repair belongs to the file the link names, and it is in this same scan as its own `item0`/`item1` finding. Fix it there and this clears itself.
- **`item10/alias`** — a wikilink target that is not an entry but another entry's **alias** (`[[tpr]]` where `recall.md` carries `aliases: ["tpr"]`). Obsidian resolves an alias as an alternative slug (`wiki-builder/references/writing.md`), so the link works — this is **not** a dangler. It is an ordinary **fix in place**: rewrite it to the piped form the message gives, `[[recall|TPR]]` — the owning entry as the target, the alias as the display label. **Never stub it.** A stub at the alias's own name creates a *file*, a file outranks an alias, and every `[[TPR]]` in the vault silently stops resolving to the entry that owns the alias and starts resolving to the new one-line stub — a re-pointing nothing afterwards reports as an item-18 clash. A **file** always wins over an alias, so a target that also matches a filename case-insensitively is reported as `item10/case`, not here.
- **`item10/dup`** — the same target wikilinked more than once in one entry's prose. Task 2's de-duplicate trigger. Counted over the entry's prose with **fenced blocks (``` and `~~~`), indented code blocks (4 spaces or a tab) and inline code spans of any backtick-run length blanked**, as the dangling scan is: a target shown in a listing was never linked, so "keep first only" applied to it would edit the listing or delete the one real link.

Two further keys are **not** an `itemN` and not compound:

- **`item0`** — the file could not be read at all (not UTF-8, a dangling symlink, a permission error). The scan **skips** that file and carries on, so one bad file no longer takes the whole run down; the entry is absent from `inventory` and from every worklist. Nothing to fix in the entry itself — report it to the user.
- **`stub`** — a legacy stub carrying a `**Related:**` footer, which the stub structure forbids (wiki-builder's SKILL.md, *Stubs (legacy)*: stubs carry no footer). It is an ordinary **fix in place** — delete the footer line — and is listed alongside the `itemN` fixes in `SKILL.md`'s finding taxonomy. It has no checklist number because item 11, which owns the footer, is one of the items stubs are exempt from.

## Floor, not ceiling

The scanner is a **floor, not a ceiling**. It mechanizes every deterministic check it can: YAML validity (item 1 — no frontmatter at all, an opening `---` that is not the file's first line, a closing fence that is not exactly `---` (a `----` or `--- text` line closes nothing — Obsidian shows no properties, and `find("\n---")` used to certify such an entry clean), and each individually unparseable frontmatter line, reported per line while the rest of the entry still scans), field order + **all nine mandatory keys present** (`title`, `type`, `sources`, `created`, `updated`, `description`, `tags`, `parents`, `read` — the same list, in the same order, as wiki-builder's `lint_entry.MANDATORY_KEYS`; only four were checked here until a `title:`-less entry came back from a whole-vault pass with no findings at all while a single-file lint reported two, and a `title:` key carrying **no value** — bare, null, or a list — is the same silent no-op and is reported under the same item-2 message) + quoting (item 2 — including the `read:` type check and the bare-`parents:` check, emitted as `item2/read-type` and `item2/parents-null` and both ordinary fixes, and the two valueless-`read:` checks emitted as `item2/read-missing` (no key) and `item2/read-null` (key present, value YAML null), both report-only findings the linter must not fix; see item 2 in Task 1), date format/validity + `created ≤ updated` (item 3 — **two independent findings, and neither gates the other**: the format check reports anything that is not `^\d{4}-\d{2}-\d{2}$`, while the ordering check parses any date it can understand — the unpadded `2026-1-1` included — and compares the parsed **dates**. Comparing the raw strings got it wrong both ways (`2026-1-1` sorts after `2026-01-02`, inventing a violation; `2026-12-01` sorts before `2026-2-05`, hiding one), and gating the *ordering* check on the *format* rule only traded the first error for the second. An unpadded date is reported for its spelling **and** still ordered by the day it names. The ordering check is emitted as `item3/user-action`, a report-only finding the linter must not fix; see item 3 in Task 1), sources format (item 4), slug↔filename + bare-slug + the five collision probes (item 5), the API-surface failure-string scan + backtick-identifier cap + fenced-code detection — **both fence spellings, ``` and `~~~`** (item 6), description presence + length + plain-text — on stubs as well as full entries (item 7), tags validity — enum membership, `#`-prefix, not-a-wikilink, abbreviation/synonym detection, **case variants of an enum slug** (`#Machine-Learning`), duplicate tags **counted on the canonical slug, after alias expansion and case folding** (so `#ml` beside `#machine-learning` is the one duplicate it is — counting raw slugs reported none, and item 8's own mandated rewrite then created it), and the stub-must-have-a-tag rule (item 8), blank-line/opener/Person-Event-dates — again on stubs as well as full entries, since a stub is exempt from item 9's *length* clause only (item 9), dangling + duplicate links — read with **fenced blocks (``` and `~~~`; a fence closes only on a run of the same character at least as long as its opener, per CommonMark, so a ``` sample inside a ```` block stays masked), indented code blocks (4 spaces or a tab) and inline code spans of any backtick-run length blanked** (a list item's indented continuation is *not* a listing and stays checked), since a `[[…]]` in a listing links nothing and treating it as a dangler would prescribe an edit for a sample of link syntax, and with the three resolving forms carved out under their own keys (`item10/case`, `item10/unparsed`, `item10/alias`) (item 10), Related-footer bare-link casing (item 11), the stray-frontmatter-key scar — **outside fenced code**, since a `Software` entry legitimately *shows* `type:`/`tags:` in a listing and deleting a line out of its own example is the one destructive fix in this scan (item 13), source-meta phrasings (item 14), body-opener coherence (LaTeX/parenthetical-tolerant, and an opener with **no bold span at all** on a full entry is flagged — presence as well as form) + the unenumerated-bold scan + emphasis-around-wikilink/math/code (item 16), alias collisions — **compared folded**, so two aliases differing only in case or normalization are the one name they are on the vault's volume — + within-entry duplicates (counted raw AND case/normalization-folded — two spellings of one name inside one `aliases:` list are reported too) + display-label token-match (inflection- and cross-domain-tolerant) + display-label plain-text (item 18), flashcard presence/absence — the heading matched as a whole line, *tolerantly*: a `### Flashcards` or space-variant heading is a PRESENT section with its own fix-the-heading finding, never a missing section (whose remedy would add a second one), a mid-line mention is just prose, and section markers (this heading and the `**Related:**` line) are located on fenced-stripped text so a listing showing one is a sample, not the section — + per-card structure (3 contiguous lines, `??`/`!!` line 2, the `---` separator), line-1 markup restrictions, per-card line-1 answer-leak (every candidate tested in hyphenated AND de-hyphenated spellings; the primary card of a disambiguated title recognized with the discipline parenthetical stripped, so its alias needles are in play), and line-3 plain-text (item 19), and the item-12 *format* layer (unescaped literal `$`, image-embed caption presence + caption plain-text — plus the report-only `item12/remote-image` observation, which is **not** a violation, and — with `--images` — the report-only `item12/missing-image` embed-existence check `CONVENTIONS.md` §1 assigns to this skill). The **judgment layer** stays the model's: whether a flashcard definition is genuinely *unambiguous* in both review directions (and unique against other entries' definitions), whether an entry's `tags:` name the right disciplinary *home(s)* (the "uses" trap and the math/statistics/ML calibration — surfaced, since re-homing an entity without the source is a judgment call, even though tag *format* is mechanized), which fix a flagged unenumerated bold needs (italic vs wikilink), whether two surface forms are the *same entity*, whether a collision candidate is a real *duplicate*, the *closeness* of each backfill candidate, and the *shape* of the hierarchy. Items with **no mechanical layer** — type-assignment judgment (item 6), item 12's equation clauses (coverage read-detected from the note's own prose, display form, notation — in scope, no source needed), stacked-body *semantics* (item 13 — the stray-key scar is flagged, the duplicated-opening judgment is not), and alias *same-entity* semantics (item 17) — are checked by the model reading the entries. The figure/table *coverage* audit (item 12) and example values (item 15) have no mechanical layer either, but both **need the source**, so they are out of scope — surfaced, never performed (see *Out of scope* in `references/qc-items.md`). The scanner output is the model's starting worklist, not the whole job.

## Before you call a finding a false positive

Several checks are deliberately loose or deliberately noisy, and the reasons are recorded as comments in `scripts/scan_vault.py` next to the code. Read the comment before "tightening" anything or overriding a flag wholesale — two of them exist because an earlier stricter version produced false positives at scale, and each re-breaks something wiki-builder mandates if re-tightened: the **item-18 display-label subset/superset test** (an exact-match version false-flagged the cross-domain bare-term links wiki-builder mandates — 108 of 110 findings on a real run — and the tempting "fix", adding the bare term as an alias, is the silent collision wiki-builder exists to prevent) and the **item-16b bullet term-anchor pattern** (a stricter version flagged wiki-builder's own canonical definition bullet, `- **True positives** (TP) — …`, which it then re-emitted every run). A third is the report-only `item12/remote-image` key, which was an ordinary `item12` violation until it turned out to prescribe destroying an embed wiki-builder mandates — don't re-file it as a fixable finding. A check that fires often on **real** issues is the check working; only a genuine, recurring **false** positive is grounds for a proposal to narrow it (SKILL.md, *Closing the loop*).

**These two checks are why this file has a mechanical trigger.** `item16` and `item18` are the only findings whose looseness is deliberate and documented, so they are the only ones with a recorded reason to be second-guessed — and both are greppable in the scan JSON. The third loose case, `item12/remote-image`, needs no lookup: it is fully specified in the Step 0 finding taxonomy and in item 12 of `references/qc-items.md`, and it is report-only either way.
