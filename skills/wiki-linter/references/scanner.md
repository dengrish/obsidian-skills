# The scanner — CLI, output contract, and what it does not check

Read this when a scan exits non-zero, a JSON field/finding is unfamiliar, or an `item16`/`item18` result needs interpretation. Those checks have intentional allowances described under [Before you call a finding a false positive](#before-you-call-a-finding-a-false-positive). Run the helper at [Step 0](../SKILL.md#step-0--inventory-the-vault); use [QC actions](qc-items.md#finding-actions) to decide what may be changed.

Contents: [CLI](#cli) · [Output contract](#output-contract) · [Item keys](#item-keys-in-problems) · [Coverage limits](#floor-not-ceiling).

The scanner is `scripts/scan_vault.py`, a read-only stdlib Python helper. Its JSON describes detections, not permission to edit the vault.

## CLI

```
python3 scripts/scan_vault.py WIKI [--images DIR] [--out FILE] [--indent N]
```

- `WIKI` — the vault's **`Wiki/` folder**, not the vault root. MOCs (`*-moc.md`) and the three suggestion logs (`*-suggestions.md`) live in the root, which is why they are never linted and never listed inside a MOC: the scanner never walks them.
- `--images DIR` — the vault's flat **`Sources/Images/`** folder. With it, every `![[…png]]` embed in every entry is checked to name a file that is really there, emitted as `item12/missing-image`. **Pass it on every real run.** `CONVENTIONS.md` §1 makes this skill that folder's embed validator and nothing else in the plugin walks `Wiki/`, so without the argument that check silently does not run at all and an entry embedding a figure that is not on disk — the state §1a's rename hazard leaves behind — scans clean. It turns on one check and changes nothing else in the output. Matched on the **basename**, case- and normalization-folded (Obsidian resolves an embed by basename, and the documented vault's volume is insensitive to both), so a path-qualified `![[Sources/Images/X.png]]` and a case variant both resolve. Embeds inside fenced code are skipped: a listing showing embed syntax is not an embed.
- `--out FILE` — write the JSON to `FILE` instead of stdout. Use this on any real vault and read the file in slices (filter by `item`, by slug, by key) rather than pulling the whole object into context.
- `--indent N` — JSON indent, default `2`; `--indent 0` emits one compact line.
- Exit status `2` with a usage error if `WIKI` is not a directory, or if `--images` is given and is not a directory. The second guard is deliberate: a mistyped image folder that read as "empty" would report **every** embed in the vault as naming a missing file, and nothing in the output would distinguish that from a genuinely broken vault. Every other failure is a genuine crash worth reporting as execution friction (SKILL.md, *Closing the loop*).

The scanner **never writes to the vault.** It reads `Wiki/*.md` and prints; every fix, MOC, `parents:` value, and log append is the model's own edit.

## Output contract

One JSON object with these keys.

| key | type | contents |
| --- | --- | --- |
| `run_timestamp` | string | `YYYY-MM-DD HH:MM` at scan time. This is the stamp for the suggestion-log dated blocks — use it, do not re-derive a time. |
| `wiki_path` | string | absolute path actually scanned (confirms an overridden path took effect) |
| `inventory` | object | `entries`, `full`, `stubs` (counts) and `full_slugs`, `stub_slugs` (sorted slug lists). A slug is the filename without `.md`. |
| `discipline_tags` | object | valid enum slug → `{"full": N, "stub": N}`. The keys are the disciplines **in use** — exactly the MOCs Task 3 builds (a discipline needs ≥1 **non-stub** entry, so a key whose `full` is `0` gets no MOC). |
| `off_enum_tags` | object | malformed / off-enum tag slug → the entries carrying it. Every one of these is an item-8 finding too; this key groups them by bad slug so a vault-wide pattern is visible at a glance. |
| `untagged_full` | array | full entries whose `tags:` key is present but empty. **Not a violation** — they are *unplaced*: no MOC, no `parents:`. |
| `problems` | array | `{"slug", "item", "message"}`, sorted. The deterministic violations. See *Item keys* below. |
| `problem_tally` | array | per item: `{"item", "entries", "pct_of_full", "issues"}`, ranked by entries affected. `pct_of_full` is the share of **full** entries touched — the recurrence evidence a wiki-builder proposal cites. |
| `collision_candidates` | array | `{"a", "b", "probe", "detail"}` — two slugs the item-5 probes matched. `probe` ∈ `exact`, `plural`, `hyphenation`, `word-order`, `word-order-singular`, `µ-variant`; `detail` is the two colliding identifiers. `word-order-singular` sorts the tokens *after* singularising each one, which is what catches `weight-tying` against `tying-weights` — a pair a raw token sort misses on `weights` ≠ `weight`. It has to be here because wiki-builder runs the same two-key probe on every candidate (`wiki-builder/SKILL.md`, step 3 probe (e)) and CONVENTIONS §9 makes whole-vault dedup detection this skill's alone: a pair already sitting in the vault is seen by nothing else. Unordered pairs, de-duplicated per probe. **Review only — never merged.** wiki-builder's create-time probe (g), token-superset, is deliberately **not** mirrored in this vault-wide sweep — qualified-vs-base pairs (`feature-machine-learning` beside `machine-learning`) are exactly what the disambiguation rules produce on purpose, so a whole-vault pass would flood on legitimate pairs; its absence from this probe list is by design (`wiki-builder/SKILL.md`, step 3). |
| `rename_candidates` | array | `{"slug", "new_slug", "inbound_links", "target_exists"}` — entries whose filename ≠ `slug(title)`. `inbound_links` is how many wikilinks a rename would have to rewrite; `target_exists: true` means the destination is already taken — either an existing file **(whether or not it parsed as an entry: a file with no frontmatter is absent from `inventory` and still occupies its name, and the approved `mv` would destroy it)**, **or a second candidate in this same list proposing the same `new_slug`** — so this is a likely duplicate/disambiguation and must **not** be renamed into (applying both of a colliding pair in sequence would have the second silently overwrite the first). `new_slug` is never empty: a title that reduces to the empty slug (CJK, all-symbol) is reported as an `item5` problem instead, because renaming to it would produce a file literally called `.md`. **Propose for approval — never auto-applied.** |
| `backfill_candidates` | array | `{"slug", "target", "surface"}` — a bare-text mention of `target`'s title/alias (or its plural) found in `slug`'s prose. Existing links, embeds, bare common-noun destinations (including plural or alias mentions), ambiguous title/alias surfaces, duplicate-basename destinations, and targets already linked in that entry are excluded, and stubs are not scanned. **Three line kinds are masked out** for one reason — the worklist proposes linking the *first* occurrence, so a first occurrence somewhere a link may not be written is both un-actionable and *hides* the linkable occurrence below it: whole-line **italic captions** (item 12 forbids links in captions), **markdown table rows** (item 10 forbids links in table cells), and **fenced code blocks** (a listing is shown, not asserted, and `[[…]]` inside one renders literally). The plural form is the title with its **head token** inflected, so an irregular (`Confusion matrix` → `Confusion matrices`, `Hypothesis` → `Hypotheses`) is matched — inflecting the whole title matched no irregular in `plurals.py`'s table and produced `Confusion matrixes`. **`bare_noun_alias`** (bool) tags a candidate whose matched surface is a single all-lowercase word reached only through an alias (`attribute`, `target`) — these flooded the worklist with identical re-judgments every run; batch them in the report. A worklist, not a decision: each one still has to clear the closeness bar, tagged or not. |
| `hierarchy_diagnostic` | object | `full_entries`, `self_parented` (slugs whose existing `parents:` points at themselves), `parent_cycles` (cycles of length ≥ 2 in `parents:` — `[["ping", "pong"]]` for two entries parenting each other — each listed once and rotated to start at its alphabetically first slug; a self-parent is the 1-cycle and stays in `self_parented`. An entry in a cycle has **no path to a MOC root**, so Task 3 breaks the cycle before placing either end; the correct value is `[]`), and `per_discipline`: `{"discipline", "self_parent", "full", "check_rooting"}`. `check_rooting` is `true` at ≥1 self-parent in one discipline. **`per_discipline` lists only disciplines with ≥1 self-parented full entry — a discipline absent from it has zero, not "unknown"**, so a discipline whose `parents:` are all empty simply does not appear; that is the expected state on a never-linted vault and is not itself a finding. Note this reflects the `parents:` **from the last run**, not the tree you are building. **Its meaning changed with the MOC-root rule** (`references/hierarchy.md`): trees are now rooted at the discipline's MOC note, so no entry self-parents and the correct value of `self_parented` is `[]`. Every slug it lists is therefore **stale `parents:`** — written by a pre-MOC-root run or hand-edited — which this run overwrites; `check_rooting: true` is expected on the first run after the change and clears itself. The threshold moved with the rule — it was `≥3`, the old model's tolerance for ~1 legitimate root per discipline, and is now `≥1`, because after a run any non-empty `self_parented` at all is a defect. |

### Item keys in `problems`

`item1` … `item19` map to the builder's [numbered checklist](../../wiki-builder/SKILL.md#quality-checklist). There is no `item20`; existing `importance:` is preserved and not flagged. The complete repair/report routing is in [QC finding actions](qc-items.md#finding-actions), rather than a second action list here.

| Key | Detected condition |
| --- | --- |
| `item2/read-missing` | No `read:` key. |
| `item2/read-null` | Present but valueless: bare `read:`, null, or `~`. |
| `item2/read-type` | A recognizable boolean answer in another spelling, such as quoted `"false"`, `yes`/`no`, or `0`/`1`. |
| `item2/read-unknown` | No recognizable boolean meaning, including arbitrary strings and lists. |
| `item2/parents-null` | YAML null where the empty parents list belongs. |
| `item2/obsidian-key` | A valid Obsidian-owned appearance/publish key, not a schema violation. |
| `item3/user-action` | `created` is later than `updated`; ordinary `item3` also detects date format/calendar problems. |
| `item4/source-identity` | PDF and Markdown references share a normalized stem; this does not prove they are one source. |
| `item10/dangling` | An actual entry-link target is absent after resolution checks. |
| `item10/case` | A target resolves only after case or Unicode-normalization matching. |
| `item10/alias` | A target resolves to another entry's unambiguous alias; a filename match takes precedence. |
| `item10/ambiguous` | Multiple files own the basename or multiple entries claim the alias. |
| `item10/unparsed` | The target file exists but did not parse as an entry; its own finding is `item0` or `item1`. |
| `item10/dup` | The same target appears more than once in actual body prose, excluding code/listings. |
| `item12/remote-image` | A valid remote Markdown image URL, reported as a possible localization opportunity. |
| `item12/missing-image` | An image embed has no file in the supplied `--images` directory; without that argument the check did not run. |
| `item0` | A file could not be read (encoding, symlink, permissions); it is absent from inventory/worklists and the scan continues. |
| `stub` | A legacy stub carries a forbidden Related footer. |

A case variant, alias, ambiguous owner, or unparsed file is not a genuinely missing target. Body code samples and embeds are not entry links. Resolve findings with the linked action guide; never infer that an `itemN` is automatically fixable.

## Floor, not ceiling

The scanner is a **floor, not a ceiling**. It mechanizes every deterministic check it can: YAML validity (item 1 — no frontmatter at all, an opening `---` that is not the file's first line, a closing fence that is not exactly `---` (a `----` or `--- text` line closes nothing — Obsidian shows no properties, and `find("\n---")` used to certify such an entry clean), and each individually unparseable frontmatter line, reported per line while the rest of the entry still scans), field order + **all nine mandatory keys present** (`title`, `type`, `sources`, `created`, `updated`, `description`, `tags`, `parents`, `read` — the same list, in the same order, as wiki-builder's `lint_entry.MANDATORY_KEYS`; only four were checked here until a `title:`-less entry came back from a whole-vault pass with no findings at all while a single-file lint reported two, and a `title:` key carrying **no value** — bare, null, or a list — is the same silent no-op and is reported under the same item-2 message) + quoting (item 2 — including the `read:` type check and the bare-`parents:` check, emitted as `item2/read-type` and `item2/parents-null` and both ordinary fixes, and the report-only `read:` checks emitted as `item2/read-missing` (no key), `item2/read-null` (YAML null), and `item2/read-unknown` (no recognizable boolean answer), none of which the linter may fix; see item 2 in Task 1), date format/validity + `created ≤ updated` (item 3 — **two independent findings, and neither gates the other**: the format check reports anything that is not `^\d{4}-\d{2}-\d{2}$`, while the ordering check parses any date it can understand — the unpadded `2026-1-1` included — and compares the parsed **dates**. Comparing the raw strings got it wrong both ways (`2026-1-1` sorts after `2026-01-02`, inventing a violation; `2026-12-01` sorts before `2026-2-05`, hiding one), and gating the *ordering* check on the *format* rule only traded the first error for the second. An unpadded date is reported for its spelling **and** still ordered by the day it names. The ordering check is emitted as `item3/user-action`, a report-only finding the linter must not fix; see item 3 in Task 1), sources format (item 4), slug↔filename + bare-slug + the five collision probes (item 5), the API-surface failure-string scan + backtick-identifier cap + fenced-code detection — **both fence spellings, ``` and `~~~`** (item 6), description presence + length + plain-text — on stubs as well as full entries (item 7), tags validity — enum membership, `#`-prefix, not-a-wikilink, abbreviation/synonym detection, **case variants of an enum slug** (`#Machine-Learning`), duplicate tags **counted on the canonical slug, after alias expansion and case folding** (so `#ml` beside `#machine-learning` is the one duplicate it is — counting raw slugs reported none, and item 8's own mandated rewrite then created it), and the stub-must-have-a-tag rule (item 8), blank-line/opener/Person-Event-dates — again on stubs as well as full entries, since a stub is exempt from item 9's *length* clause only (item 9), dangling + duplicate links — read with **fenced blocks (``` and `~~~`; a fence closes only on a run of the same character at least as long as its opener, per CommonMark, so a ``` sample inside a ```` block stays masked), indented code blocks (4 spaces or a tab) and inline code spans of any backtick-run length blanked** (a list item's indented continuation is *not* a listing and stays checked), since a `[[…]]` in a listing links nothing and treating it as a dangler would prescribe an edit for a sample of link syntax, and with the three resolving forms carved out under their own keys (`item10/case`, `item10/unparsed`, `item10/alias`) (item 10), Related-footer bare-link casing (item 11), the stray-frontmatter-key scar — **outside fenced code**, since a `Software` entry legitimately *shows* `type:`/`tags:` in a listing and deleting a line out of its own example is the one destructive fix in this scan (item 13), source-meta phrasings (item 14), body-opener coherence (LaTeX/parenthetical-tolerant, and an opener with **no bold span at all** on a full entry is flagged — presence as well as form) + the unenumerated-bold scan + emphasis-around-wikilink/math/code (item 16), alias collisions — **compared folded**, so two aliases differing only in case or normalization are the one name they are on the vault's volume — + within-entry duplicates (counted raw AND case/normalization-folded — two spellings of one name inside one `aliases:` list are reported too) + display-label token-match (inflection- and cross-domain-tolerant) + display-label plain-text (item 18), flashcard presence/absence — the heading matched as a whole line, *tolerantly*: a `### Flashcards` or space-variant heading is a PRESENT section with its own fix-the-heading finding, never a missing section (whose remedy would add a second one), a mid-line mention is just prose, and section markers (this heading and the `**Related:**` line) are located on fenced-stripped text so a listing showing one is a sample, not the section — + per-card structure (3 contiguous lines, `??`/`!!` line 2, the `---` separator), line-1 markup restrictions, per-card line-1 answer-leak (every candidate tested in hyphenated AND de-hyphenated spellings; the primary card of a disambiguated title recognized with the discipline parenthetical stripped, so its alias needles are in play), and line-3 plain-text (item 19), and the item-12 *format* layer (unescaped literal `$`, image-embed caption presence + caption plain-text — plus the report-only `item12/remote-image` observation, which is **not** a violation, and — with `--images` — the report-only `item12/missing-image` embed-existence check `CONVENTIONS.md` §1 assigns to this skill). The **judgment layer** stays the model's: whether a flashcard definition is genuinely *unambiguous* in both review directions (and unique against other entries' definitions), whether an entry's `tags:` name the right disciplinary *home(s)* (the "uses" trap and the math/statistics/ML calibration — surfaced, since re-homing an entity without the source is a judgment call, even though tag *format* is mechanized), which fix a flagged unenumerated bold needs (italic vs wikilink), whether two surface forms are the *same entity*, whether a collision candidate is a real *duplicate*, the *closeness* of each backfill candidate, and the *shape* of the hierarchy. Items with **no mechanical layer** — type-assignment judgment (item 6), item 12's equation clauses (coverage read-detected from the note's own prose, display form, notation — in scope, no source needed), stacked-body *semantics* (item 13 — the stray-key scar is flagged, the duplicated-opening judgment is not), and alias *same-entity* semantics (item 17) — are checked by the model reading the entries. The figure/table *coverage* audit (item 12) and example values (item 15) have no mechanical layer either, but both **need the source**, so they are out of scope — surfaced, never performed (see *Out of scope* in `references/qc-items.md`). The scanner output is the model's starting worklist, not the whole job.

## Before you call a finding a false positive

Several checks are deliberately loose or deliberately noisy, and the reasons are recorded as comments in `scripts/scan_vault.py` next to the code. Read the comment before "tightening" anything or overriding a flag wholesale — two of them exist because an earlier stricter version produced false positives at scale, and each re-breaks something wiki-builder mandates if re-tightened: the **item-18 display-label subset/superset test** (an exact-match version false-flagged the cross-domain bare-term links wiki-builder mandates — 108 of 110 findings on a real run — and the tempting "fix", adding the bare term as an alias, is the silent collision wiki-builder exists to prevent) and the **item-16b bullet term-anchor pattern** (a stricter version flagged wiki-builder's own canonical definition bullet, `- **True positives** (TP) — …`, which it then re-emitted every run). A third is the report-only `item12/remote-image` key, which was an ordinary `item12` violation until it turned out to prescribe destroying an embed wiki-builder mandates — don't re-file it as a fixable finding. A check that fires often on **real** issues is the check working; only a genuine, recurring **false** positive is grounds for a proposal to narrow it (SKILL.md, *Closing the loop*).

**These two checks are why this file has a mechanical trigger.** `item16` and `item18` are the only findings whose looseness is deliberate and documented, so they are the only ones with a recorded reason to be second-guessed — and both are greppable in the scan JSON. The third loose case, `item12/remote-image`, needs no lookup: it is fully specified in the Step 0 finding taxonomy and in item 12 of `references/qc-items.md`, and it is report-only either way.
