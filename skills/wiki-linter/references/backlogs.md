## Run report


End every run with a single consolidated report:

- **Inventory** — N entries (full / stub), per-discipline-tag non-stub counts, and any untagged full entries.
- **Image-folder observations** — every report-only `image_folder_findings`
  record, grouped by kind (nested item, staging residue, unreadable/unusable
  path, or portable-name collision). These observations never authorize moving,
  renaming, or deleting media.
- **Autonomous agent-review coverage** — `agent-reviewed/readable in-scope full entries`, plus every skipped or unreadable file by name and reason. Scanner execution is counted separately from the agent's semantic pass; neither requires user review or sign-off.
- **Task 1 — tags fixed / unresolved:** tag *format* fixes applied (added `#`/quotes, de-duplicated, abbreviation expanded to an enum slug, wikilink-form converted to a `#`-tag, blank stub given an inherited tag). The executing agent applies clear disciplinary-home corrections from the published calibration; cases lacking enough evidence are left unchanged and reported as unresolved, without blocking the run.
- **Task 1 — QC fixes**, grouped by checklist item: per fixed entry, the item and a one-line description of the fix, including every claim-preserving local prose repair and its kind. Separately, **renames proposed for approval** — each as `old-slug → new-slug`, the inbound-wikilink count that would be rewritten, the reason (stale/variant filename vs. title correction), and a collision flag where the target file already exists — and, if the user approved any during the session, **renames applied** (only the approved ones). Report **semantic-invalid aliases proposed for removal** the same way: entry, alias, evidence that it names another entity, likely canonical owner, inbound alias-target count, and any ownership ambiguity. If approval led to action, list **semantic-invalid aliases removed** separately, with the canonical owner, rewritten-link count and surfaces, and clean re-scan result; never describe a proposal as applied. Duplicate spellings inside one alias list remain ordinary format fixes. Also report **`Software` reclassifications** (item 6, corrected artifact type plus the selective API-scope result) and any **ambiguous code-content/type calls left unchanged and reported with the missing evidence**.
- **Task 1 — duplicate-entry candidates:** item-5 collision-probe matches and synonym/near-duplicate candidates found by the agent are reported as merge proposals. The agent performs the semantic comparison; applying a merge remains approval-gated.
- **Task 2 — Links:** backfill candidates **applied** (entry → target) vs **rejected** (entry → target, why — failed identity or the closeness bar), with `bare_noun_alias: true` rejections grouped by surface/target and count so repeated low-value alias matches do not dominate the report (itemize any applied exception). Group or itemize `organism_common_name: true` decisions separately, including every applied link, and state that no global alias was added. Also report links **pruned** (entry → target, reason) — *itemize every prune*; **duplicates collapsed**; **danglers resolved** (all dropped to bare text; stubs are never created); and **ambiguous bare terms left as text** (flagged).
- **Task 3 — Hierarchy:** report the initial and residual `placement_gaps`, `unresolved_parents`, `parent_state_findings`, and `moc_consistency_findings` counts and entries (`placed_unparented` remains the compatibility projection of placement gaps). Include missing/represented disciplines, invalid stub/untagged parent state, MOC tree/label/coverage defects, and exact parent-union mismatches. Report MOCs created/updated or structurally reorganized, unlinked category placeholders, `parents:` changes, legacy self-links cleared, and unplaced entries. Separately list connected closures skipped for scope, legacy-unmarked/malformed/unreadable MOCs and what they blocked, and any interrupted closure that failed its postconditions. None may be described as partially updated or clean.
- **Missing-entry candidates** — dangling-link targets that were dropped but look like real gaps (a concept several entries lean on, a heavily-referenced name), surfaced here and in `wiki-notes-suggestions.md` so the user can run a supporting source through wiki-builder to create them properly. If that source already appears in any entry, say that the builder request must carry explicit **resume/re-run intent**; a plain process request will correctly hit its prior-coverage skip gate. **Stubs are never created** — not for danglers, not for disciplines or category slots (tags aren't wikilinks, each tree is rooted at its MOC note rather than an entry, and category slots use unlinked terms).
- **Entries untouched** — count (the churn-avoidance signal: most of a steady-state vault).
- **Notes for the user** — optional, nonblocking follow-ups only: authorization-gated retitles, alias removals, splits, merges, and other vault-wide refactors; unresolved disciplinary evidence; Related footers past the soft cap; `item3/report-only` date ordering; remote images; Obsidian-owned keys; missing, null, or unknown `read:` state; unreadable files; missing embedded-image files; and dates or equations inserted into `read: true` entries. These are traceability and user-owned-state notices, not a required review queue; the lint run completes without a response.
- **Proposing improvements (wiki-builder and wiki-linter)** — the report's closing section: two short, ranked sets of concrete, evidence-grounded proposals — one for the **wiki-builder** skill (from recurring vault-content patterns), one for the **wiki-linter** skill itself (from recurring execution friction) — or an explicit "nothing systematic this run" for either side. Every item is listed, but the two cases are distinguished: items **newly appended** to the vault-root log with the run timestamp (`wiki-builder-suggestions.md` / `wiki-linter-suggestions.md`) vs. items **already open there**, whose recurrence count was bumped in place and which were *not* re-appended — with the count. The report notes what was written and where. Specified in full in the next section.
- **Proposing note improvements** — content/clarity/organization suggestions for the *notes themselves* (thin or unclear entries, missing or duplicate concepts, sprawl, uneven coverage, inconsistent formatting) that need source evidence, a user-owned state decision, or an out-of-scope operation — distinct from the two skill logs (which are about the tooling) and from auto-fixes (already applied this run). Recorded in `wiki-notes-suggestions.md` under the same new-vs-recurring rule. The content-level items under *Notes for the user* above are the same ones recorded here. See *Proposing note improvements*.

## Proposal scope


Every run ends by proposing improvements in three directions, none of which it applies: to the **wiki-builder** skill, to **wiki-linter itself**, and to the **notes' content**. Each goes in its own log in the vault root — `wiki-builder-suggestions.md`, `wiki-linter-suggestions.md`, `wiki-notes-suggestions.md` — which is the vault-artifact form of *proposing*; wiki-linter modifies **neither skill file**. Nothing is invented to fill a section: the *report* always carries all three sides, but a log gets a dated block only when there is something real and **new** for it.

**Why the loop exists.** wiki-linter sees the **whole vault at once**, and it is the only component positioned to notice that a problem is *systematic*: it sees in aggregate what wiki-builder produced *and* feels where its own checks strain across every entry. Each direction draws on different evidence — a **wiki-builder** proposal comes from a pattern in the vault's *content* (what entries look like); a **wiki-linter** proposal comes from friction in the linter's *own execution* (a check that fired on something genuinely fine, a real issue the scanner has no check for and the executing agent resolved semantically, a decision the linter's own rules left ambiguous, a tool limit the run hit); a **notes** proposal is about the *content as a body of knowledge*, things that need source evidence, a user-owned state decision, or an out-of-scope operation. All three are **always part of the report** — the loop is only useful if it is reliable — and all three are strictly evidence-bound (*No fabrication*).

### Proposing improvements — to wiki-builder and to itself

Every candidate, in either skill direction, passes the same three tests.

**1. Recurrence — a pattern, not an instance.** Propose from patterns, never one-offs. For **wiki-builder**: the same issue across many entries — a checklist item firing on a meaningful share of the vault (use the scanner's `problem_tally` key — per item, `entries`, `pct_of_full` and `issues`), the same judgment-flag recurring, or the same auto-fix applied dozens of times — signals wiki-builder's *behavior*, not one stray source or hand-edit. Recurrence counts whether or not wiki-linter fixed it: a format slip silently auto-fixed on 40 entries is exactly what wiki-builder should stop emitting — the fix *is* the signal. For **wiki-linter**: the *friction* recurs — the same false flag overridden across many entries, the same unchecked issue fixed by hand again and again, the same ambiguity resolved by guess each time, the same tool failure. A single false positive or a one-time hiccup is noise; a repeated one is a self-improvement candidate.

**2. Attributability — whose change fixes it?** The filter that makes the proposals worth reading. Each recurring pattern routes to a **wiki-builder** change, a **wiki-linter** change, or **neither** — and one observation can hit both skill destinations at once (e.g. "descriptions keep mismatching the title": wiki-builder should stop producing the mismatch *and* the linter, which has no mechanical check for it, could add one).

- **→ wiki-builder** when the pattern is in something it controls writing one entry from one source: descriptions consistently over the length cap, LaTeX consistently on flashcard line 3, a frontmatter field consistently mis-ordered, ML methods consistently over-tagged `#mathematics`/`#statistics` instead of `#machine-learning` (the "uses" trap), an alias/title convention consistently slipped. It is **not** wiki-builder's when it is an **incremental-generation gap** — missing links between entries, MOCs, `parents:`, cross-vault dedup — which are architectural and **wiki-linter's job by design** (wiki-builder cannot see entries that do not exist yet; **never** propose making it add the cross-links / build the MOCs / dedupe the vault / populate `parents:`), nor when it is a **hand-edit** or **legitimate source variation**. When wiki-builder *already* specifies the violated rule, propose about **enforcement** — a worked counter-example, promotion to a hard QC-checklist item, or the specific missed edge (e.g. line-3 LaTeX leaking from the body's defining equation) — not the rule's existence.
- **→ wiki-linter (self)** when the friction is in the linter's own behavior: a recurring **false positive** (a mechanical check flagged something the executing agent verified is fine → propose tightening the condition, with the pattern as evidence); a **coverage gap** (a class of real issue the executing agent keeps resolving semantically *that is mechanizable* → propose a scanner check; if it is irreducibly a judgment call it stays with the executing agent, and a brittle mechanical check for it is not an improvement); **ambiguous self-guidance** (a decision point the linter's own prose did not determine, so the executing agent had to guess and might guess differently next run → propose clarifying that rule); **operational/tooling friction** (a tool limit, performance wall, or environment hazard the run actually hit → propose a concrete mitigation); or **awkward/indirect handling** (a case detected only indirectly, in a way that misleads, recurring → propose a more direct check or clearer message).
- **→ neither** when a check correctly caught real problems (working as intended), when a one-off was handled fine, or when the executing agent simply wishes it could do something outside the current mode (editing wiki-builder, extracting unrelated new entities, or applying a split/merge during routine lint). If that repeatedly surfaces, report the exact boundary and recurring case rather than proposing a naive feature add. Explicit source-backed refactor mode is a separate authorized workflow, not a reason to widen routine lint.

**3. Actionability — specific, located, with the fix.** Each proposal names the **pattern + evidence** (count/share or representative slugs for wiki-builder; the recurring friction for wiki-linter), the **attribution** (one phrase on why this skill is the right place to change it), the **location** (wiki-builder: the field/section/checklist item; wiki-linter: the scanner check, the prose section, or an operational note — the linter can point at its own structure, using the relevant entrypoint, reference, or script), and the **proposed change** (concrete: the rule to add/tighten/exemplify, the check to add/refine, the mitigation to adopt). "Improve flashcards" / "make the linter smarter" are useless; "tighten wiki-builder's line-3 rule in `references/flashcards-and-emphasis.md` §4 with a worked example, because 18% of entries carried `$…$` there" and "narrow the linter's line-1 italic check — `$a*b$` LaTeX multiplication is flagged as italic on N entries" are actionable.

### Anti-drift — self-proposals serve the skill's purpose, not its convenience

A skill proposing changes to *itself* carries a specific risk: drifting toward what makes its own job easier rather than what keeps it correct. Guard against it. wiki-linter's purpose is **faithful enforcement of wiki-builder's schema** under the floor-not-ceiling model, with churn-avoidance — self-proposals must *sharpen* that, never relax it. A proposal to flag *less*, enforce *less* faithfully, or drop a check is legitimate **only** with a genuine false-positive justification; "this check is annoying / fires a lot" is not one. Never propose changes that would weaken the schema's authority, expand the skill past its deliberate boundaries, or alter its character. The bar for a self-change is *higher*, not lower, than for a wiki-builder change.

### Hard boundary — propose, never apply (to either skill)

wiki-linter **modifies neither skill file** — not wiki-builder's, and not its own. Both skills are authored and maintained by the user; a skill that rewrites itself mid-run is out of bounds (and a self-edit hazard besides). What wiki-linter *does* write is **vault artifacts**: entries, MOCs, and the three **suggestion logs** in the vault root. Writing a proposal into `wiki-builder-suggestions.md`, `wiki-linter-suggestions.md`, or `wiki-notes-suggestions.md` is the vault-artifact form of *proposing* — the same kind of act as writing a MOC — **not** applying: the logs are advisory text the user reads and acts on. Write them only within an apply-capable maintenance request; a report-only run leaves them untouched. Never edit files belonging to either skill during a vault run.

### No fabrication — the "always" has integrity

Always include the section in the run report, but never invent a proposal to fill a side. If the run surfaces no recurring wiki-builder-attributable defect, say *"No systematic wiki-builder gaps surfaced this run."* If it surfaces no genuine execution friction, say *"No wiki-linter limitations surfaced this run."* A fabricated suggestion is worse than none — for wiki-builder it sends the user to change a generator that was not the problem; for wiki-linter it risks churning a working skill toward convenience. Report what is real. **The "always" applies to the report, not to the logs:** when a side has nothing new this run, write nothing to that file.

### Format

Each side is a short ranked list, most-systematic-first and **capped at the few highest-value items** (a focused handful beats an exhaustive dump). Each item carries a **stable ID** and four lines:

```markdown
### [flashcard-line3-latex] LaTeX on flashcard line 3
- **Pattern:** `$…$` on line 3 of 18% of full entries (item19, 22 entries)
- **Why wiki-builder:** the rule exists but has no worked counter-example
- **Change:** add one to wiki-builder's `references/flashcards-and-emphasis.md` §4, showing the body's defining equation leaking into line 3
- **Seen:** ×1 · first 2026-08-08 09:41 · latest 2026-08-08 09:41
```

The **ID** is a short kebab-case slug of the defect and its location (`flashcard-line3-latex`, `desc-over-110`, `moc-reorg-churn`). It is what makes a proposal identifiable across runs, so it must be **stable**: before minting one, read the IDs already open in that log and **reuse the existing ID** when this run's proposal is the same defect. The log's own IDs are the vocabulary; a near-miss synonym re-raises an item that is already there. Recurring *split candidates* roll up under wiki-builder ("its scoping rule lets entries sprawl across N subjects — tighten one-entity-per-entry"), not as per-entry notes.

### Persisting to the vault logs

The proposals are durable, not just printed. Each run records them in **three files in the vault root** — `wiki-builder-suggestions.md`, `wiki-linter-suggestions.md`, `wiki-notes-suggestions.md` — so they accumulate into a backlog the user works through between runs. **A log is a set of open items, not a transcript of runs**, and its length is bounded by the number of distinct unresolved proposals — never by the number of times the linter has run.

- **Read and snapshot the log first, always.** Before writing anything, read the file and collect the IDs of the items already in it. Keep the exact bytes and identity as the expected snapshot under the shared [safe-write protocol](../../../shared/SAFE_WRITES.md). This tells new from recurring and prevents a concurrent run from being overwritten. Build the complete resulting log in scratch, conditionally publish it only while that snapshot remains current, then confirm the prior content is still present. Never call a whole-file write with only the new content, and do not use an unguarded shell append: either can lose or duplicate another run's update.
- **New proposal → append a dated block in the staged result.** For each side with at least one proposal whose ID is **not** already open in that log, add a section at the **end** of the snapshotted content, headed with the run timestamp (the scanner's `run_timestamp` key — use it, don't re-derive a time): `## YYYY-MM-DD HH:MM — <short run context>`, e.g. the vault size, followed by that side's genuinely-new items in the format above. Never reorder or delete what was already there. If conditional publication finds a later version, re-read its IDs and rebuild instead of forcing the stale append.
- **Recurring proposal → update it in place; do not re-append it.** If an item with the same ID is already in the log and still unresolved, the proposal has **not** changed and the paragraph is **not** written again. Edit that item's existing `**Seen:**` line only — bump the count and set `latest` to this run's timestamp — and leave every other byte of the file alone. This is a one-line targeted edit, not a rewrite, and it is the only in-place edit the linter ever makes to a log. The repetition across runs is still recorded, and still exactly the evidence that the item remains open; it is now recorded as a **count**, which does not grow the file. **This is the churn-avoidance contract applied to the logs**: the same reason an unchanged entry is left byte-for-byte untouched is the reason an unchanged proposal is not re-appended.
  - *If the underlying pattern genuinely changed* — different evidence, different proposed fix, a different location — that is a **different** proposal: give it its own new ID and append it as new. Re-stating the same item with a bigger number is not a new proposal: leave its evidence line unchanged, update only `Seen:`, and put this run's new count in the report.
- **Nothing new → no block.** A run whose entire output for a side is recurrences appends **no dated block** to that file; only the `Seen:` counters move. A run with nothing at all for a side leaves the file untouched (per *No fabrication*). No empty dated sections, ever.
- **Create with a one-line header if missing.** If the file does not exist (first run, or the user just reset it), publish it exclusively with a short title and a note — e.g. `# wiki-builder — suggested changes (appended by wiki-linter runs; implement, then clear to reset; newest at the bottom)` — then the first dated block. A path that appears after the missing check is another run's log and must survive unchanged; re-read and merge the proposal instead.
- **The user resets; the linter never does.** The linter appends new items and bumps counters. It does **not** truncate, clear, prune, reorder, or de-duplicate these files, and it never removes an item — resolving one and clearing it is the user's action. (Bumping a counter is not removal, and it is strictly less destructive than the re-append it replaces.)
- **Report and log stay consistent.** The report's lists and the logs carry the same content, and the report distinguishes the two cases: which items were **newly appended** (with the timestamp and file names, so the user knows where the backlog lives) and which were **already open and had their recurrence count bumped** (with the count). A recurring item still appears in the report — the user sees everything real this run — it just does not get written to the log a second time.

### Proposing note improvements

The two logs above are about the **tooling** — how the generator and the linter behave. This third channel is about worthwhile improvements to the *notes themselves* that remain after Task 1's narrow local repairs because they need source evidence, a user-owned state decision, or an operation the skill keeps out of scope. They go in `wiki-notes-suggestions.md`, under the **same mechanics** as the skill logs (*Persisting to the vault logs*) — including stable IDs and update-in-place on recurrence, which matter most here: a thin entry stays thin until the user expands it, so it would otherwise be re-logged forever.

**What belongs here — broadly, anything that makes the notes better as a body of knowledge:**

- **Depth & gaps** — a full entry thin relative to its importance, worth expanding; a concept many entries lean on but none defines (a missing node — often a recurring dangling target or a heavily-referenced stub); an entry missing a salient aspect the rest of the vault assumes.
- **Clarity & coherence** — a definition that is circular, vague, or conflates senses; a title or qualifier, description, opener, equation, flashcard, or closely linked neighbor whose claims conflict or drift in scope; or a flow problem that cannot be repaired through Task 1's claim-preserving local operations. Name the exact surfaces or paragraph boundary and proposed action; any factual choice requires a source-backed decision. Length, a missing transition word, or lexical overlap alone is not evidence.
- **Scope & catalogs** — under item 9, source/tutorial scaffolding, extended worked narratives, or application catalogs that do not serve this entity; under item 6, `Software` prose that drifts from artifact-wide design into API inventories, defaults, version logs, or recipes; under item 15, an unnecessary or tangential example. Judge purpose, never length or item count. Substantive trimming is proposed for a separate source-backed editing request.
- **Organization** — two entries that are the **same concept under different names** (the synonym-duplicate the slug probes can't catch) and should be merged; an entry that independently defines several durable subjects and should be split into linked atomic notes; a cluster of entries a missing intermediate concept would organize better; lopsided coverage (a discipline that is mostly stubs). A split proposal names the existing slug, proposed note boundaries or titles, the source support that must be checked, and the intended wikilinks. A long note, several headings, or several sources alone is not a split candidate; inherent facets stay together.
- **Formatting & consistency beyond the QC floor** — patterns that are not rule *violations* but read as uneven: similar entries differing in whether they use sub-headings, inconsistent figure use, Related footers that are inconsistently full.

**The gate — each item is:** (1) a **genuine** improvement worth the user's time, not a nitpick; (2) **specific and located** — which entry or entries, and what to do; (3) **not already handled** — never log what the linter auto-fixed this run (that is in the report), and never log something whose right fix is a *skill* change (a content **pattern the generator keeps producing** is a wiki-builder proposal; this log is for improving the **specific notes as they stand**); (4) **real** — if nothing this run is worth noting, write nothing; never invent filler.

**Faithful to the no-source stance.** With no source in hand, wiki-linter cannot verify facts, so these are observations and suggestions, not authoritative corrections. Routine Task 1 applies only the source-independent repairs enumerated by each QC item. Factual reconciliation and substantive trimming require a separate source-backed request; splits, merges, and cross-entry redistribution additionally require explicit authorization naming the operation or the affected entries and intended outcome. A generic request to lint, audit, clean up, or fix notes does not supply it. Pure renames and semantic-invalid-alias removals follow their approval and complete-reference-rewrite rules. The report's *Notes for the user* and this log carry the same content; the report says what was appended, what was counted, and where.
