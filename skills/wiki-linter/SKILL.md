# Wiki Linter

**Runtime setup:** Read [shared/RUNTIME.md](../../shared/RUNTIME.md) once per
task for vault selection, script paths, Python dependencies, and host tools.

A **no-source, whole-vault maintenance pass** over a wiki produced by `wiki-builder`. The two skills are separated by **reach**: wiki-builder's edits stop at the entries it is writing from the source in front of it, and wiki-linter is the only pass that reaches across entries and back over the vault it has already built.

**wiki-builder links only inside the entries it writes, and only at targets that exist.** Processing a source, it wikilinks within the entry bodies it creates or merges and builds each one's `**Related:**` footer; it creates **no stubs** — an entity too thin for a full entry gets no note and no link, its mention staying plain text (neither skill creates stubs any more). Its reach stops there: it **does not touch entries it did not write this run**. It has no back-fill audit (an entry mentioning another entry as bare text is not wiki-builder's to wrap), and its orphan-link audit covers only the entries this run created or merged — a dangling link inside one of its own new entries is repaired there and then (the missed full entry created, or the link dropped to bare text), and the rest of the vault is left alone. Refactoring stays out of its scope too: it never renames a slug and rewrites the inbound links, never splits a sprawled entry, never merges two entries, and never populates `parents:`.

**wiki-linter owns every link that crosses entries, reaches backwards, or spans the vault.** Nothing about its run is scoped to one document, and nothing else links vault-wide — so the whole retroactive and cross-entry surface is its alone:

- **Backfill across the whole vault.** Wrapping a bare-text mention of an existing entry in another entry's prose is wiki-linter's, everywhere, including in entries a wiki-builder run passed over.
- **Pruning — both kinds.** Dropping a *resolving* link that is too weak to keep, and de-duplicating a target linked twice in one body, both need the no-source vantage.
- **Repairing orphans inherited from earlier runs.** A dangling link in an entry wiki-builder wrote *before* this arrangement, or in an entry its narrowed audit never reached, is wiki-linter's to resolve — dropped to bare text, with the missing entry surfaced as a note proposal when it looks like a real gap (**stubs are never created**). Do not assume the vault has already been swept — see *Dangling links* in `references/link-hygiene.md`.
- **`parents:`, MOCs, whole-vault dedup detection, and cross-entry QC** — the things wiki-builder structurally cannot do, because it sees one source at a time and cannot know about entries that do not exist yet.

**Why the split moved here.** The two skills used to link vault-wide under separately-stated bars, and the bars drifted: a marginal link got added by one and pruned by the other on alternating runs, churning `updated:` forever. Confining wiki-builder to the entries it writes removes **almost all** of that overlap rather than trying to hold two bars identical — one case stays in both scopes (a merged entry is wiki-builder's while it is being merged and this skill's ever after), and CONVENTIONS §9's on-merge narrowing rule is what closes the churn loop there.

It does three things:

1. **Retro-QC** — re-check every entry against the source-independent subset of wiki-builder's Quality Checklist and fix violations in place.
2. **Link hygiene** — backfill wikilinks that couldn't exist when an earlier entry was written (entries are created sequentially, so an early entry can mention a later-created entity only as bare text), and prune duplicate or weakly-related links.
3. **Hierarchy** — derive one per-discipline concept hierarchy and use it to (a) populate every entry's `parents:` and (b) build/maintain one MOC file per discipline tag. (wiki-builder recently replaced `roots:` — a single wikilink to a self-rooted discipline *note* — with `tags:`: one or more `#`-prefixed discipline slugs from a fixed 27-discipline enum, which are **not** wikilinks and reference no note. So "discipline" now means *a tag value*, not an entry in the vault. The tree is rooted at the discipline's **MOC note** instead — the one per-discipline note that always exists, because this skill writes it — see Task 3.)

**Every run also ends by proposing improvements it does not apply** — to the **wiki-builder** skill (so the generator stops emitting a defect at the source), to the **wiki-linter** skill itself (so the linter stops mis-flagging, or starts catching, something next run), and to the **notes' own content** (thin entries, duplicate concepts, sprawl — things that need a source or a human call). All three are shown in the run report and recorded in three logs in the vault root — a genuinely new proposal appended with the run timestamp, one already open counted in place rather than restated. The linter *proposes*; it edits neither skill file. See *Closing the loop* below.

**The wiki-builder schema is the source of truth; wiki-linter does not redefine it.** wiki-builder's SKILL.md carries the *Quality Checklist* and a one-line-per-field cheat-sheet; the full rules live in its `references/` files, and that is where to go for the real text: **field definitions and *Quoting policy*** → `wiki-builder/references/writing.md` (§1); **the wikilink form and *Cross-domain term disambiguation*** → `wiki-builder/references/writing.md` (§3); **the slug algorithm** → the plugin's `shared/scripts/slugify.py`, the single implementation both skills import — no prose copy of the pipeline survives anywhere; **the Related-footer format** → `wiki-builder/references/writing.md` (*The Related footer*, §2); **the equation policy — coverage (a calculation the source states in words is typeset), the display-block form, the vault notation standard, normalization** → `wiki-builder/references/equations.md`; **the Flashcards format and the bold/italic rules** → `wiki-builder/references/flashcards-and-emphasis.md` (§4 *Flashcards*, §5 *Bold and italic*) — that file is the second half of `writing.md`, which stops at §3 and carries neither rule; **the legacy stub format** → wiki-builder's SKILL.md (*Stubs (legacy)*) — recognition and promotion only; **neither skill creates stubs any more**, and the structural rules below apply to stubs already in the vault. This file restates the *assertions* it enforces compactly and points at wiki-builder by file + section name / checklist-item number for the full rule. If a rule here ever drifts from wiki-builder's, **wiki-builder wins** — so when adjudicating a drift, open the reference file named above rather than settling it from the cheat-sheet or from memory. **The one carve-out is linking.** Because wiki-builder now links only inside the entries it writes, *when* a mention across entries earns a wikilink, which links get pruned, and how a dangling target is resolved are **wiki-linter's to decide** — if wiki-builder's files still say something about vault-wide or retroactive linking, it is stale and this skill governs. The precedence rule is unchanged for everything else: the schema and field definitions, naming and slugs, body and prose conventions (including the sentence-length and example-discipline rules), the Related-footer and Flashcards formats, and the legacy stub format all remain wiki-builder's.

## Vault layout

Unless told otherwise (same vault layout as wiki-builder):

- **Vault root:** `<vault>` selected using `shared/RUNTIME.md`
- **Wiki folder:** `<vault>/Wiki`
- **Sources/Images folder:** `<vault>/Sources/Images`
- **MOC files:** written to the **vault root** (not `Wiki/`), one per discipline tag in use, named `<discipline-slug>-moc.md` where the slug is the tag value with the `#` stripped (e.g. the `#machine-learning` tag → `machine-learning-moc.md`). Because MOCs live in the vault root and the linter only ever walks `Wiki/`, a MOC is never linted as an entry and never listed inside another MOC — both exclusions are automatic.
- **Suggestion logs:** three files in the **vault root** — `wiki-builder-suggestions.md` and `wiki-linter-suggestions.md` (improvements to the two *skills* — see *Proposing improvements*) and `wiki-notes-suggestions.md` (improvements to the *notes themselves* — content, clarity, organization — see *Proposing note improvements*) — where each run records its proposals. Each is a **set of open items, not a run transcript**: a new proposal is appended, a proposal already open is counted in place, and nothing is ever removed except by the user. All vault-root, so the linter (which only walks `Wiki/`) never lints them; all named `*-suggestions.md`, distinct from `*-moc.md`, so the MOC step never touches them.

The user may override any path per-request; the override applies to that run only. Resolve the vault using `shared/RUNTIME.md` rather than editing these files.

## Relationship to wiki-builder — two deliberate overrides

wiki-linter intentionally suspends two wiki-builder rules. These are **not** contradictions; they are the reason the skill exists.

1. **Removing a link that resolves is allowed.** wiki-builder's Related footer is *additive-only* ("never remove an existing wikilink — each represents a connection a previous source saw"), because wiki-builder can't second-guess a judgment a source made; the only link it drops is a **dangling** one inside an entry it just wrote. wiki-linter is the deliberate maintenance pass with no source to defer to, so **anywhere in the vault** it may also drop a body wikilink whose target exists but whose relationship fails the closeness bar, prune the matching Related-footer entry, and de-duplicate repeated links. This override applies only to body-prose and Related-footer wikilinks; `tags:`, `sources:`, and `parents:` are never pruned by the link-hygiene mechanism.
2. **`parents:` is owned here.** wiki-builder writes `parents: []` on a **new** entry and says a separate skill fills it later; on a **merge** into an existing entry it leaves a populated `parents:` **untouched**, so a value wiki-linter wrote survives any number of subsequent wiki-builder runs. wiki-linter is that separate skill: it is the only writer of `parents:`, and it recomputes the field from the current tree each run (see Task 3) rather than defending it against erasure. **An empty `parents:` is written `[]`, never as a bare `parents:`** — the vault pins the property as `multitext`, and a bare key is YAML null, which Obsidian renders as an empty *text* field rather than an empty list, so the declared type and the value on disk disagree. Because this is the field wiki-linter owns, emitting `[]` for an entry with no parents is its job, and normalizing a bare `parents:` it finds is an ordinary fix in place (`item2/parents-null`). No other field changes ownership.

Everything else follows wiki-builder exactly.

## Scope and order of a run

**Default: the whole `Wiki/` folder, all three tasks, in this fixed order:**

1. **Inventory + QC** (Task 1) — parse and validate every entry first, so links and hierarchy are computed against clean, well-formed data.
2. **Link hygiene** (Task 2) — backfill and prune. Runs after QC because alias and tag fixes from Task 1 change what link targets resolve to (renames are *gated* — not applied here; an approved rename does its own full vault-wide link rewrite).
3. **Hierarchy → `parents:` + MOCs** (Task 3) — last, because it consumes the finalized entry set and the corrected `tags:` values from Tasks 1–2.

The user can narrow scope ("just rebuild the MOCs," "only backfill links," "lint only the AI entries"); run only the requested task(s) but still run Step 0 first.

### Churn-avoidance contract

A steady-state vault is mostly already-correct. **Only write an entry that actually changes.** An entry with no QC violation, no link to add or remove, and no `parents:` change is left **byte-for-byte untouched** — not re-serialized, not re-ordered, not rewritten. The run report (not the filesystem) is the record of what was touched. Per the *Dates* policy below, the linter modifies none of `created:`, `updated:` or `read:` on any entry.

### Dates

`created:` and `updated:` are **source-provenance** fields owned by wiki-builder (`updated:` = date of the most recent *source merge*). A lint pass is not a merge, so **wiki-linter never writes `created:` or `updated:`** — not on a QC fix, not on a link change, not on a `parents:` change; an *existing* entry's dates are never touched, and the linter creates no entries of any kind (stub creation is retired), so there is no new-entry exception. The run report is the audit trail.

**`read:` is the same argument over a different field.** It is the user's review checkbox — the one value in the schema that is theirs to set — and a lint pass is not a revision any more than it is a merge, so **wiki-linter never writes `read:`** either: not on a QC fix, not on a link change, not on a `parents:` change. It creates no entries (stub creation is retired), so there is no new-entry carve-out. On an entry that already exists the field is never touched — and that includes both ways it can carry no answer: a **missing** `read:` key, and a `read:` present with a **null** value (bare `read:`, `read: null`, `read: ~`). Both are reported rather than filled, because writing `read: false` into a note the user had already marked read destroys exactly the state the field exists to hold, and a null gives the linter nothing to preserve — it would be inventing the answer, not correcting its spelling. Both findings route to *Notes for the user* like `item3/user-action` (item 2 in `references/qc-items.md`). An unrecognizable value (`item2/read-unknown`), such as `read: banana` or a list, is report-only too: no boolean meaning can be preserved. A `read:` that is present, carries an answer, and is merely **wrongly typed** is the other case entirely and *is* fixed here: only its spelling is wrong.

## Step 0 — Inventory the vault

Before any task, build the initial model of the vault with **one scan**. Give the script its full path (`<skill>` is the directory this SKILL.md sits in — your working directory is normally the vault, where a bare `scripts/…` resolves to nothing):

```bash
python3 '<skill>/scripts/scan_vault.py' '<vault>/Wiki' --images '<vault>/Sources/Images' --out '/tmp/wiki-scan-<run-id>.json'
```

**Pass `--images` on every real run.** `CONVENTIONS.md` §1 makes this skill the validator of the embeds pointing at `Sources/Images/`, and it is the only thing that checks them: nothing else walks `Wiki/`, and `paper-summarizer`'s `note_lint.py --images` only ever sees an `Articles/` note. Without the argument that one check silently does not run, and an entry embedding a figure that is not on disk — the state §1a's rename hazard leaves behind — comes back clean. It adds `item12/missing-image` findings and changes nothing else. A path that is not a directory is a **usage error, not an empty folder**: the script exits 2 rather than reporting every embed in the vault as broken.

**Pick a `<run-id>` unique to this run** (the vault name plus a timestamp, say `claude-main-0912`) and use that same literal filename in every later slice and grep of this run. A fixed `/tmp/wiki-scan.json` is silently clobbered the moment a second session runs a scan — over a different Wiki folder, or mid-way through your own pass — and every verdict you then read from it is computed against a vault state that is not yours, which is indistinguishable from a correct answer.

Pass the **`Wiki/` folder**, not the vault root — MOCs and the suggestion logs live in the root, and the scanner never walking them is what keeps them out of the lint. Stdlib-only Python 3, nothing to install. On a real vault write to a file and read it in slices (filter by `item`, by slug, by key) rather than pulling the whole object into context; `--indent 0` emits one compact line. **The scanner never writes to the vault** — every fix, MOC, `parents:` value and log append below is the model's own edit.

It parses every `Wiki/*.md`, builds the slug→entry index Tasks 1–3 all need, and emits one JSON object:

| key | what it is | what to do with it |
| --- | --- | --- |
| `run_timestamp` | `YYYY-MM-DD HH:MM` for this run | stamp the suggestion-log blocks with it |
| `inventory` | counts + `full_slugs` / `stub_slugs` | opens the run report |
| `discipline_tags` | enum slug → `{full, stub}` counts | the disciplines in use — one MOC per discipline whose `full` count is ≥1; a stub-only discipline (`full: 0`) gets none (Task 3) |
| `off_enum_tags` | malformed / off-enum slug → entries using it | item-8 format fixes (Task 1) |
| `untagged_full` | full entries with a present-but-empty `tags:` | **valid, not a violation** — report as *unplaced* |
| `problems` | `{slug, item, message}` — the deterministic violations | Task 1 worklist |
| `problem_tally` | per item: entries affected, `pct_of_full`, issue count | the recurrence evidence for a wiki-builder proposal |
| `collision_candidates` | `{a, b, probe, detail}` — possible duplicate entries | **review only, never merge** |
| `rename_candidates` | `{slug, new_slug, inbound_links, target_exists}` | **propose for approval, never auto-apply** |
| `backfill_candidates` | `{slug, target, surface, bare_noun_alias}` — bare mentions of other entries; `bare_noun_alias` tags single-word lowercase alias surfaces for batching | judge each against the closeness bar (Task 2) |
| `hierarchy_diagnostic` | who self-parents now, per discipline | **stale-`parents:` detector** — nothing self-parents under the MOC-root rule, so every slug listed is left over from an earlier run and gets overwritten this run (Task 3) |

**Three classes of finding, and only one of them is a fix.**

1. **Fix in place** — the ordinary `itemN` entries in `problems`, plus the standalone `stub` key. Each has a determinate fix; apply it and touch nothing else in the entry (*Churn-avoidance contract*).
2. **Report, never fix** — eight keys, all of which go to *Notes for the user* and nowhere else. **`item0`** is the odd one and does not follow the `itemN` pattern's meaning: it is not a checklist violation at all but a file the scanner could not read (`unreadable: <error>`), so there is nothing in the entry to fix and the fix is at the filesystem — name the path and the error and move on. It is easy to misroute precisely because it *looks* like an ordinary `itemN` fix-in-place key, and the scan still exits 0, so nothing else signals it. `item3/user-action` (`created > updated`), because wiki-linter writes neither date (*Dates*) — quote both dates. `item12/remote-image` (a `![](http…)` embed), because that form is the one wiki-builder **mandates** for a remote URL — see item 12 in `references/qc-items.md`. `item2/obsidian-key` (a frontmatter key that is Obsidian's own — `cssclasses`, `publish`, `permalink` and the rest), because it is not a schema violation at all and the only thing "fix in place" could mean for an unexpected key is to **delete** it, which destroys the user's own appearance/publish configuration. And the `read:` keys that carry no recognizable answer — `item2/read-missing` (no `read:` key) and `item2/read-null` (the key is there, its value is YAML null: bare `read:`, `read: null`, `read: ~`) — because `read:` is the user's own review checkbox and wiki-linter never writes it (*Dates*): supplying `read: false` would silently clear the tick on a note the user had already marked read, exactly the state the field exists to hold. An unrecognizable string or list (`item2/read-unknown`) follows the same route. **None has a known boolean value to preserve**; only a `read:` that already means something can be retyped. And `item12/missing-image` (an `![[…]]` embed naming a file that is not in `Sources/Images/` — emitted only when Step 0 was given `--images`), because the two repairs are both outside the entry: the figure was never extracted, or an approved source rename renamed it (`CONVENTIONS.md` §1a). **Never delete the embed or its caption** — deletion is the only thing "fix in place" could mean here, and it throws away the one record of which figure belongs there. **None of the eight is a finding this pass can close**: two are not violations at all (`item12/remote-image`, `item2/obsidian-key`), two are repaired outside the entry (`item0`, `item12/missing-image`), and four only the user can resolve (`item3/user-action`, `item2/read-missing`, `item2/read-null`, `item2/read-unknown`). Nothing else happens to any of them. (Of the other seven slashed keys, `item10/dangling` and `item10/dup` *are* acted on — in Task 2, not Task 1 — `item10/unparsed` is reported and repaired on the file it names, which arrives as its own `item0`/`item1` finding, and four are class-1 fixes in place: `item10/case`, where the link resolves case-insensitively in Obsidian, so rewrite its target to the on-disk slug the message names, and **never** stub it — on the vault's case-insensitive volume that stub write opens and overwrites the real entry; `item10/alias`, where the target is another entry's alias, so pipe the link through its owner and **never** stub it either; `item2/read-type`, a `read:` whose value is a real answer in the wrong spelling; and `item2/parents-null`, a bare `parents:` where the empty list belongs. **`item2/parents-null` and `item2/read-null` look alike and route oppositely**, and the difference is whether the fix invents anything: `parents: []` re-spells an empty value that is already empty, while `read: false` supplies an answer the field does not have. See `references/scanner.md`.)
3. **Propose, never apply** — `rename_candidates` (vault-wide reach) and `collision_candidates` (merging is refactoring, out of scope). Both are surfaced for the user; the run proceeds on the current filenames.

**The scanner is a floor, not a ceiling.** It mechanizes what is deterministic. The judgment layer stays the model's — whether a flashcard definition is genuinely unambiguous, whether an entry's `tags:` name its right disciplinary *home*, whether a collision candidate is a real duplicate, whether a backfill candidate clears the closeness bar, what shape the hierarchy takes — and several checklist items (type assignment, item-12's equation clauses — coverage from the note's own prose, display form, notation — item-13 stacked-body semantics, item-17 alias semantics) have **no** mechanical layer at all and are checked only by reading the entries. (Item-12 *figure* coverage and item 15 have no mechanical layer either, but both need the source — out of scope: surfaced, never performed; see *Out of scope* in `references/qc-items.md`.) The scanner output is the starting worklist, not the whole job.

**Read `references/scanner.md` when the scan JSON contains an `item16` or `item18` finding, when you need a JSON field the table above does not list, or when the scan exits non-zero.** All three are decidable before you open it — `grep -cE '"item16"|"item18"' '/tmp/wiki-scan-<run-id>.json'` settles the first (`-E` with a plain `|`: the BRE `\|` alternation is a GNU extension that macOS grep treats as a literal pipe, i.e. it never matches and this trigger silently never fires). Those two checks are the only ones loose *on purpose*, which is why they are the trigger: re-tightening the item-18 display-label test re-breaks the cross-domain bare-term links wiki-builder mandates, and re-tightening the item-16 bullet term-anchor pattern (the scanner's "16b" branch — it is emitted under the plain `item16` key) re-flags wiki-builder's own canonical definition bullet. Both reasons are recorded there and in the script's comments. A scan with neither key contains no finding with a documented reason to be overridden, so the file stays shut.

## Task 1 — Retro-QC (source-independent subset)

Re-check every **full** entry against wiki-builder's Quality Checklist and fix violations **in place**. Legacy stubs — entries whose `sources:` is `["stub"]`; neither skill creates new ones, but older vaults still hold them — follow the stub structure (see *Stubs (legacy)* in wiki-builder's SKILL.md): they are exempt from items 11, 12, 19, and **item 9's *length* guidance — that clause only**. Item 9's other clauses still bind a stub, because the stub format itself requires them: the prose opener, no blank line after the frontmatter, and the parenthetical date on a `Person`/`Event` opener. Two of those exemptions are themselves narrower than they read: item 12's figure/caption/literal-`$` rules are exempt on a stub, but the `--images` **embed-existence check still runs and reports on stubs** (`item12/missing-image` — a dead embed is dead whatever the entry is), and item 19's exemption is **one-directional** — a stub must not *have* a `## Flashcards` section, and the scanner flags one that does. Items 1, 2, 7 (description — a stub carries a real one), 8 (tags — always ≥1 on a stub, never blank), 17 and 18 apply too.

**Read `references/qc-items.md` when Task 1 runs, before fixing anything.** It carries the per-item enforcement detail for items 1–19, what is out of scope because it needs the source, the fix-discipline limits (targeted localized fixes; no discretionary body-prose rewriting), and the item-6 strip-vs-reclassify call. What follows is only the routing.

**Work the `problems` array by item key.** Most `itemN` findings have one determinate output — unbold a span, trim a description to ≤110, convert a bare Related link to piped form, strip a source-meta phrase, repair a tag's *format*, spell an empty `parents:` as `[]`, split a 35+-word sentence (item 9), add a body-introduced alias missing from `aliases:` (item 17), typeset or normalize an equation under item 12's equation clauses (insert the display equation a note's own prose states, convert an inline defining equation to a display block, rename off-standard symbols together with their prose references) — the last three are read-detected rather than scanner-emitted; see items 9, 12 and 17 in `references/qc-items.md`. One key is not an `itemN` at all: **`stub`** — a stub carrying a `**Related:**` footer, which the stub structure forbids — and it is an ordinary fix in place (delete the footer line). These keys route differently:

- **`item2/read-missing`** — report-only, per class 2 above. The `read:` key is absent; **never add it.** `read:` is the user's review checkbox, so writing `read: false` into an entry they had already marked read destroys the one piece of state the field holds — the same shape as `item3/user-action`, and it goes to the same place: *Notes for the user*, slug listed, for the user to add by hand.
- **`item2/read-null`** — report-only too, and for exactly the reason above. The `read:` key is present but carries no value: a bare `read:`, `read: null`, or `read: ~`, all of which are YAML null. **Never fill it in.** A null is not a wrongly-spelled answer, it is the *absence* of one, so there is nothing here to preserve and `read: false` would be the linter inventing the user's review state — the same harm as writing the missing key, which is why it routes with `item2/read-missing` and not with `item2/read-type`. Report it under *Notes for the user* with the slug and the spelling found.
- **`item2/read-type`** — an ordinary fix in place: `read:` is present and *does* carry an answer, just not as a bare YAML boolean (`"false"`, `yes`/`no`, `0`/`1`). Rewrite it to bare `true`/`false`, **preserving which one it means** — the value's sense is unambiguous and only its spelling is wrong, which is exactly what distinguishes this from the missing, null, and unrecognizable cases. A quoted `"false"` is a non-empty string, and Obsidian's checkbox renders it as permanently checked.
- **`item2/read-unknown`** — report-only. The value is not a recognizable true/false answer, including an arbitrary string or a list. Never coerce it to a boolean; report the spelling and ask the user to supply their review state.
- **`item2/parents-null`** — an ordinary fix in place: `parents:` is present but bare, i.e. YAML null, where an empty list belongs. Write `parents: []`. A bare key renders as an empty *text* field against the `multitext` type the vault pins, and `parents:` is wiki-linter's own field (Task 3), so the spelling is its to normalize.
- **`item2/obsidian-key`** — report-only, per class 2 above. The key is Obsidian's own (`cssclasses`, `cssclass`, `publish`, `permalink`, `cover`, `image`, `banner`, `icon`), not this schema's, and it is **not a violation**. **Never delete or reorder it** — it is the user's appearance or publish configuration, no skill here writes it, and nothing can reconstruct it. Name the slug and the key under *Notes for the user*. A genuinely off-schema key (`mood:`, a stacked-merge scar) arrives as a plain `item2` and is fixed as one.
- **`item3/user-action`** — report-only, per class 2 above. Never rewrite either date.
- **`item4/source-identity`** — report-only. A PDF and a markdown source share a filename stem, which can mean either a PDF/summary pair or two independent sources. Inspect the markdown note's decoded `sources:` (or legacy `source:`); preserve both references unless that provenance establishes it is a summary of this PDF. A URL-origin clipping must not be dropped because its filename happens to match. Report unresolved or malformed provenance under *Notes for the user*.
- **`item12/remote-image`** — report-only, per class 2 above. A `![](http…)` embed is the form wiki-builder mandates for a remote URL; **never rewrite it to a `![[…]]` embed** — that resolves to nothing and loses the URL. Mention it in the report as an image that *could* be localized by re-running clipping-processor on the source clipping, and move on.
- **`item12/missing-image`** — report-only, per class 2 above, and emitted only when Step 0 was given `--images`. An `![[…]]` embed names a file that is not in `Sources/Images/`, so Obsidian renders the embed as plain text and the reader silently gets no picture. **Never delete the embed or its caption.** The repair is outside the entry either way — the figure was never extracted (pdf-figure-extractor has not run on that source), or an approved source rename renamed it with its source (`CONVENTIONS.md` §1a), in which case the embed is rewritten to the new stem once the user confirms the new name. Name the slug and the filename under *Notes for the user*.
- **`item10/dangling` / `item10/dup`** — Task 2's, not Task 1's: a dangler is dropped to bare text (never stubbed — stub creation is retired; a real gap is surfaced as a missing-entry candidate), a duplicate is collapsed by pruning.
- **`item10/case`** — an ordinary fix in place, right here in Task 1: the target matches an entry once case and Unicode normalization are ignored, so the link *resolves* in Obsidian — rewrite the link target to the on-disk slug the message names, preserving existing anchors and explicit display labels. **Never route it to the dangler protocol:** on the vault's case-insensitive volume, a stub written at the link's spelling opens the existing entry and overwrites it (`references/scanner.md`).
- **`item10/alias`** — an ordinary fix in place, also here in Task 1: the target is not an entry but another entry's **alias**, which Obsidian resolves, so the link works and only its spelling is wrong. Rewrite it to the piped form the message gives — `[[recall|TPR]]`, the owner as the target; retain any existing anchor and explicit display label, using the alias as the label only when none was supplied. **Never stub it.** Stubbing creates a file at the alias's name, a file outranks an alias, and every `[[TPR]]` in the vault stops resolving to the entry that owns the alias and starts resolving to the new one-line stub — a silent re-pointing that nothing afterwards reports as an item-18 clash.
- **`item10/ambiguous`** — report-only. More than one file has this basename, or more than one entry claims this alias. Preserve the complete link, including its path, anchor and display text, until the intended destination is resolved; never pick the first file or alias owner, and never drop it as dangling.
- **`item10/unparsed`** — reported, not fixed here, and **never stubbed**: the target names a file that is on disk but did not parse as an entry, so the link *resolves* and a stub written at that name would overwrite the file. The repair belongs to that file, and it arrives in this same scan as its own `item0` (unreadable) or `item1` (no frontmatter) finding — fix it there, and this finding clears itself. An `item1` repair reconstructs only what the file itself evidences; the fields the linter may not write — `created:`, `updated:`, `read:`, and a `title:` it would have to invent — route to *Notes for the user* per item 2, never made up. (An `item0` stays report-only — its fix is at the filesystem.)
- **`item19`** — the mechanical floor (per-card structure, line-2 form, line-1 markup, answer leak, line-3 plainness) is fixed on **every** card; whether a card's *definition* may be rewritten at all depends on its review history. **Read `references/flashcards.md` whenever you are about to change a card.**
- **`item8`** — apply the unambiguous *format* fixes automatically (add the `#`, add the quotes, drop a duplicate, expand a safe abbreviation, convert a wikilink-form tag, give a blank-tagged stub an inherited tag), but **surface the disciplinary-home judgment** rather than re-homing an entity on a guess.

**Two things Task 1 surfaces and never performs.**

- **A retitle/re-slug is a rename — proposed, never applied.** Its reach is vault-wide: the file, every inbound wikilink, `parents:`, *and* the vault-root MOCs. Report each candidate with its `inbound_links` count and reason; apply one **only** after explicit user approval, and then fully, rewriting every reference everywhere including the MOCs. A candidate with `target_exists: true` is never renamed into — flag both entries as a likely duplicate or disambiguation.
- **Duplicates are reported, not merged.** `collision_candidates` covers slug *shape* only; synonym/near-synonym duplicates (the same concept under two names, a stub restating a full entry) are a blind spot the probes cannot catch, so surface those too as you read. Merging is refactoring — out of scope.

**Valid blanks are not violations.** Blank `tags:` on a full entry is an intended state; never "fill it in" as a QC fix. (Blank `tags:` on a *stub* **is** a violation — a stub needs ≥1 tag.)

**`importance:` is retired, and a legacy one is left alone.** The field was removed from wiki-builder's schema, so new entries omit the key; the entries already in the vault still carry it, populated. **Never strip it, never rewrite it, never flag it** — at any severity. The scanner emits no finding for it, and there is no item 20 (see *In scope* in `references/qc-items.md`).

**Refresh after QC edits.** If Task 1 changed entries, re-run the Step 0 command before Task 2 or Task 3 consumes its worklists. Use the refreshed inventory, aliases, `backfill_candidates`, and `discipline_tags`: a newly added alias or corrected tag is absent from the original scan. Keep the first scan's `run_timestamp` as this run's suggestion-log timestamp.

## Task 2 — Link hygiene

Two directions: **backfill** the links that couldn't exist when an earlier entry was written, and **prune** duplicate or weak links. This is the only place wiki-linter modifies body-prose wikilinks and the Related footer, and the only **destructive** operation in the skill — so every prune is itemized in the run report.

`backfill_candidates` is the worklist for the first; `item10/dup` plus your own reading is the worklist for the second; `item10/dangling` is the third case — drop the link to bare text (never stub; see *Dangling links*). (`item10/case` findings are **not** danglers and never reach this protocol — they were already fixed in place in Task 1 by rewriting the link's spelling.)

Every one of those decisions — add, keep, prune, drop — is made against **one strict conceptual closeness bar**, which is wiki-linter's own: nothing else links across the vault, so the bar answers to this skill alone. In brief, a mention earns a link only when the reader would genuinely benefit from jumping there and the relationship is conceptual rather than incidental co-occurrence; a passing mention or bare name-drop is **rejected even when the slug exists and the reference is unambiguous** — correctly identifying which entity a word refers to is a precondition for linking, never a reason to link. **When in doubt, do not link — over-linking is the failure mode.**

**Read `references/link-hygiene.md` when Task 2 runs** — before applying or rejecting a single candidate, pruning any link, or resolving any dangler. It holds the four criteria in full, the cross-domain bare-term rule (never auto-link a bare common noun to a bare slug), the two removal triggers and what is never pruned by this mechanism, the dangler protocol (drop, never stub — including orphans inherited from earlier runs; assume the vault has *not* been swept), and why backfill and prune do not oscillate.

## Task 3 — Hierarchy: `parents:` and MOCs

`parents:` and the MOC are **two renderings of one tree.** Derive a single concept hierarchy per discipline once per run, then use it for both — so an entry's parent(s) and its position(s) in the MOC never disagree.

One tree per discipline **tag** carried by ≥1 non-stub entry (the `discipline_tags` keys with a non-zero `full` count), **rooted at that discipline's own MOC note** — `[[machine-learning-moc]]` for `#machine-learning`. The root is not an entry and is never chosen: the MOC's name falls out of the tag (`<discipline-slug>-moc.md`, in the vault root), wiki-linter creates the file in this same task so it always exists, and it is a real note, so the wikilink resolves and it is a legal `parents:` target. **Rooting is therefore deterministic — two runs over the same vault pick the same roots with no judgment and no hand intervention.** The discipline *tag* is still not a note: never a bullet, never a `parents:` value.

Every top-level branch takes the MOC as its parent; everything below points **up** to its nearest broader full entry. **Nothing self-parents — the correct count is zero, in every discipline.** This replaces the old anchor-entry rule, which required a full entry for the discipline itself (`machine-learning.md`); wiki-builder never writes one — no source treats a discipline as an entity — and wiki-linter may not mint one, so its fallback made every broadest branch self-parent, which is precisely what `check_rooting` calls an un-rooted tree. Read `hierarchy_diagnostic` accordingly: it reports what **last** run wrote, so any `self_parented` slug is stale and this run's recomputed `parents:` clears it — `check_rooting: true` on the first run after this change is expected and self-resolving. After a run, re-scanning must show `self_parented: []`; a non-empty list then is a real defect at *any* count — which is where the flag now sits too, firing at `≥1` rather than the old rule's `≥3`.

**Read `references/hierarchy.md` when Task 3 runs.** It holds the derivation principles (shallow, organised by the field's own taxonomy, category slots filled by unlinked terms rather than minted stubs), the exact `parents:` semantics including the multi-tagged, root, unplaced and stub cases, the MOC file format and the reorganise-freely-but-don't-churn rule, and the consistency contract between the two renderings.

## Run report

End every run with a single consolidated report:

- **Inventory** — N entries (full / stub), per-discipline-tag non-stub counts, and any untagged full entries.
- **Task 1 — tags fixed / flagged:** tag *format* fixes applied (added `#`/quotes, de-duplicated, abbreviation expanded to an enum slug, wikilink-form converted to a `#`-tag, blank stub given an inherited tag) vs **disciplinary-home calls flagged** for the user — an entity whose tag set looks like a "uses"-trap mis-home or a borderline calibration case (`Markov chain` → math or ML?), surfaced not silently re-homed.
- **Task 1 — QC fixes**, grouped by checklist item: per fixed entry, the item and a one-line description of the fix. Separately, **renames proposed for approval** — each as `old-slug → new-slug`, the inbound-wikilink count that would be rewritten, the reason (stale/variant filename vs. title correction), and a collision flag where the target file already exists — and, if the user approved any during the session, **renames applied** (only the approved ones); **`Software` reclassifications** (item 6, type flipped to legitimize API surface) and any **ambiguous code-content/type calls flagged** for the user to resolve.
- **Task 1 — duplicate-entry candidates:** item-5 collision-probe matches (probe + the two slugs), plus any **synonym/near-duplicate candidates** noticed while reading (same concept, different names; a stub restating a full entry) — surfaced for the user to review; **not merged** (merging is out of scope).
- **Task 2 — Links:** backfill candidates **applied** (entry → target) vs **rejected** (entry → target, why — failed the closeness bar), links **pruned** (entry → target, reason) — *itemize every prune*, **duplicates collapsed**, **danglers resolved** (all dropped to bare text; stubs are never created), and **ambiguous bare terms left as text** (flagged).
- **Task 3 — Hierarchy:** **MOCs created/updated** (which discipline tags); when a MOC was **structurally reorganized** (not just appended to), summarize how — group headers added/renamed/merged/dissolved, branches re-nested — so a large diff is explained rather than surprising; **unlinked category terms** placed as structural placeholders (list — these are the slots awaiting real entries), **`parents:` set/changed** (count, noting how many changed *because of* a reorg vs. new entries), **legacy self-links cleared** (entries whose `parents:` pointed at themselves under the old anchor-root rule and now point at their MOC or a real ancestor — the `hierarchy_diagnostic.self_parented` slugs), **unplaced entries** (blank `tags:`).
- **Missing-entry candidates** — dangling-link targets that were dropped but look like real gaps (a concept several entries lean on, a heavily-referenced name), surfaced here and in `wiki-notes-suggestions.md` so the user can run a source through wiki-builder to create them properly. **Stubs are never created** — not for danglers, not for disciplines or category slots (tags aren't wikilinks, each tree is rooted at its MOC note rather than an entry, and category slots use unlinked terms).
- **Entries untouched** — count (the churn-avoidance signal: most of a steady-state vault).
- **Notes for the user** — anything needing a human call: contested retitles, alias collisions that need a disambiguation decision, entries that sprawl across several subjects (candidates for a wiki-builder-style split, which is out of scope here), Related footers past ~12, borderline disciplinary-home/tag calls, blank-`tags:` full entries that might now have a clear disciplinary home, **`created > updated` entries** (the scanner's `item3/user-action` findings — slug plus both dates; the linter cannot write either field, so these are the user's to correct), **entries carrying a remote image** (the scanner's `item12/remote-image` findings — slug plus URL; the embed is valid and was left alone, but the image is one clipping-processor could localize into `Sources/Images/` on a re-run of the source clipping), **entries carrying an Obsidian built-in frontmatter key** (the scanner's `item2/obsidian-key` findings — slug plus key; it is valid and was left alone, and only the user can say whether they still want it), **entries whose `read:` carries no recognizable answer** (`item2/read-missing` — slug alone; `item2/read-null` or `item2/read-unknown` — slug plus the spelling found; the linter cannot infer the user's review state, so all three are the user's to set), **unreadable files** (the scanner's `item0` findings — path plus the error; the fix is at the filesystem, so only the user can make it), **entries embedding a figure that is not on disk** (the scanner's `item12/missing-image` findings — slug plus filename; the embed and caption were left alone, and both repairs are outside the entry: extract the figure, or confirm the renamed stem per `CONVENTIONS.md` §1a), and **equations inserted into read entries** (item 12's coverage clause — slug plus the equation inserted; the linter never writes `read:`, so the checkbox is the user's to clear).
- **Proposing improvements (wiki-builder and wiki-linter)** — the report's closing section: two short, ranked sets of concrete, evidence-grounded proposals — one for the **wiki-builder** skill (from recurring vault-content patterns), one for the **wiki-linter** skill itself (from recurring execution friction) — or an explicit "nothing systematic this run" for either side. Every item is listed, but the two cases are distinguished: items **newly appended** to the vault-root log with the run timestamp (`wiki-builder-suggestions.md` / `wiki-linter-suggestions.md`) vs. items **already open there**, whose recurrence count was bumped in place and which were *not* re-appended — with the count. The report notes what was written and where. Specified in full in the next section.
- **Proposing note improvements** — content/clarity/organization suggestions for the *notes themselves* (thin or unclear entries, missing or duplicate concepts, sprawl, uneven coverage, inconsistent formatting) that need a human or a source — distinct from the two skill logs (which are about the tooling) and from auto-fixes (already applied this run). Recorded in `wiki-notes-suggestions.md` under the same new-vs-recurring rule. The content-level items under *Notes for the user* above are the same ones recorded here. See *Proposing note improvements*.

## Closing the loop — three propose-only backlogs

Every run ends by proposing improvements in three directions, none of which it applies: to the **wiki-builder** skill, to **wiki-linter itself**, and to the **notes' content**. Each goes in its own log in the vault root — `wiki-builder-suggestions.md`, `wiki-linter-suggestions.md`, `wiki-notes-suggestions.md` — which is the vault-artifact form of *proposing*; wiki-linter modifies **neither skill file**. Nothing is invented to fill a section: the *report* always carries all three sides, but a log gets a dated block only when there is something real and **new** for it.

This whole protocol lives here, in the spine — there is no reference file to open for it, and no run needs one.

**Why the loop exists.** wiki-linter sees the **whole vault at once**, and it is the only component positioned to notice that a problem is *systematic*: it sees in aggregate what wiki-builder produced *and* feels where its own checks strain across every entry. Each direction draws on different evidence — a **wiki-builder** proposal comes from a pattern in the vault's *content* (what entries look like); a **wiki-linter** proposal comes from friction in the linter's *own execution* (a check that fired on something genuinely fine, a real issue the scanner has no check for and the model fixed by hand, a decision the linter's own rules left ambiguous, a tool limit the run hit); a **notes** proposal is about the *content as a body of knowledge*, things that need a source or a human call. All three are **always part of the report** — the loop is only useful if it is reliable — and all three are strictly evidence-bound (*No fabrication*).

### Proposing improvements — to wiki-builder and to itself

Every candidate, in either skill direction, passes the same three tests.

**1. Recurrence — a pattern, not an instance.** Propose from patterns, never one-offs. For **wiki-builder**: the same issue across many entries — a checklist item firing on a meaningful share of the vault (use the scanner's `problem_tally` key — per item, `entries`, `pct_of_full` and `issues`), the same judgment-flag recurring, or the same auto-fix applied dozens of times — signals wiki-builder's *behavior*, not one stray source or hand-edit. Recurrence counts whether or not wiki-linter fixed it: a format slip silently auto-fixed on 40 entries is exactly what wiki-builder should stop emitting — the fix *is* the signal. For **wiki-linter**: the *friction* recurs — the same false flag overridden across many entries, the same unchecked issue fixed by hand again and again, the same ambiguity resolved by guess each time, the same tool failure. A single false positive or a one-time hiccup is noise; a repeated one is a self-improvement candidate.

**2. Attributability — whose change fixes it?** The filter that makes the proposals worth reading. Each recurring pattern routes to a **wiki-builder** change, a **wiki-linter** change, or **neither** — and one observation can hit both skill destinations at once (e.g. "descriptions keep mismatching the title": wiki-builder should stop producing the mismatch *and* the linter, which has no mechanical check for it, could add one).

- **→ wiki-builder** when the pattern is in something it controls writing one entry from one source: descriptions consistently over the length cap, LaTeX consistently on flashcard line 3, a frontmatter field consistently mis-ordered, ML methods consistently over-tagged `#mathematics`/`#statistics` instead of `#machine-learning` (the "uses" trap), an alias/title convention consistently slipped. It is **not** wiki-builder's when it is an **incremental-generation gap** — missing links between entries, MOCs, `parents:`, cross-vault dedup — which are architectural and **wiki-linter's job by design** (wiki-builder cannot see entries that do not exist yet; **never** propose making it add the cross-links / build the MOCs / dedupe the vault / populate `parents:`), nor when it is a **hand-edit** or **legitimate source variation**. When wiki-builder *already* specifies the violated rule, propose about **enforcement** — a worked counter-example, promotion to a hard QC-checklist item, or the specific missed edge (e.g. line-3 LaTeX leaking from the body's defining equation) — not the rule's existence.
- **→ wiki-linter (self)** when the friction is in the linter's own behavior: a recurring **false positive** (a mechanical check flagged something the model verified is fine → propose tightening the condition, with the pattern as evidence); a **coverage gap** (a class of real issue the model keeps fixing by judgment *that is mechanizable* → propose a scanner check; if it is irreducibly a judgment call it stays the model's, and a brittle mechanical check for it is not an improvement); **ambiguous self-guidance** (a decision point the linter's own prose did not determine, so the model had to guess and might guess differently next run → propose clarifying that rule); **operational/tooling friction** (a tool limit, performance wall, or environment hazard the run actually hit → propose a concrete mitigation); or **awkward/indirect handling** (a case detected only indirectly, in a way that misleads, recurring → propose a more direct check or clearer message).
- **→ neither** when a check correctly caught real problems (working as intended), when a one-off was handled fine, or when the model simply wishes it could do something the skill places **out of scope by design** (splitting/merging, editing wiki-builder, generating entries). If the model repeatedly wishes for an out-of-scope capability, surface it as *"X is out of scope by design; here is the recurring case, if you want to reconsider that boundary"* — not a naive feature add.

**3. Actionability — specific, located, with the fix.** Each proposal names the **pattern + evidence** (count/share or representative slugs for wiki-builder; the recurring friction for wiki-linter), the **attribution** (one phrase on why this skill is the right place to change it), the **location** (wiki-builder: the field/section/checklist item; wiki-linter: the scanner check, the prose section, or an operational note — the linter can point at its own structure, since this SKILL.md *is* the linter), and the **proposed change** (concrete: the rule to add/tighten/exemplify, the check to add/refine, the mitigation to adopt). "Improve flashcards" / "make the linter smarter" are useless; "tighten wiki-builder's line-3 rule in `references/flashcards-and-emphasis.md` §4 with a worked example, because 18% of entries carried `$…$` there" and "narrow the linter's line-1 italic check — `$a*b$` LaTeX multiplication is flagged as italic on N entries" are actionable.

### Anti-drift — self-proposals serve the skill's purpose, not its convenience

A skill proposing changes to *itself* carries a specific risk: drifting toward what makes its own job easier rather than what keeps it correct. Guard against it. wiki-linter's purpose is **faithful enforcement of wiki-builder's schema** under the floor-not-ceiling model, with churn-avoidance — self-proposals must *sharpen* that, never relax it. A proposal to flag *less*, enforce *less* faithfully, or drop a check is legitimate **only** with a genuine false-positive justification; "this check is annoying / fires a lot" is not one. Never propose changes that would weaken the schema's authority, expand the skill past its deliberate boundaries, or alter its character. The bar for a self-change is *higher*, not lower, than for a wiki-builder change.

### Hard boundary — propose, never apply (to either skill)

wiki-linter **modifies neither skill file** — not wiki-builder's, and not its own. Both skills are authored and maintained by the user; a skill that rewrites itself mid-run is out of bounds (and a self-edit hazard besides). What wiki-linter *does* write is **vault artifacts**: entries, MOCs, and the three **suggestion logs** in the vault root. Writing a proposal into `wiki-builder-suggestions.md`, `wiki-linter-suggestions.md`, or `wiki-notes-suggestions.md` is the vault-artifact form of *proposing* — the same kind of act as writing a MOC — **not** applying: the logs are advisory text the user reads and acts on. So the boundary is exact: write the vault logs freely; never touch wiki-builder's files or this one.

### No fabrication — the "always" has integrity

Always include the section in the run report, but never invent a proposal to fill a side. If the run surfaces no recurring wiki-builder-attributable defect, say *"No systematic wiki-builder gaps surfaced this run."* If it surfaces no genuine execution friction, say *"No wiki-linter limitations surfaced this run."* A fabricated suggestion is worse than none — for wiki-builder it sends the user to change a generator that was not the problem; for wiki-linter it risks churning a working skill toward convenience. Report what is real. **The "always" applies to the report, not to the logs:** when a side has nothing new this run, write nothing to that file.

### Format

Each side is a short ranked list, most-systematic-first and **capped at the few highest-value items** (a focused handful beats an exhaustive dump). Each item carries a **stable ID** and four lines:

```markdown
### [flashcard-line3-latex] LaTeX on flashcard line 3
- **Pattern:** `$…$` on line 3 of 18% of full entries (item19, 22 entries)
- **Why wiki-builder:** the rule exists but has no worked counter-example
- **Change:** add one to wiki-builder's `references/flashcards-and-emphasis.md` §4, showing the body's defining equation leaking into line 3
- **Seen:** ×1 · first 2026-08-08 09:41 · latest 2026-08-08 09:41
```

The **ID** is a short kebab-case slug of the defect and its location (`flashcard-line3-latex`, `desc-over-110`, `moc-reorg-churn`). It is what makes a proposal identifiable across runs, so it must be **stable**: before minting one, read the IDs already open in that log and **reuse the existing ID** when this run's proposal is the same defect. The log's own IDs are the vocabulary; a near-miss synonym re-raises an item that is already there. Recurring *split candidates* roll up under wiki-builder ("its scoping rule lets entries sprawl across N subjects — tighten one-entity-per-entry"), not as per-entry notes.

### Persisting to the vault logs

The proposals are durable, not just printed. Each run records them in **three files in the vault root** — `wiki-builder-suggestions.md`, `wiki-linter-suggestions.md`, `wiki-notes-suggestions.md` — so they accumulate into a backlog the user works through between runs. **A log is a set of open items, not a transcript of runs**, and its length is bounded by the number of distinct unresolved proposals — never by the number of times the linter has run.

- **Read the log first, always.** Before writing anything, read the file and collect the IDs of the items already in it. This is what tells new from recurring, and it is also the safety mechanic: **never call a whole-file write with only the new content** — the file tools overwrite by default, and one such call silently destroys the accumulated backlog. Read-then-append, or a shell append (`>> file`). After writing, confirm the prior content is still present.
- **New proposal → append a dated block.** For each side with at least one proposal whose ID is **not** already open in that log, **append** a section at the **end** headed with the run timestamp (the scanner's `run_timestamp` key — use it, don't re-derive a time): `## YYYY-MM-DD HH:MM — <short run context>`, e.g. the vault size, followed by that side's genuinely-new items in the format above. Appending means adding at the end; never rewrite, reorder, or delete what is already there.
- **Recurring proposal → update it in place; do not re-append it.** If an item with the same ID is already in the log and still unresolved, the proposal has **not** changed and the paragraph is **not** written again. Edit that item's existing `**Seen:**` line only — bump the count and set `latest` to this run's timestamp — and leave every other byte of the file alone. This is a one-line targeted edit, not a rewrite, and it is the only in-place edit the linter ever makes to a log. The repetition across runs is still recorded, and still exactly the evidence that the item remains open; it is now recorded as a **count**, which does not grow the file. **This is the churn-avoidance contract applied to the logs**: the same reason an unchanged entry is left byte-for-byte untouched is the reason an unchanged proposal is not re-appended.
  - *If the underlying pattern genuinely changed* — different evidence, different proposed fix, a different location — that is a **different** proposal: give it its own new ID and append it as new. Re-stating the same item with a bigger number is not a new proposal: leave its evidence line unchanged, update only `Seen:`, and put this run's new count in the report.
- **Nothing new → no block.** A run whose entire output for a side is recurrences appends **no dated block** to that file; only the `Seen:` counters move. A run with nothing at all for a side leaves the file untouched (per *No fabrication*). No empty dated sections, ever.
- **Create with a one-line header if missing.** If the file does not exist (first run, or the user just reset it), create it with a short title and a note — e.g. `# wiki-builder — suggested changes (appended by wiki-linter runs; implement, then clear to reset; newest at the bottom)` — then append the first dated block under it.
- **The user resets; the linter never does.** The linter appends new items and bumps counters. It does **not** truncate, clear, prune, reorder, or de-duplicate these files, and it never removes an item — resolving one and clearing it is the user's action. (Bumping a counter is not removal, and it is strictly less destructive than the re-append it replaces.)
- **Report and log stay consistent.** The report's lists and the logs carry the same content, and the report distinguishes the two cases: which items were **newly appended** (with the timestamp and file names, so the user knows where the backlog lives) and which were **already open and had their recurrence count bumped** (with the count). A recurring item still appears in the report — the user sees everything real this run — it just does not get written to the log a second time.

### Proposing note improvements

The two logs above are about the **tooling** — how the generator and the linter behave. This third channel is about the **content**: worthwhile improvements to the *notes themselves* that wiki-linter notices while reading the whole vault but does **not** make on its own, because they need the source, a human's judgment, or an operation the skill keeps out of scope. They go in `wiki-notes-suggestions.md`, under the **same mechanics** as the skill logs (*Persisting to the vault logs*) — including stable IDs and update-in-place on recurrence, which matter most here: a thin entry stays thin until the user expands it, so it would otherwise be re-logged forever.

**What belongs here — broadly, anything that makes the notes better as a body of knowledge:**

- **Depth & gaps** — a full entry thin relative to its importance, worth expanding; a concept many entries lean on but none defines (a missing node — often a recurring dangling target or a heavily-referenced stub); an entry missing a salient aspect the rest of the vault assumes.
- **Clarity & quality** — a definition that is circular, vague, or quietly conflates two senses; a passage that reads awkwardly; **a worked example running past ~2 sentences, or a passage tangential to the entity** (wiki-builder's tightened length rules — trimming body content needs the source or a human call, so it is proposed here, never cut by the linter); a flashcard whose chosen *facet* is peripheral, or an entry whose distinct facet warrants a source-supported **split into another entry** (each entry still has exactly one card; the review rewrites wording but does not create another card or re-pick the tested facet); content that looks dated.
- **Organization** — two entries that are the **same concept under different names** (the synonym-duplicate the slug probes can't catch) and should be merged; an entry that **sprawls across several subjects** and should be split; a cluster of entries a missing intermediate concept would organize better; lopsided coverage (a discipline that is mostly stubs).
- **Formatting & consistency beyond the QC floor** — patterns that are not rule *violations* but read as uneven: similar entries differing in whether they use sub-headings, inconsistent figure use, Related footers that are inconsistently full.

**The gate — each item is:** (1) a **genuine** improvement worth the user's time, not a nitpick; (2) **specific and located** — which entry or entries, and what to do; (3) **not already handled** — never log what the linter auto-fixed this run (that is in the report), and never log something whose right fix is a *skill* change (a content **pattern the generator keeps producing** is a wiki-builder proposal; this log is for improving the **specific notes as they stand**); (4) **real** — if nothing this run is worth noting, write nothing; never invent filler.

**Faithful to the no-source stance.** With no source in hand, wiki-linter cannot verify facts, so these are **observations and suggestions, not authoritative corrections** — "this definition may conflate X and Y," "consider expanding," "candidate to merge with Z." It proposes; the user decides and edits (the same posture as the *Hard boundary* — wiki-linter still never rewrites conforming body prose itself). The report's *Notes for the user* and this log carry the same content; the report says what was appended, what was counted, and where.
