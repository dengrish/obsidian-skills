# Images and captions

> **When to read this:** Read this when `find '<images-folder>' -name '<source_stem>_fig*'` prints anything — the same mechanical trigger `SKILL.md` lists — **or when a markdown source contains remote `![alt](http…)` image references**, which live in no folder a find can see and have their own rules below. A source that *has* figures nobody has extracted has nothing here to apply. Skip it entirely when both triggers are empty; say so in the report rather than guessing at images.

---

### Images

Wiki entries embed images from the source — figures, diagrams — as a default. Every figure the source provides is treated as candidate content for the wiki, and the default is to use it: figures took the source's author real effort to design, they often carry information prose cannot capture as concisely, and a figure left unused is a piece of the source's value that the wiki has dropped on the floor. **The default is to place every available source figure in some entry**, paired with the entry whose subject the figure best illustrates. (Source *tables* are not embedded as images — they are recreated in Markdown per the Body Structure tables rule, cells and numbers intact: prose principle 7's "drop the source's data values" governs worked examples in prose and carves recreated tables out explicitly, because a results table with its values removed is an empty grid.)

**Where images come from depends on the source type:**

- **PDF source.** Figures are pre-extracted by the `pdf-figure-extractor` skill into the vault's `Sources/Images/` folder. Naming pattern: `[pdf_stem]_fig_<N>.png`, where `<N>` is the figure number exactly as it appears in the source — which may be a simple integer (`1`), a chapter-and-figure pair (`1-2` for "Figure 1.2"), or a deeper hierarchy (`1-2-4` for "Figure 1.2.4"); supplementary figures use an `S` prefix on the number (`S1`, `S2-3`). Examples: `Burges_LearningToRank_2010_fig_1.png`, `Geron_HandsOnML_2025_03_Classification_fig_3-2.png` (chapter 3, figure 2), `Prince_UDL_2026_12_Transformers_fig_1-2-4.png`, `Doe_GutMicrobiome_2025_fig_S1.png` (supplementary figure 1) — all canonical stems, which is what `pdf-organizer` produces and what `pdf-figure-extractor` will now refuse to key a figure to otherwise (`CONVENTIONS.md` §1a). **Match on `[stem]_fig`, not on `[stem]_fig_`, and accept any image extension.** Everything written into `Sources/Images/` today uses the `[pdf_stem]_fig_<N>.png` shape, so a fresh vault is uniform. **The loose match stays anyway**, and the reason is on the user's disk rather than in this plugin: figures extracted before the naming converged are still sitting in `Sources/Images/` under an older spelling that ran the number straight on after `fig`, and nothing has deleted them. Tightening the glob does not clean those up — it stops seeing them. Matching only the stricter pattern means a PDF whose figures are *already sitting in `Sources/Images/`* yields entries with no images at all, and the unused-figure diagnostic stays silent about it because it walks the same wrong pattern — a total, invisible loss. Extensions vary too: PDFs give `.png`, clippings give `.jpg`, `.webp`, `.gif`, `.svg`. List the `Sources/Images/` folder and match by source stem to find available images. **If a PDF source has no matching extracted figures** (the extractor wasn't run yet, or the PDF has no figures), the use-by-default rule has nothing to apply to — entries for that source have no images, and no figures are fabricated. **Tables are not pre-extracted** — when the source has a table worth recreating in the entry, identify it while reading the PDF and recreate it in Markdown per the Body Structure tables rule.
- **Markdown source.** Image links are embedded in the source `.md` itself — Obsidian embeds `![[…]]` for images already in the vault's `Sources/Images/` folder, and standard markdown `![alt](https://…)` for anything still remote. **A note produced by `clipping-processor` names its downloaded images `[source_stem]_fig_<N>.<ext>` — the note's own filename stem, same string and same casing — precisely so this skill can find them**, so the unused-figure diagnostic below does apply to those. It cannot see the *remote* ones, which have no file in `Sources/Images/` at all; for those the check is instead that every image reference *in the source* is either placed in an entry or has a recorded skip reason. Extract the relevant image references directly from the source's markdown and reuse them in the entry — a remote `![alt](https://…)` stays in markdown form and is never rewritten as a wikilink, which would resolve to nothing and lose the URL.

**A figure and its panels are one exhibit, and the composite is the default.** A file whose label ends in a lowercase letter — `Burges_LearningToRank_2010_fig_3a.png` beside `Burges_LearningToRank_2010_fig_3.png` — is one panel of that figure, written by the same extractor into the same folder (`CONVENTIONS.md` §8b). It answers the `_fig` glob because it is a figure, but it is not a separate candidate: **place the whole figure, and reach for a panel only when the entry's subject is that panel's alone** — a panel showing one mechanism belongs in that mechanism's entry even when the composite it came from spans four topics, and that is the case the panels exist for. Never place a figure and a panel of it in the same entry; that is one picture twice. **For the use-by-default rule and the diagnostic below, an exhibit is the composite**: an unplaced panel is not an unused figure and needs no skip reason, placing the composite discharges every panel under it, and placing any panel discharges the composite.

**Selection: use by default; skip only with a specific reason.** Every figure available from the source is placed in some entry unless one of three specific conditions applies. **Skip condition 1 — the figure adds no information.** A decorative chapter banner, a stock photograph used purely for visual interest, an aerial shot of a campus illustrating "where the lab is" without any technical content — figures that exist for layout rather than to convey something about the subject. The bar here is *no information*, not *less information than the prose*: a figure that says the same thing as the prose still earns inclusion, because the visual representation is itself information the reader benefits from. **Skip condition 2 — another retained figure already covers the same specific aspect more completely.** If two figures depict the same mechanism, the same structure, the same diagram-type, keep the one that conveys more (more dimensions, higher clarity, more complete labeling) and drop the other. "Same specific aspect" is hardened the same way it is in *Images on merge* (`references/merge.md`) — two figures on the same broader subject that show *different aspects* (mechanism vs. application, architecture vs. training dynamics, etc.) both stay; only same-aspect duplicates collapse to one. **Skip condition 3 — the figure's only home is an entity with no entry.** A figure illustrating an entity the source covers too thinly for a full entry (an *Entities deferred* case, or a legacy stub left unpromoted — stubs never carry images) has nowhere legal to go. Skip it and record the reason; without this condition the figure is unplaceable *and* undocumented, so every run re-flags it as a violation and re-fails at placing it. A figure landing here is also a signal worth reading — a source that gives an entity a whole figure often covers it well enough for a full entry after all, so re-check the substance call before recording the skip.

**Pairing figures to entries.** Each figure belongs to exactly one entry — the entry whose subject the figure most directly illustrates. A figure showing the gradient-scaling mechanism inside LambdaRank goes in `lambdarank.md`, not in the broader `learning-to-rank.md`. A figure showing the canonical TPR-vs-FPR curve goes in `roc-curve.md`. A figure showing the agent→action→reward loop goes in `reinforcement-learning.md`. When a figure could plausibly illustrate two entries, choose the more specific one (the figure illustrates a particular concept; the broader concept's entry can reference the more specific concept's entry through wikilinks). When a figure is genuinely about a topic without a sufficiently specific entry — e.g. a figure illustrating a comparison across many concepts where each concept has its own entry but the *comparison itself* isn't a separate entry — place it in the most relevant existing entry and write motivating prose that ties it to that entry's subject.

**The count an entry ends up with depends on what the source provides, not on a target number.** An entry might have zero images (the source had no figures for the entity, or every candidate figure hit one of the three skip conditions above), one, or several. The 1:1 image-to-motivating-paragraph rule (under *Placement* below) is what governs how many images can sit in one entry — if the entry only has one paragraph that motivates a particular figure, that figure goes there; if three figures each motivate a distinct paragraph, all three stay. The selection rule above tells you *which* figures to include; the 1:1 placement rule tells you *where* each one goes.

**Diagnostic for forgotten figures.** After the run, the figures available in `Sources/Images/` for each source should be (close to) fully placed in the wiki — every `[source_stem]_fig*` file **that is not a panel of another one** should appear as an embed in some entry, with the exceptions being the figures that genuinely fall under the three skip conditions above **and have an explicit per-figure skip-reason recorded in the run report (Quality Checklist item 12)**. An unused figure without a documented skip reason is the failure shape to catch: re-walk the source and place it. If many figures from a source end up unused, the default has been violated and the whole set should be revisited. Step 7 of the workflow surfaces unused figures with their skip-reason annotations in the run report so this failure mode is visible.

**Embed syntax.** Use Obsidian's image-embed wikilink form: `![[Burges_LearningToRank_2010_fig_3.png]]` for `Sources/Images/`-based images (Obsidian resolves the basename across the vault). For external URLs from a markdown source's clipping, use standard markdown image syntax `![alt](https://...)` since wikilinks don't handle remote URLs — the `alt` slot is plain alt-text (typically left empty or filled with a brief identifier), **not** the wiki-builder caption. **The italic-caption-on-next-line rule (see *Captions* below) applies uniformly to both embed forms** — wikilink and markdown — so every image embed, however written, has its `*caption*` line directly below it.

**Placement: inline, on the line immediately after the sentence or paragraph the image illustrates.** Placement is determined by the image's motivating prose, not by a fixed slot.

Specifically forbidden:

- **Image without a caption below it.** Every embed has a one-line italic caption on the next line — see "Captions" below.
- **Image detached from its motivating prose, parked at the end of the body just before the Related footer.** This is the default "treat the image as a trailing afterthought" failure mode — and the most common image-placement mistake. If the image illustrates content from the second paragraph of a multi-paragraph body, the image goes between the second and third paragraphs — not at the bottom of the last paragraph. The rule is "next to the motivating prose" — wherever in the body that prose lives.
- **Image at the top of the entry**, before the first prose paragraph. The opening sentence is the canonical definition; nothing visual precedes it.
- **Multiple images grouped as a gallery** anywhere in the body. **Each image gets its own motivating paragraph** — a 1:1 mapping between images and the prose paragraphs they illustrate. **When a source gives an entry two figures on genuinely different aspects but the entry has only one paragraph that motivates a figure, write the second motivating paragraph** — the entry has more to say about the subject or the figure would not exist. Do not drop the figure and do not stack it against the first; the skip conditions do not cover "no room", and *Images on merge* prescribes exactly this move for the merge case. Two images sharing one paragraph, or consecutive embeds with no prose between them, are never correct: if you have two figures worth including, they belong next to two different paragraphs.

Example of correct inline placement:

```markdown
**LambdaRank** is a [[learning-to-rank|learning to rank]] method that sidesteps the non-differentiability of ranking metrics by defining gradients directly, scaled by the change in the target metric from swapping a pair of items.

It starts from [[ranknet|RankNet]]'s pairwise cross-entropy loss and modifies the gradient with a multiplicative $|\Delta\text{NDCG}|$ term — the change in [[ndcg|NDCG]] that would result from swapping the two items in the current ranking.

![[Burges_LearningToRank_2010_fig_3.png]]
*The gradient is scaled by the NDCG change from swapping a pair of items.*

This makes the optimizer push harder on pairs whose swap would change the top of the ranking, where NDCG is most sensitive, and ignore pairs deep in the list where the metric is flat.

**Related:** [[ranknet|RankNet]] · [[ndcg|NDCG]] · ...
```

The image sits between the paragraph that introduces the gradient-scaling mechanism and the paragraph that explains its consequence — right where the diagram clarifies the surrounding text.

**Images and tables do not appear in the YAML frontmatter, in the description, in aliases, or in the Related footer** — only in the body prose. Image embeds and recreated table lines are display elements and do not count toward the prose-length judgment (see Body Structure).

### Captions

Every image embed has a caption directly below it — **never omit it**, even when the surrounding prose already explains the figure. **Captions are brief and always italicized.** The same caption rule applies to recreated Markdown tables (see *Body Structure → Markdown tables*); a table's caption sits on the line immediately below the table, same format as an image caption.

Describe what the figure or table shows in standalone form — no source-relative figure/table numbers (`Figure 3`, `Table 2`), no source attribution (`from Burges (2010)`).

**Formatting — no wikilinks, no markdown formatting; LaTeX is allowed.** Wikilink syntax (`[[...]]`) and markdown formatting (`**bold**`, `*italic*`, backtick code) clutter the caption's role as a one-line self-description and conflict with the outer italic styling. LaTeX math is fine — `$\alpha$`, `$|\Delta\text{NDCG}|$`, `$O(n \log n)$` — when the caption refers to a quantity the figure or table depicts symbolically. Entity names that would be wikilinked in body prose stay bare in the caption; terms that would be emphasized with `**bold**` or `*italic*` in body prose stay plain in the caption (LaTeX symbols are the only inline markup allowed). Work titles and Latin binomials that would be italicized in body prose also stay plain in captions — the no-formatting rule overrides typographic convention here, in the same trade-off as wikilink display labels (see binomial Limitation under Italic pattern 7).

**Style.** A one-line sentence wrapped in `*...*` (italic) **on the line immediately below the embed (or the table), with no blank line between them** — the embed-and-caption (or table-and-caption) form one visual unit, with blank lines above and below to separate the unit from surrounding prose. Example: `*The gradient is scaled by $|\Delta\text{NDCG}|$ — the NDCG change from swapping a pair of items.*`.
