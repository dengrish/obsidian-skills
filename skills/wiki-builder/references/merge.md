# Merge Logic — integration, frontmatter, no-op merges, stub promotion, conflicts

> **When to read this:** Read this as soon as step 3 reports any match. If a run is all creates and no merges, you never need this file.

---

## Merge Logic

The merge case (existing entry + new source) is the most consequential and the easiest to get wrong. Read this section carefully.

### Integration principle

When a new source covers an entity that already has a wiki entry, the new information is **integrated into the existing body to produce a unified, coherent note**, not appended as source-specific paragraphs. The merged entry reads as if a single author wrote it with knowledge of all contributing sources, organized by the entity's logical structure (what it is, how it works, important details, related concepts), not by the chronology of when each source was added.

The body may be rewritten as needed:
- **Existing prose may be rephrased, reorganized, or replaced** when integration improves coherence.
- **The opening sentence may be updated** if the new source provides a meaningfully better canonical statement — but only if better. Don't change the opening sentence just for the sake of change.
- **New facts are woven into the appropriate part of the existing structure**, not bolted on at the end.
- **Body length after integration follows the same guidance as fresh entries** — the shortest body that explains the entity clearly, under the same example and sentence-length discipline (Body Structure length rule; prose principles 6, 7 and 9). If integration pushes the entry beyond its proper scope (covering several distinct things, not just adding depth to one), surface this to the user in the run report rather than letting it sprawl unnoticed.
- **The merge produces a single coherent body, never two stacked bodies.** A failure mode worth naming: writing the new source's body in full and appending it after the existing body, producing an entry with two opening sentences, two duplicated explanations of the same mechanism, and (if the merge step's serialization is sloppy) a stray fragment of YAML frontmatter wedged between them. This is **not a merge** — it is a concatenation that violates the Integration principle. The diagnostic shapes to watch for in the output: two `**Title**` bold-on-first-occurrence markers in the same body; two paragraphs that both open with "X is a Y that …" for the same X; any line in the body that looks like a YAML key (`description:`, `created:`, `updated:`, `tags:`, `title:`, `type:`, `aliases:`, `sources:`, `parents:`), a stray bare digit on its own line, or a stray `---` fence anywhere in the body content **other than the legitimate horizontal-rule separator between the Related footer and the `## Flashcards` heading** (see *Flashcards* (`references/flashcards-and-emphasis.md` §4) — that one `---` is required and is not a failure shape). The merge must produce **one** body where the new source's information is woven in alongside the existing prose. If after writing the merged body you can spot two of any of these duplicated landmarks, the merge has failed and the body needs to be rewritten as a unified whole.

### Frontmatter and Related footer

**Frontmatter and Related footer changes on merge are conservative.** They're metadata and curation records, not narrative — list-valued fields are append-only (each entry on the list represents a real connection the original source saw, and removing it would lose that signal), and single-value fields are updated only when the new source justifies a change:

1. **Frontmatter `sources:`** — append the new source to the list **only if it is not already present**. Compare the full wikilink string for the duplicate check, including the `#page=N` anchor for PDFs — `[[Foo.pdf#page=4]]` and `[[Foo.pdf#page=7]]` are different anchors of the same source, so both can appear (a re-run that re-reads the source and picks the same introducing page produces `[[Foo.pdf#page=4]]` already in the list, which is the duplicate-skip case; a re-run that picks a different introducing page on this run is the rarer signal-of-drift case — surface in *Notes for the user* rather than appending the second anchor silently). For PDF sources, include the `#page=N` anchor pointing at the physical page within *this* PDF where the entity is introduced (set per entity, since one source contributes to many entries). For markdown sources, no anchor — the duplicate check is plain string equality on the wikilink. **Two exceptions, both replacements rather than appends:** (a) if the existing entry is a stub (`sources: ["stub"]`), the `"stub"` marker is replaced rather than appended alongside — see "Stub promotion" below; (b) if the incoming PDF and an existing `.md` citation are a **confirmed PDF/summary pair**, replace that summary citation with the PDF link. Establish the pairing from the markdown note's decoded `sources:` (or legacy `source:`), using the source-identity rules in `SKILL.md` step 1. **A shared stem alone never authorizes replacement:** a URL-origin clipping is an independent source even when its filename matches the PDF, so keep that `.md` citation and append the PDF normally. Missing, malformed, or conflicting origin metadata leaves the pairing unresolved; preserve both references and report the uncertainty. For a confirmed pair, the PDF carries the entity's `#page=N` anchor; note the replacement in *Review-pass fixes*. The helpers' `4-duplicate-source` / `item4/source-identity` findings request provenance review, not deletion.
2. **Frontmatter `updated:`** — set to today. Any change at all fires it: a `sources:` append, a new alias, a reworded description, a footer link. It is the broadest trigger in this section, and deliberately broader than the `read:` reset below — see *The `read:` reset*, which is a different test over a narrower set of merges.
3. **Frontmatter `aliases:`** — append any new aliases observed in the new source **only if they are not already present** (compare against existing aliases on the slugged form, which is what `aliases:` stores). Duplicate aliases — same string on the list twice, or two spellings differing only in case/normalization — are silent corruption that item 18 of the Quality Checklist now also catches mechanically (`lint_entry.py`'s `18-alias-duplicate`); dedupe at the point of append so the duplicate is never written at all.
4. **Frontmatter `tags:`** — preserved on full-entry merges, growing additively. Existing discipline tags are never removed, and a single source's disagreement on the disciplinary home is not grounds for dropping a tag; the existing assignment stands. **What can change:** (a) **Blank → populated:** if the original full entry left `tags:` blank and the new source establishes a canonical home, populate it. (b) **Add a discipline:** if the new source establishes that the entity is *also* canonically a primary topic in a discipline not yet tagged (the canonical-home test — not mere use), **add** that tag alongside the existing ones — tags grow as later sources reveal additional homes. Add conservatively: only when the new source genuinely establishes a new canonical home, not whenever a source's field merely touches the entity. (c) **Stub promotion** (legacy stubs only): a stub's provisional tags may be *revised* (re-derived from the body) — see *Stub promotion* below. **Removing a tag from a full entry never happens** outside stub promotion — once a discipline has been recorded on a full entry, it stays.
5. **Frontmatter `importance:`** — **left exactly as found.** The field is no longer part of the schema (see *The entry* in `SKILL.md`): new entries never write the key, and legacy entries that carry it keep it, untouched, at whatever value is recorded. Same treatment as `parents:` — not this skill's field to write, revise, or strip, and its presence is never a violation. This is a one-line preserve rule, not a migration: a merge that rewrites an entry's whole body still leaves its `importance:` line exactly where it was.
6. **Frontmatter `description:`** — rewritten if the new source enables a meaningfully better description (more accurate, more informative, better grammatical structure) or if the existing one has a specific defect (vague, factually wrong, missing entity-as-subject, over 110 chars, contains forbidden formatting like LaTeX/wikilinks/markdown). Don't rewrite for stylistic preference alone. See the description field definition.
7. **`**Related:**` footer** — **additive**: preserve every wikilink already present, add new wikilinks for entities the new source's own text introduces, never remove an existing wikilink (each represents a connection a previous source saw). **A bare mention that was already in the body is not support for a footer entry.** It may be one `wiki-linter` pruned as too weak — a prune drops the body link to bare text and its footer line together — so re-adding the footer line here restores half of a link this run never judged, for the next lint to prune again, with `updated:` moving both times. Left alone it stays `wiki-linter`'s to backfill under its own bar (`CONVENTIONS.md` §9). No minimum count applies (see *The Related footer*, writing.md §2); the soft upper bound (same section) still applies: a fresh-entry guideline of ~8 doesn't constrain merge growth — a merged entry can exceed that when the new source genuinely pulls in distinct related entries. Past ~12 across multiple merges, surface in the run report rather than pruning unilaterally.

**Images on merge are preserved almost without exception, and the default move is *addition*, not *replacement*.** Existing images stay — even when the body prose is reorganized or rewritten. If paragraphs are restructured, the image moves to sit next to whatever prose now illustrates its content. **If a rewrite would remove the prose that motivates an image, do not remove the image** — write new prose nearby that motivates it instead, so the image+caption+motivating-prose unit remains coherent. **New images from the new source are added inline next to their motivating prose by default** — held to the same use-by-default rule as fresh entries (see *Images* selection rule: a figure is placed unless it adds no information, or unless another retained figure already covers the same specific aspect more completely). An entry can carry several images from several sources; the 1:1 image-to-motivating-paragraph rule under *Images* (`references/media.md`) is what governs how many are appropriate, not a single-image-per-entry cap.

**The one sanctioned removal case — replacement — is rare and narrowly scoped.** An existing image is replaced only when the new image **depicts the same specific aspect** of the entity as the existing one *and* conveys strictly more information about that aspect (a more complete diagram of the same mechanism, a higher-resolution figure of the same structure, one that adds dimensions the old figure lacked). "Same specific aspect" is hardened: it means the new image shows the same mechanism, the same structure, the same diagram-type — not merely "the same broader subject." Two figures from the same source on the same entity that depict *different aspects* of that entity are both retained, not collapsed by replacement.

**Worked counter-example: `Reinforcement learning`.** A `Reinforcement learning` entry built from one source carries `fig_1-12.png` — the canonical agent→action→reward→policy-update loop. On merge with a second source that introduces `fig_19-1.png` — a panel showing five RL *application examples* (a robot, an Atari agent, a board-game player, a thermostat, a trader) — the wrong move is to replace the loop diagram with the applications panel. The two figures depict *different aspects* of RL: the loop shows the entity's defining **mechanism**, the applications panel shows its **scope of use**. Neither subsumes the other. The correct merge **keeps both**, each next to the paragraph it motivates (the loop next to the paragraph defining how RL works; the applications panel next to the paragraph enumerating where RL is applied). The diagnostic for this failure shape: if the existing image was about "how it works" and the new image is about "what it's used for" (or vice versa), they are not the same specific aspect — replacement is wrong, addition is right. The same diagnostic applies to architecture-vs-training, structure-vs-function, mechanism-vs-application, and similar pairings within one entity.

**Tables on merge follow the same rules as images, including the addition-as-default principle.** Existing recreated tables in the body are preserved across body rewrites — moved to sit next to whatever prose now motivates them; if a rewrite would remove the motivating prose, write new motivating prose instead of removing the table. **New tables** from the new source are *added* inline next to motivating prose when the source presents data tabularly and a recreated Markdown table serves the merged entry better than prose or bullets — same selection criterion as fresh entries (see the Body Structure tables rule). **Sanctioned replacement is narrow:** an existing table is replaced only when the new source presents *the same data* more completely (more rows, more columns that earn their place, corrections, better headers) — not merely *related data on the same broader topic*. Two tables that present different cuts of an entity's data — say, a parameter table and a performance-comparison table — are both retained, not collapsed.

**Equations on merge follow the images/tables pattern, with two equation-specific points** (`references/equations.md` §4). Existing equations are preserved across body rewrites and move with their motivating prose. A **nonconforming existing equation** — off-standard symbols, a defining equation carried inline — **is normalized** to the equation policy, with every prose reference to a renamed symbol updated in the same edit: that is a format fix, so `updated:` bumps and `read:` does not reset. A **new equation added where the body had none** — including one typeset from a calculation the new source only describes in words — **is body content** and resets `read: false`, exactly as a new figure does. Replacement is narrower still: it happens only when the new source states the *same quantity* more completely, i.e. additional equivalent forms, folded into one `\begin{aligned}` block per *Multi-form equations* (`references/edge-cases.md`); different quantities get their own display blocks, both kept.

**Headings on merge follow the general body-rewrite rules**, not the image/table preservation rules. Unlike images and tables, which are display elements that should be preserved unless replaced with something strictly more informative, headings are organizational structure — they're part of the body's narrative organization, not a separate display layer. The merge author decides whether the merged entry needs headings, regardless of whether the existing entry had them: a flat-prose entry can gain `##` headings on merge if new content makes the entry hit the headings threshold (see the Headings sub-bullet under Body Structure); an entry with headings can become flat prose if integration produces a more coherent unified body without them; existing heading text can be rewritten, renamed, or reordered to fit the integrated structure. The Headings rule applies to the merged result — most entries still don't need headings; use them only when the merged entry covers genuinely distinct sub-aspects that can't be split into separate entries. If integration pushes the entry to need headings *and* the subsections would each make coherent standalone entries, surface to the run report (split candidate) rather than adopting headings as a workaround for what should be a split.

**Flashcards on merge.** The `## Flashcards` section is **revisited on regular merges, preserved on no-op merges**. The contract:

- **No-op merges** (per *Merge Logic → No-op merges*): the entire Flashcards section is preserved unchanged — same cards, same lines 1–3, same line 4+ metadata.
- **Regular merges, per existing card.** For each flashcard already in the section: if the entry's main claim has changed substantively on integration (the rewritten body's opening sentence differs in *content*, not just phrasing), re-derive line 1 from the new main claim; replace the existing line 1 only if the new definition is meaningfully more accurate or unambiguous than the existing one (same threshold as the `description:` field's rewrite criterion). Line 3 (the term) follows the title field and the acronym ↔ full-form alias pair — it updates if the title itself changes (rare; typically happens via the *Acronym-vs-full-form coherence rule* fixing a prior incoherence), **or** if an acronym ↔ full-form counterpart is added to or removed from `aliases:` on this merge, in which case the parenthetical is added, updated, or dropped to match (see *`references/flashcards-and-emphasis.md` §4, line 3* for the full rule). Line 2 (`??` or `!!`) is preserved verbatim on merge — the skill never converts between the two forms. `!!` is the user's manual disable marker (see the line-2 sub-bullet under *Flashcards* (`references/flashcards-and-emphasis.md` §4) for the convention); if the user has hand-edited a card's `??` to `!!`, the merge leaves it as `!!`. **Why the high replacement bar:** line 4+ is review history attached to a specific card by position; rewriting lines 1–3 for stylistic improvement risks the review history becoming attached to a card whose definition has drifted from what the user originally rated. Minor wording drift between the body and a flashcard is acceptable; review-metadata continuity is the load-bearing concern. The "meaningfully better" threshold accepts that the flashcard's wording may lag the body's by one merge cycle in exchange for stable review metadata.
- **Line 4+ preservation.** Per-card review metadata appended by the Obsidian Spaced Repetition plugin (line 4's `<!--SR:…-->` comment, and any subsequent lines that plugin writes) is **preserved verbatim on every merge** — wiki-builder does not write, modify, or remove these lines, even when lines 1–3 of the same card are revised. That metadata is about the card's review history (scheduling, difficulty, last-review-date), independent of the specific definition phrasing, so it survives wording refinements. If the term itself (line 3) changes on a merge — the rare title-rename case — the prior line 4+ is still preserved alongside the renamed card; the Spaced Repetition plugin is responsible for deciding on its next pass whether prior review history still applies to a renamed card.
- **No new cards on merge — ever.** One card per entry, hard rule (*Flashcards*, `references/flashcards-and-emphasis.md` §4). A merge that surfaces a second term seeming to warrant its own card has surfaced a **split**, not a card: create an entry for that term if the new source actually introduces it (the new entry carries its own single card), and leave this entry's section at one card. A facet is entry-worthy only when a **cited source** introduces it — background knowledge never adds a term, claim, or card the sources don't contain. The corpus failure this rule closes: a chapter-2 merge appended a second card quizzing *concept drift* onto the *Data drift* entry when neither cited chapter mentions that term.
- **Removing cards on merge — only with explicit justification.** Existing flashcards are preserved by default. The narrow case for removal: a card's definition was based on a body claim that the merge has *corrected* (per the *Conflict handling* rule), and the card now contradicts the corrected body. In this case, re-derive lines 1–3 in place (don't remove and re-add) so the line 4+ metadata stays attached. Outright removal is otherwise justified only for a **legacy extra card** (a section holding more than one card — item 19 caps it at one): keep the card whose line 3 is the entry's title — the **base term**, for a parenthetical-disambiguated title (`Feature`, not `Feature (machine learning)`; item 19) — remove the rest, and surface every removed card verbatim in the run report's *Notes for the user*.

The `parents:` field is preserved as-is on merge — see the `parents` field definition.

### The `read:` reset

`read:` is the user's review checkbox (see the `read` field definition), and a merge is the only thing in this skill that touches it after creation. **Set it to `false` when, and only when, the merge adds content to the body:** new prose, a new paragraph, a new image or recreated table, a newly typeset equation, a rewritten explanation, or a stub promoted to a full entry — whose body is written from scratch, so all of it is new to the reader. Those are the merges that put something in front of the user they have not read.

**Every other merge leaves the value exactly as it is.** Appending to `sources:`, appending an alias, adding a Related-footer link, rewording `description:`, adding or correcting a `tags:` value, leaving a legacy `importance:` in place, and any format fix step 7's review pass makes: none of them is a sentence the user has to read, so none of them clears the checkbox.

**This is narrower than the `updated:` bump, and the two are independent tests.** Every reset comes with a bump — content added to the body is a change — but a bump implies nothing about the reset: a merge can change the entry, and so move the date, without changing what there is to read. The two fields answer different questions: `updated:` records that the entry changed, `read:` records whether the user still has to look at it. Conflating them turns the checkbox into a second copy of the date, at which point it carries no information the date doesn't and the user stops reading it.

**When the call is genuinely close, do not reset.** The two errors are not symmetric. A false reset makes the user re-read a note they had already read, and a checkbox that clears itself for reasons they can't see is one they stop trusting — which costs the field its whole purpose, permanently. A false non-reset costs them one glance the next time they open the note, which they were going to do anyway. **Say which way a close call went in the run report**, including the calls that went to *no reset*: the report is where a judgment this skill made about the user's own field gets checked.

### No-op merges

Not every merge produces a change. A **no-op merge** is the case where a candidate passes step 2's filters (the substance test for any source, and additionally the durability test for secondary sources — the new source said something substantive *and* durable about the entity) but, on integration, every claim the candidate makes is already covered by the existing entry's body — verbatim or as a clear paraphrase — and the new source contributes no new figures, tables, or equations either. This is the common shape on re-runs of a previously-processed source that proceeded under explicit re-run intent (step 1's default-skip rule routes most re-runs to the no-modifications path before this rule applies — re-runs that *do* reach merge logic are the deliberate ones, and most of their merges will be no-ops); it also occasionally happens with genuinely new sources that elaborate the entity but don't go beyond existing coverage.

**The check, applied after extracting the candidate's content and before rewriting the body:** for each fact in the candidate, ask whether the claim is already present in the existing entry's body (verbatim or as a clear paraphrase). For each candidate figure, table, or equation, check whether the existing entry already embeds the same figure (same `Sources/Images/` filename), recreates the same table, or typesets the same equation — the same quantity's definition, where a difference of notation alone does not make it new. If *every* candidate fact, figure, table, and equation is already covered, this is a no-op merge. On a source that proceeded under explicit re-run intent (step 1's default-skip rule was overridden), the default expectation is that most merges will be no-ops — apply the check, but bias toward the no-op call when the source filename matches a previously-processed run; the per-fact check still runs.

**No-op merges skip the body and metadata rewrites:**

- **Body rewrite — skipped.** The existing body is preserved exactly as it was. No re-integration, no phrasing churn, no opening-sentence change. This is the load-bearing skip — preserving prior careful body edits is the main reason no-op merges exist as a separate case.
- **`description:` rewrite — skipped (for new-content-driven rewrites).** By definition the new source added no net-new content, so the "new source enables a meaningfully better description" trigger doesn't fire. *Pre-existing defects* in the description (vague, over 110 chars, missing entity-as-subject, forbidden formatting per the description field's rewrite criteria) are still caught by step 7's Quality Checklist on the same pass and fixed there — the no-op-merge skip applies to *new-content-driven* rewrites, not to defect-driven fixes that the QC review would catch regardless of merge type.
- **Flashcards rewrite — skipped.** The `## Flashcards` section is preserved unchanged — same cards, same lines 1–3, same line 4+ metadata. See *Flashcards on merge* above for the full rule (no-op is the explicit preserve-as-is case).
- **`updated:` bump — skipped if and only if nothing in the entry actually changes during the merge.** If the `sources:` or `aliases:` appends above introduce a genuinely new value (uncommon on a re-run but possible — e.g., a re-read produces a different introducing page anchor, or the source uses a surface form not previously aliased), the entry did change, and `updated:` bumps to today as usual. If both appends are idempotent under the dedupe rule (the typical re-run case), nothing changed and `updated:` stays at its prior date.
- **`read:` reset — never fires on a no-op merge.** The body is preserved exactly, so the reset's one trigger — content added to the body — cannot have happened. This holds even in the rare case above where a genuinely new `sources:` or `aliases:` value does move `updated:`: the entry changed, and the user still has nothing new to read. That case is the cleanest demonstration that the two rules are independent, and a no-op merge that clears the checkbox has given the user a re-read in exchange for nothing.

**The Related footer is not extended on a no-op merge.** Adding a link is a content change, which would force `updated:` to today under the rule below and collapse the whole no-op path — the two rules cannot both apply, and preserving the entry is the one that matters. A no-op merge means the new source told this entry nothing it didn't know, so it has earned no new neighbours either; if the footer genuinely should grow, that is a signal the merge was not a no-op. **No-op merges still run the other per-field append/preserve rules above (`sources:`, `aliases:`, `tags:`), with their normal dedupe behavior** — the `sources:` and `aliases:` appends are idempotent on a re-run, and the `updated:` rule above governs the rare genuinely-new-value case. `tags:`, `parents:` and any legacy `importance:` are unchanged from the regular-merge case.

**Step 7 (review and report) still fires on no-op-merged entries.** Even when the merge itself produces no body changes, the per-file Quality Checklist review and the step-7 audits run on the entry — this catches pre-existing defects (description over 110 chars, missing wikilink targets, alias collisions, etc.) that the no-op skip didn't address. Step 7's review is cheap and the safety benefit outweighs the cost. Re-running with the same source after fixing a skill bug is a legitimate use case precisely because step 7's review still fires and applies the skill's current rules to every touched entry.

**Run report log:** no-op merges are logged as a separate bullet from regular merges in step 7's run report — `Entries no-op-merged: N (existing body already covered the new source's content)`. `updated:` is unchanged on these unless a genuinely new `sources:` or `aliases:` value was appended, per the `updated:` bullet above; when that happens, say so in the bullet rather than leaving the reader with a blanket claim that nothing moved. They are *not* counted in the regular `Existing entries merged: …` bullet. A re-run where every merge turns out to be a no-op produces a report dominated by the no-op bullet — the right signal that "nothing changed, the wiki is in the same state the previous run left it in."

**Edge case — partial no-op.** A merge where *most* candidate facts are already covered but one or two are net-new is a *regular* merge, not a no-op. The skip applies only when *every* candidate fact, figure, and table is already covered. If you find yourself wanting to call something a no-op despite one net-new fact, integrate the new fact properly — the gain in honesty outweighs the cost of a few sentences of body work. The no-op classification is binary at the entry level: a merge is either fully no-op (all candidate content already present) or a regular merge.

**A merge that adds a new image, recreated table, or newly typeset equation** (with its motivating prose) IS a content change, not a no-op — even when no new textual facts are introduced, and it resets `read:` for the same reason: a figure, a table, or an equation is something the reader has not seen. Candidates that fail step 2's filters never reach merge logic: thin-mention candidates rejected by the substance test (b) and transient-signal candidates from secondary sources rejected by the durability test (c) are both filtered earlier — see *"Both (b) and (c) gate merges, not just creates"* in step 2.

### Net-new fact test

Before integrating content from the new source, ask: "Does the existing body already say this, possibly in different words?" If yes, the fact is a duplicate; the new source still gets recorded in `sources:` but the body need not change for that fact. If no, the fact is net-new and is woven into the body in the appropriate place — not appended as a separate paragraph unless the body's structure genuinely calls for one. Examples:

- Existing: "LambdaRank scales pairwise gradients by $\Delta\text{NDCG}$." / New source: "LambdaRank weights pairs by the NDCG change from swapping them." → **duplicate**, no body change.
- Existing body has no mention of LambdaLoss. / New source: "LambdaLoss later proved that LambdaRank's gradients correspond to a specific loss function." → **net-new**, integrate where the existing entry discusses empirical behavior — extending the relevant paragraph rather than adding a trailing one.

The output is a coherent body, not a body-plus-addendum.

### Stub promotion

Stubs are **legacy artifacts**: this skill no longer creates them (see *Stubs (legacy)* in `SKILL.md`), but vaults built by earlier versions still contain them, and a candidate can resolve to one through the ordinary collision probes. When the existing entry being merged into is a stub (its `sources:` field contains only the string `"stub"`), the merge has one mechanical exception to the ordinary merge rules: **`sources:`** — the `"stub"` marker is **replaced** by the new source wikilink, not appended alongside. **This is one of only two cases in the entire skill where `sources:` is mutated by replacement rather than append**; the other is the PDF-over-note replacement in the `sources:` rule above — its exception (b), the Quality Checklist item-4 case — which can fire on a stub promotion and a full-entry merge alike.

The Integration principle and the frontmatter/Related-footer rules above otherwise apply unchanged; the bullets below note how a few of them play out specifically from the stub's minimal starting state:

- **Body:** the stub's one-sentence body is fully replaced by an integrated body written from the new source. With only a single sentence to integrate against, this is effectively a fresh creation — write per the Body Structure rule (the shortest body that explains the entity clearly).
- **Description:** rewritten if the new source enables a meaningfully better one; otherwise preserved.
- **`tags:`** — the stub's inherited best-guess tags are re-evaluated against the body that gets written. Tags the body doesn't support are dropped, and disciplines the body establishes as canonical homes are added; tags the body confirms are kept. This is the one place in the skill where a full entry's `tags:` can lose a value on merge — a stub's tags are provisional.
- **Related footer:** created in this step (stubs have no Related footer; promoted entries do). Include the natural neighbors the entity has — no minimum count — per *The Related footer* rule (writing.md §2).
- **`## Flashcards` section:** created in this step (stubs have no Flashcards section; promoted entries do). Write the entry's one flashcard per *Flashcards* (`references/flashcards-and-emphasis.md` §4) — exactly one, the hard rule — covering the promoted entry's main claim, with lines 1–3 written by this skill (the Spaced Repetition plugin will append line 4 on its next pass).
- **`updated:`** bumped to today.
- **`read:`** reset to `false`. Promotion replaces the stub's single placeholder sentence with a body written from scratch, so every word of the entry is new to the reader — this is the one merge shape where the reset is never a close call, whatever the stub's checkbox said before.

After promotion, the entry is a normal entry. Future merges follow the ordinary Integration principle.

### Conflict handling

If the new source **contradicts** a fact in the existing body, resolve the disagreement using your own knowledge and judgment — pick the claim that is better-supported by the broader literature, more recent and more authoritative work, or simply more correct. Then write the resolved understanding into the integrated body as ordinary prose without source-meta phrasings: no "Wang et al. (2018) report that...", no "contradicting Burges' original characterization", no "while some sources say X, others say Y." The entry describes the subject as you understand it to be, not the trail of disagreements that produced that understanding (prose principle 5(a) applies here too).

**Contested-topic exemption.** For entries on philosophical positions, historical interpretations, religious doctrines, schools of thought, or other topics where competing views legitimately coexist and "pick the better-supported claim" doesn't apply, present the major views as parallel rather than picking one. This is the one place where prose principle 5(a)'s "no source-meta phrasings" prohibition relaxes (the exemption itself is housed as prose principle 5(g)): phrasings like "the materialist reading argues X, while the dualist reading argues Y," or "historians disagree on whether the war's primary cause was economic or ideological," or "the Stoic and Epicurean traditions differ in their account of …" are appropriate here, because the disagreement is itself part of the subject. The exemption applies in two settings: (a) fresh entries on subjects where contested interpretation is intrinsic to what the subject *is*, and (b) merges where the new source's "conflict" with the existing body turns out to reflect a legitimate alternative view rather than an error to resolve. **Topics outside the exemption — scientific facts with unsettled disputes, or topics where one view is well-established and another is fringe — fall back to the default-rule mechanics below**: dispute-resolution by your own judgment for unsettled science (the well-established view stands and the fringe view is omitted or briefly noted as fringe).

**Default-rule mechanics** (for non-contested topics — the Contested-topic exemption above governs contested ones):

- **Existing body correct, new source wrong** — keep the existing claim; the rest of the new source's net-new facts are still integrated, and the new source is still recorded in `sources:`. Note the filtered contested claim in the run report.
- **New source correct, existing body wrong** — replace the wrong claim with the corrected understanding in-place. Note the corrected claim in the run report.
- **Both partial truth** — write the synthesized claim in-place, without attributing the synthesis to any source.

In all cases, the entry reads as a single coherent description of its subject, not a transcript of who said what.

**Limitation: conflict detection is per-merge** — it triggers when a new source contradicts the existing body of an entry being merged into. Two existing wiki entries that contradict each other are not surfaced by this skill (no comparison is happening between them on any given run). If you happen to notice such a contradiction while reviewing or while writing related entries, flag it in the run report's *Notes for the user* — but resolving it is out of scope (it's wiki refactoring).
