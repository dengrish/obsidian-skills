# Merge Logic — integration, frontmatter, source-no-op merges, stub promotion, conflicts

> **When to read this:** Read this as soon as step 3 reports any match. If a run is all creates and no merges, you never need this file.

---

## Collision decisions

Probes (a)–(e) run against **both filename stems and every entry's `aliases:` list**:

- **(a) basic slug equality** — the candidate slug compared as-is, untransformed.
- **(b) µ-variant** — if the title contains microsign `µ` (U+00B5) or Greek mu `μ` (U+03BC), both variants are probed.
- **(c) singular/plural** — plural and singular forms probed (`neural-network` against `neural-networks.md`). The shared inflection helper covers regular forms and the maintained irregular table (including scientific forms such as `archaeon`/`archaea`, `fungus`/`fungi`, `protozoan`/`protozoa`, and `mitochondrion`/`mitochondria`); do not reimplement the table in a skill script.
- **(d) hyphenation-collapse** — all hyphens stripped from both sides, then compared (`cross-validation` against `crossvalidation.md`, `out-of-bag` against `outofbag.md`).
- **(e) word-order-permutation** — both slugs tokenized on `-` and sorted alphabetically, then compared (`forward-feed` against `feed-forward.md`). **Tokens are singularized before sorting** — without that step `weight-tying` and `tying-weights` slip past on `weights` ≠ `weight`.

**When adjudication confirms a genuine duplicate**, route the incoming candidate to one canonical entry — typically the form the literature uses more often — and add the candidate's alternate slug as an alias. This does not authorize merging or deleting two pre-existing files; that remains a refactoring proposal.

**`ls` cannot run these probes** — half of what they compare lives inside the files. A source covering "true positive rate" finds no filename match, never learns `recall.md` already claims that alias, and writes a duplicate that splits inbound links between the two.

**Probes (a) and (b) are decisive only when they identify one existing owner: a unique match is a merge** — (b) only fires on the two µ codepoints, which are the same character in practice. If several existing files claim those matches, the verdict stays `adjudicate`; resolve the destination before merging, never choose a file by index order. **The rest — (c), (d), (e), and the two probes described below, (f) stem-morphology and (g) token-superset — are signals, not verdicts** — they surface a candidate for *your* adjudication. This matters: `Weight tying` and `Tying weights` fire probe (e) and are two different techniques from two different papers; auto-merging would fuse them and lose both. The script also probes **candidates against each other**, which the five probes alone don't — one paper yielding both "masked language model" and "masked language modeling" would otherwise write two files.

If adjudication identifies distinct techniques with confusable surface forms, read [same-surface-form handling](edge-cases.md#same-surface-form-different-technique) before choosing titles or aliases. Any rename of a pre-existing entry remains a refactoring proposal.

**A sixth probe, (f) stem-morphology, catches gerund-vs-noun and morphological pairs** (`tokenization` vs `tokenize`, `masked-language-model` vs `masked-language-modeling`). It is on by default and always returns `adjudicate`, never `merge` — deliberately, because it fires on process/tool/unit triples the schema wants kept apart (`tokenization` / `tokenizer` / `token` are three different entities). `--no-stem` disables it. Treat a probe-(f) hit as a question, not a duplicate.

**A seventh probe, (g) token-superset, catches a candidate that merely extends an existing slug by a token or two** — every probe above compares whole token sets, so "K-means clustering" against `k-means.md`, or "Gradient descent" against `stochastic-gradient-descent.md`, fires nothing and ships a duplicate. After (f)'s stemming and singularizing, (g) fires when one slug's token set is a *proper* subset of the other's with at most two extra tokens; like the others it runs against filenames, aliases, and the run's candidates against each other, and like (f) it always returns `adjudicate`, never `merge` — a qualified title beside its base term is often two entities on purpose. `--no-superset` disables it, as `--no-stem` does (f). It is deliberately a **create-time probe only**, implemented in `find_collisions.py` and not mirrored in `wiki-lint`'s vault-wide sweep: qualified-vs-base pairs (`feature-machine-learning` beside `machine-learning`) are exactly what the disambiguation rules produce on purpose, so a whole-vault pass would flood on legitimate pairs — the pairs already in the vault were adjudicated when they were created.

An empty new wiki has no existing-entry collisions; candidates are still probed against each other. Index problems keep unmatched candidates at `adjudicate`, since an unreadable or malformed entry may conceal an alias. Resolve those problems before treating absence of a match as permission to create.

## Merge Logic

The merge case (existing entry + new source) is the most consequential and the easiest to get wrong. Read this section carefully. A correction based only on sources the entry already cites is instead wiki-lint's [source-backed correction mode](../../wiki-lint/references/source-backed-corrections.md).

### Integration principle

When a new source covers an entity that already has a wiki entry, the new information is **integrated into the existing body to produce a unified, coherent note**, not appended as source-specific paragraphs. The merged entry reads as if a single author wrote it with knowledge of all contributing sources, organized by the entity's logical structure (what it is, how it works, important details, related concepts), not by the chronology of when each source was added.

The body may be rewritten as needed:
- **Existing prose may be rephrased or reorganized** when integration improves
  coherence, but the rewrite preserves every substantive existing claim unless
  the inspected sources justify a correction under *Conflict handling*. The
  current note is merge input in its own right: an uncited hand edit is not
  disposable merely because its provenance is unclear. If its relationship to
  the new source cannot be resolved safely, preserve it and report the conflict.
- **The opening sentence may be updated** if the new source provides a meaningfully better canonical statement — but only if better. Don't change the opening sentence just for the sake of change.
- **New facts are woven into the appropriate part of the existing structure**, not bolted on at the end. Before inserting them, give each affected paragraph a short phrase naming its controlling idea. Extend a paragraph only when the new claim advances that idea by defining, explaining, supporting, qualifying, contrasting, exemplifying, or drawing a consequence from it; a shared noun is not enough. Otherwise split or reorder the affected prose, or start an adjacent paragraph for the new facet. Re-read the changed paragraph and both neighboring boundaries so integration does not create an abrupt pivot.
- **A sentence rewrite does not create link provenance.** When integration rephrases or moves a carried-over claim, targets mentioned only by that old claim remain carried over too. Link a target on merge only when the active source introduces it or contributes a substantive relationship to it. A later source can supply genuinely new evidence for a target wiki-lint previously pruned; that source-backed relationship may be linked and reported, but rewrite mechanics alone never restore it.
- **Body scope after integration follows the same atomicity guidance as fresh entries.** There is no size target: integrate every relevant fact needed to explain this entity clearly, under the [scope, paragraph-flow, example, and sentence guidance](writing.md#2-the-body). Do not add an optional example or image merely because the new source supplies one. A distinct concept taught substantively by the new source is a separate candidate and linked entry; pre-existing off-scope content is not silently moved or deleted during this merge, but is reported as a refactoring proposal.
- **`Software` API permission remains selective on merge.** Reapply the step-2 substance gate before treating a library mention as a contribution: a source that uses the artifact to teach another concept, or lists the classes and settings used, does not teach the software itself and earns neither body prose nor a source append. Integrate cross-cutting interface or design knowledge; omit per-algorithm catalogs, default inventories, version-history catalogs, and recipes. Another API object that merely instantiates a convention the body already explains is duplicate coverage and follows the source-no-op path.
- **The merge produces a single coherent body, never two stacked bodies.** A failure mode worth naming: writing the new source's body in full and appending it after the existing body, producing an entry with two opening sentences, two duplicated explanations of the same mechanism, and (if the merge step's serialization is sloppy) a stray fragment of YAML frontmatter wedged between them. This is **not a merge** — it is a concatenation that violates the Integration principle. The diagnostic shapes to watch for in the output: two `**Title**` bold-on-first-occurrence markers in the same body; two paragraphs that both open with "X is a Y that …" for the same X; any line in the body that looks like a YAML key (`description:`, `created:`, `updated:`, `tags:`, `title:`, `type:`, `aliases:`, `sources:`, `parents:`), a stray bare digit on its own line, or a stray `---` fence anywhere in the body content **other than the legitimate horizontal-rule separator between the Related footer and the `## Flashcards` heading** (see *Flashcards* (`references/flashcards-and-emphasis.md` §4) — that one `---` is required and is not a failure shape). The merge must produce **one** body where the new source's information is woven in alongside the existing prose. If after writing the merged body you can spot two of any of these duplicated landmarks, the merge has failed and the body needs to be rewritten as a unified whole.

### Frontmatter and Related footer

**Frontmatter and Related footer changes on merge are conservative.** They're metadata and curation records, not narrative — list-valued fields are append-only (each entry on the list represents a real connection the original source saw, and removing it would lose that signal), and single-value fields are updated only when the new source justifies a change:

1. **Frontmatter `sources:`** — follow [shared source-reference rules](../../../shared/CONVENTIONS.md#7-source-references), including full-citation deduplication and reporting a rerun's anchor drift. Append only a citation that is not already present. Replace the legacy `"stub"` marker when promoting a stub. Replace an existing Markdown summary citation with the PDF only after decoded provenance confirms that pair; a shared stem alone never authorizes replacement. Keep independent URL-origin clippings and unresolved references, reporting uncertain provenance rather than guessing. Record confirmed representation replacements in *Review-pass fixes*. A PDF citation uses the entity's introducing physical page; a Markdown citation has no anchor.
2. **Frontmatter `updated:`** — set to today. Any change at all fires it: a `sources:` append, a new alias, a reworded description, a footer link. It is the broadest trigger in this section, and deliberately broader than the `read:` reset below — see *The `read:` reset*, which is a different test over a narrower set of merges.
3. **Frontmatter `aliases:`** — append any new aliases observed in the new source **only if they are not already present** (compare against existing aliases on the slugged form, which is what `aliases:` stores). Duplicate aliases — same string on the list twice, or two spellings differing only in case/normalization — are silent corruption that item 18 of the Quality Checklist now also catches mechanically (`lint_entry.py`'s `18-alias-duplicate`); dedupe at the point of append so the duplicate is never written at all.
   A pre-existing alias that the active source shows to name a different entity is **not removed during this merge**. Report the semantic-invalid alias, the evidence, and the likely canonical owner. Removal is a separately scoped vault-wide refactor under [shared alias conventions](../../../shared/CONVENTIONS.md#4b-aliases-use-the-same-slug-rule). Route an authorized removal to `wiki-lint`'s explicit refactor mode: it rewrites resolving entry-link surfaces in Wiki bodies/Related footers, entry frontmatter such as `parents:`, and root MOCs while preserving labels and anchors; it does not alter sources, embeds, or logs on a text match. It verifies ownership and a clean re-scan before deleting the alias; no additional human sign-off is required. This does not block ordinary within-list duplicate cleanup.
4. **Frontmatter `tags:`** — preserved on full-entry merges, growing additively. Existing discipline tags are never removed, and a single source's disagreement on the disciplinary home is not grounds for dropping a tag; the existing assignment stands. **What can change:** (a) **Blank → populated:** if the original full entry left `tags:` blank and the new source establishes a canonical home, populate it. (b) **Add a discipline:** if the new source establishes that the entity is *also* canonically a primary topic in a discipline not yet tagged (the canonical-home test — not mere use), **add** that tag alongside the existing ones — tags grow as later sources reveal additional homes. Add conservatively: only when the new source genuinely establishes a new canonical home, not whenever a source's field merely touches the entity. (c) **Stub promotion** (legacy stubs only): a stub's provisional tags may be *revised* (re-derived from the body) — see *Stub promotion* below. **Removing a tag from a full entry never happens** outside stub promotion — once a discipline has been recorded on a full entry, it stays.
5. **Frontmatter `importance:`** — **left exactly as found.** The field is no longer part of the schema (see [The entry](../SKILL.md#the-entry)): new entries never write the key, and legacy entries that carry it keep it, untouched, at whatever value is recorded. Same treatment as `parents:` — not this skill's field to write, revise, or strip, and its presence is never a violation. This is a one-line preserve rule, not a migration: a merge that rewrites an entry's whole body still leaves its `importance:` line exactly where it was.
6. **Frontmatter `description:`** — rewritten if the new source enables a meaningfully better description (more accurate, more informative, better grammatical structure) or if the existing one has a specific defect (vague, factually wrong, missing entity-as-subject, over 110 chars, contains forbidden formatting like LaTeX/wikilinks/markdown). Don't rewrite for stylistic preference alone. See the description field definition.
7. **`**Related:**` footer** — **additive**: preserve every wikilink already present, add new wikilinks for entities the new source's own text introduces, never remove an existing wikilink (each represents a connection a previous source saw). **A bare mention that was already in the body is not support for a footer entry.** It may be one `wiki-lint` pruned as too weak — a prune drops the body link to bare text and its footer line together — so re-adding the footer line here restores half of a link this run never judged, for the next lint to prune again, with `updated:` moving both times. Left alone it stays `wiki-lint`'s to backfill under its own bar (`CONVENTIONS.md` §9). No minimum count applies (see *The Related footer*, writing.md §2); the soft upper bound (same section) still applies: a fresh-entry guideline of ~8 doesn't constrain merge growth — a merged entry can exceed that when the new source genuinely pulls in distinct related entries. Past ~12 across multiple merges, surface in the run report rather than pruning unilaterally.

**Images on merge: preserve existing content; select incoming figures.** Existing images and captions stay with their motivating prose, even when the body is reorganized. If that unit no longer fits a focused, atomic entry, preserve it for this run and propose consolidation or removal in the run report; do not silently delete it or invent a new tangent to justify it. New images must earn a place under the same [selection rule](media.md#selection) as fresh entries. Apply that rule before integration: a newly available image does not by itself justify a new paragraph, a wider topic, or a reset of `read:`.

**Replacement remains narrow and must be reported.** An existing image may be replaced only when the new one depicts the same specific aspect of the entity and offers strictly better explanatory value — a clearer or more complete view of the same mechanism, structure, or diagram-type, not merely the same broad subject. Name both images and the concrete benefit in the report, and preserve the underlying image files. This exception does not authorize other removal or consolidation, which stays a proposal. Different aspects do not subsume each other, but that does not make an incoming figure mandatory.

**Example: `Reinforcement learning`.** Keep an existing agent→action→reward loop diagram. An incoming gallery of robots, games, and thermostats usually adds no needed explanation of that mechanism: skip it with that reason, rather than replacing the loop or adding an applications paragraph just to include the gallery.

**Tables on merge retain their selection and preservation rules.** Existing recreated tables in the body are preserved across body rewrites — moved with the prose that motivates them; if that unit no longer fits, propose consolidation rather than silently removing user content or adding a tangent to justify it. **New tables** from the new source are *added* inline next to motivating prose when the source presents data tabularly and a recreated Markdown table serves the merged entry better than prose or bullets — same selection criterion as fresh entries (see the Body Structure tables rule). **Sanctioned replacement is narrow:** an existing table is replaced only when the new source presents *the same data* more completely (more rows, more columns that earn their place, corrections, better headers) — not merely *related data on the same broader topic*. Two tables that present different cuts of an entity's data — say, a parameter table and a performance-comparison table — are both retained, not collapsed.

**Equations on merge follow the images/tables pattern, with two equation-specific points** (`references/equations.md` §4). Existing equations are preserved across body rewrites and move with their motivating prose. A **nonconforming existing equation** — off-standard symbols, a defining equation carried inline — **is normalized** to the equation policy, with every prose reference to a renamed symbol updated in the same edit: that is a format fix, so `updated:` bumps and `read:` does not reset. A **new equation added where the body had none** — including one typeset from a calculation the new source only describes in words — **is body content** and resets `read: false`, exactly as a new figure does. Replacement is narrower still: it happens only when the new source states the *same quantity* more completely, i.e. additional equivalent forms, folded into one `\begin{aligned}` block per *Multi-form equations* (`references/edge-cases.md`); different quantities get their own display blocks, both kept.

**Headings on merge follow the general body-rewrite rules**, not the image/table preservation rules. Unlike preserved display content, headings are organizational structure — they're part of the body's narrative organization, not a separate display layer. The merge author decides whether the merged entry needs headings, regardless of whether the existing entry had them: flat prose can gain `##` headings when new content creates genuine sub-aspects of the same entity; an entry with headings can become flat prose when integration produces a more coherent flow; existing heading text can be rewritten, renamed, or reordered to fit the integrated structure. Length alone does not decide. If a new-source subsection would make a coherent standalone entry and passes the substance filter, create and link that candidate; if the same split would require redistributing pre-existing content, report the refactoring proposal rather than using headings to hide mixed scope.

**Flashcards on merge.** The `## Flashcards` section is **revisited on regular merges; source-driven rewriting is skipped on source-no-op merges**. The contract:

- **Source-no-op merges** (per *Merge Logic → Source-no-op merges*): skip source-driven card rewriting, but still run step 7's item-19 QC, including the semantic equation-coverage repair below. A conforming section remains byte-for-byte unchanged. A current-rule defect in the three content lines is fixed in place; a missing card is restored from the entry's already-established main claim with `??`; recognized scheduling state and block IDs remain verbatim.
- **Equation coverage on every merge.** Apply the canonical [line-1 coverage rule](flashcards-and-emphasis.md#line-1-equation-coverage) to every card, including a source-no-op merge and an accurate pre-existing verbal definition with unknown review history. This targeted item-19 repair adds directly supported inline math for the same tested claim, preserving the cue, answer line, and all attachments. It does not require a changed main claim or authorize other wording changes; those follow the regular-merge threshold below. A card-only repair bumps `updated:` under this skill's actual-change test and preserves `read:`.
- **Regular merges, primary card.** Identify the primary card by the canonical primary-answer contract. If the entry's main claim has changed substantively on integration (the rewritten body's opening sentence differs in *content*, not just phrasing), re-derive line 1 from the new main claim; replace the existing line 1 only if the new definition is meaningfully more accurate or unambiguous than the existing one (same threshold as the `description:` field's rewrite criterion). Line 3's term content follows the title field and its opener-established, alias-bound counterpart. Recompute that content when the title changes, when a qualifying counterpart is added to or removed from `aliases:`, **or when the opener adds, removes, or changes the direct binding that makes an already-listed alias qualify** — for example `(short for *…*)` or an italic scientific abbreviation. Add, update, or drop the parenthetical to match (see *`references/flashcards-and-emphasis.md` §4, line 3* for the three qualifying classes), without changing any attached schedule or block ID. Line 2 (`??` or `!!`) is preserved verbatim on merge — the skill never converts between the two forms. `!!` is the user's manual disable marker (see the line-2 sub-bullet under *Flashcards* (`references/flashcards-and-emphasis.md` §4) for the convention); if the user has hand-edited a card's `??` to `!!`, the merge leaves it as `!!`. **Why the high replacement bar:** a pre-existing card may have review history attached in the note or stored externally by the Spaced Repetition plugin. Rewriting the content for stylistic improvement risks changing what a learner is tested on while its prior schedule continues. Missing inline metadata does not prove the card is fresh, so the high bar applies to other wording changes on every pre-existing card. Minor wording drift between the body and a flashcard is acceptable; review-history continuity is the load-bearing concern.
- **Legacy extra cards.** Preserve each extra card's own answer and tested claim; review it against the body evidence for that claim and apply only directly supported local repairs. Do not derive its definition or answer from the entry's main claim or title.
- **Attachment preservation.** Every schedule/comment, exact `sr|card-metadata` callout, and trailing block ID recognized by the canonical [card-format rule](flashcards-and-emphasis.md#4-flashcards) is **preserved byte-for-byte and in place on every existing card** — wiki-build does not write, normalize, move, or remove it, even when a content line is revised. A legacy extra card is preserved and quoted in full in the report unless the request already authorizes its source-backed relocation or explicitly names it for deletion. If the term content changes on a merge — the rare title-rename case — its prior attachments stay with that card; the Spaced Repetition plugin is responsible for deciding on its next pass whether prior review history still applies.
- **No new extra cards on merge — ever.** The target presentation shape is one card per entry (*Flashcards*, `references/flashcards-and-emphasis.md` §4), while pre-existing extras remain preserved under the next bullet. Restoring the required primary card when none exists is item-19 repair, not an additional card. A merge that surfaces a second term seeming to warrant its own card has surfaced a **split**, not a card: create an entry for that term if the new source actually introduces it (the new entry carries its own single card), and otherwise leave every pre-existing card untouched. A facet is entry-worthy only when a **cited source** introduces it — background knowledge never adds a term, claim, or card the sources don't contain. The corpus failure this rule closes: a chapter-2 merge appended a second card quizzing *concept drift* onto the *Data drift* entry when neither cited chapter mentions that term.
- **Removing cards on merge requires explicit authorization.** Existing flashcards are preserved by default. When a card's definition was based on a body claim that the merge has corrected (per the *Conflict handling* rule) and now contradicts the corrected body, re-derive its content in place rather than removing and re-adding it, so every attachment stays with the card. A legacy extra card remains report-only during an ordinary source merge: identify the primary card, preserve every card and attachment, and quote each extra card verbatim in *Notes for the user*. Move or remove an extra card only when the user's request explicitly authorizes a source-backed split/merge that accounts for its tested claim and every attachment, or explicitly names that card for deletion. An instruction to build from or merge a new source does not itself grant that separate refactor authority.

The `parents:` field is preserved as-is on merge — see the `parents` field definition.

### The `read:` reset

`read:` is the user's review checkbox (see the `read` field definition), and a merge pass is the only thing in this skill that touches it after creation. **Set it to `false` when, and only when, the pass adds or rewrites unread explanatory body content:** new prose, a new paragraph, a new image or recreated table, a newly typeset equation, a newly inserted Person/Event date, a rewritten explanation, or a stub promoted to a full entry — whose body is written from scratch, so all of it is new to the reader. This test applies whether the unread content came from the active source or from independent step-7 QC.

**Every other change leaves the value exactly as it is.** Appending to `sources:`, appending an alias, adding or repairing a Related-footer link, rewording `description:`, adding or correcting a `tags:` value, removing navigation-only or other invalid prose, repairing a flashcard, leaving a legacy `importance:` in place, and format-only QC fixes do not add unread explanatory content, so none clears the checkbox.

**This is narrower than the `updated:` bump, and the two are independent tests.** Every reset comes with a bump — content added to the body is a change — but a bump implies nothing about the reset: a merge can change the entry, and so move the date, without changing what there is to read. The two fields answer different questions: `updated:` records that the entry changed, `read:` records whether the user still has to look at it. Conflating them turns the checkbox into a second copy of the date, at which point it carries no information the date doesn't and the user stops reading it.

**When the call is genuinely close, do not reset.** The two errors are not symmetric. A false reset makes the user re-read a note they had already read, and a checkbox that clears itself for reasons they can't see is one they stop trusting — which costs the field its whole purpose, permanently. A false non-reset costs them one glance the next time they open the note, which they were going to do anyway. **Say which way a close call went in the run report**, including the calls that went to *no reset*: the report is where a judgment this skill made about the user's own field gets checked.

### Source-no-op merges

Not every active source contributes new entry content. A **source-no-op merge** is the case where a candidate passes step 2's filters (the substance test for any source, and additionally the durability test for secondary sources) but every fact, figure, table, and equation selected **from that source** is already covered by the entry, verbatim or as a clear paraphrase. Apply the [example guidance](writing.md#prose-principles) and [figure selection rule](media.md#selection) first: an optional example or figure skipped for a documented reason is not new body content. The classification says nothing about the entry's final bytes: source/alias metadata may still append, and independent step-7 QC may still repair a current-rule defect. This is the common shape on deliberate re-runs of a previously processed source; it also occurs when a genuinely new source elaborates an entity without extending its coverage.

**The check, applied after selecting the candidate's content and before source-driven rewriting:** for each fact selected for the entry, ask whether the claim is already present in the existing entry's body (verbatim or as a clear paraphrase). For each selected figure, table, or equation, check whether the existing entry already embeds the same figure (same `Sources/Images/` filename), recreates the same table, or typesets the same equation — the same quantity's definition, where a difference of notation alone does not make it new. If *every* selected source contribution is already covered, this is a source-no-op merge. On a source that proceeded under explicit re-run intent, the default expectation is that most merges will be source-no-ops; the per-fact check still runs.

For a `Software` entry, compare the new material at the level of the interface or design idea, not identifier spelling. A newly named class that follows an already-covered estimator contract is duplicate coverage even though the token itself is absent. Conversely, a genuinely new artifact-wide convention or limitation may be net-new when the source substantively teaches it.

**Source-no-op merges skip source-driven rewrites, then run ordinary QC:**

- **Source-driven body rewrite — skipped.** Do not re-integrate or churn phrasing merely because the source was reconsidered. Independent step-7 QC remains active and may make the smallest targeted body repair its checklist authorizes, such as adding a Person/Event date directly supported by the active source or existing same-entry evidence, inserting an equation already warranted by carried-over prose, or removing a navigation-only cue. A conforming body stays byte-for-byte unchanged.
- **`description:` rewrite — skipped (for new-content-driven rewrites).** By definition the new source added no net-new content, so the "new source enables a meaningfully better description" trigger doesn't fire. *Pre-existing defects* in the description (vague, over 110 chars, missing entity-as-subject, forbidden formatting per the description field's rewrite criteria) are still caught by step 7's Quality Checklist on the same pass and fixed there — the source-no-op skip applies to *new-content-driven* rewrites, not to defect-driven fixes that the QC review would catch regardless of merge type.
- **Flashcards source-driven rewrite — skipped.** Step 7 still applies item-19 fixes, including the required line-1 equation coverage, under *Flashcards on merge* above; otherwise the section stays unchanged. Recognized scheduling state and block IDs are always preserved verbatim.
- **`updated:` uses the ordinary change test.** Any actual source/alias/metadata or QC change bumps it to today. It stays at its prior date only when the final entry is byte-unchanged.
- **`read:` uses the independent unread-content test.** Source/alias appends and formatting/removal/card/description/link repairs do not reset it. Independent QC that adds unread explanatory content — specifically a Person/Event date supported by the active source or existing same-entry evidence, or an equation warranted by carried-over prose — does reset it. Thus a source-no-op can have either field outcome; a byte-unchanged one keeps both values.

**The Related footer is not extended from the active source on a source-no-op merge.** The source told the entry nothing new and therefore earned no new neighbor; a genuinely source-supported new relationship means the merge was regular. Independent QC may still canonicalize a footer target/label or remove an invalid entry under the checklist's ordinary rules. **Source-no-op merges still run the other per-field append/preserve rules above (`sources:`, `aliases:`, `tags:`), with normal dedupe behavior.** `parents:` and any legacy `importance:` retain their regular-merge preservation rules.

**Step 7 (review and report) still fires on source-no-op-merged entries.** The per-file Quality Checklist and step-7 audits catch pre-existing defects that the source-driven skip deliberately does not address. Re-running with the same source after fixing a skill bug is a legitimate use case precisely because current rules still apply to every touched entry.

**Run report log:** source-no-op merges are logged separately from regular merges — `Entries source-no-op-merged: N (the active source added no net-new selected content)`. They are not counted under regular `Existing entries merged`. Itemize any source/alias appends and QC fixes through the normal report bullets, name every `read:` reset or close no-reset call, and state which source-no-ops were byte-unchanged. Do not summarize a QC-changing run as leaving the wiki in the same state.

**Edge case — partial source no-op.** A merge where *most* selected source facts are already covered but one or two are net-new is a regular merge, not a source-no-op. The classification is binary at the entry level: either every selected active-source contribution is already covered, or the source contributes new content and the merge is regular.

**An active source that adds a new image, recreated table, or newly typeset equation** (with its motivating prose) makes this a regular merge and resets `read:` because the reader has not seen that content. A different case is an equation inserted by step-7 QC solely because carried-over prose already states the calculation: the active source remains a source-no-op, while the actual-change test bumps `updated:` and the unread-content test resets `read:`. Candidates that fail step 2's filters never reach merge logic.

### Net-new fact test

Before integrating content from the new source, ask: "Does the existing body already say this, possibly in different words?" If yes, the fact is a duplicate; the new source still gets recorded in `sources:` but the body need not change for that fact. If no, the fact is net-new and is placed by the body's logical structure. Extend an existing paragraph only when the fact advances that paragraph's controlling idea; otherwise a new or reorganized paragraph is the coherent integration, not an addendum. Examples:

- Existing: "LambdaRank scales pairwise gradients by $\Delta\text{NDCG}$." / New source: "LambdaRank weights pairs by the NDCG change from swapping them." → **duplicate**, no body change.
- Existing body has no mention of LambdaLoss. / New source: "LambdaLoss later proved that LambdaRank's gradients correspond to a specific loss function." → **net-new**, place it beside the relevant mechanism or empirical discussion, extending that paragraph only if it develops the same controlling idea; never leave it as a trailing source-shaped fact.

The output is a coherent body, not a body-plus-addendum.

### Stub promotion

Stubs are **legacy artifacts**: this skill no longer creates them (see *Stubs (legacy)* in `SKILL.md`), but vaults built by earlier versions still contain them, and a candidate can resolve to one through the ordinary collision probes. When the existing entry being merged into is a stub (its `sources:` field contains only the string `"stub"`), the merge has one mechanical exception to the ordinary merge rules: **`sources:`** — the `"stub"` marker is **replaced** by the new source wikilink, not appended alongside. **This is one of only two cases in the entire skill where `sources:` is mutated by replacement rather than append**; the other is the decoded-provenance PDF-over-note replacement in the `sources:` rule above, the Quality Checklist item-4 case, which can fire on a stub promotion and a full-entry merge alike.

The Integration principle and the frontmatter/Related-footer rules above otherwise apply unchanged; the bullets below note how a few of them play out specifically from the stub's minimal starting state:

- **Body:** the stub's one-sentence body is fully replaced by an integrated body written from the new source. With only a single sentence to integrate against, this is effectively a fresh creation — write per the Body Structure and atomicity rules, with no note-level size target.
- **Description:** rewritten if the new source enables a meaningfully better one; otherwise preserved.
- **`tags:`** — the stub's inherited best-guess tags are re-evaluated against the body that gets written. Tags the body doesn't support are dropped, and disciplines the body establishes as canonical homes are added; tags the body confirms are kept. This is the one place in the skill where a full entry's `tags:` can lose a value on merge — a stub's tags are provisional.
- **Related footer:** created in this step (stubs have no Related footer; promoted entries do). Include the natural neighbors the entity has — no minimum count — per *The Related footer* rule (writing.md §2).
- **`## Flashcards` section:** created in this step (stubs have no Flashcards section; promoted entries do). Write the entry's one flashcard per *Flashcards* (`references/flashcards-and-emphasis.md` §4) — exactly one, the hard rule — covering the promoted entry's main claim, with its three content lines written by this skill (the Spaced Repetition plugin may attach scheduling state on a later review).
- **`updated:`** bumped to today.
- **`read:`** reset to `false`. Promotion replaces the stub's single placeholder sentence with a body written from scratch, so every word of the entry is new to the reader — this is the one merge shape where the reset is never a close call, whatever the stub's checkbox said before.

After promotion, the entry is a normal entry. Future merges follow the ordinary Integration principle.

### Conflict handling

If the new source **contradicts** a fact in the existing body, arbitrate only from
the active source and the existing entry's cited sources that can actually be
inspected. Do not settle the conflict from memory, uncited general knowledge, or
an assumed literature consensus. Methods, scope, date, and authority may weigh
the evidence only when the inspected sources establish them. If the available
evidence does not resolve the disagreement, preserve the existing claim, omit
the contradictory new clause, and report both claims with their source pages;
continue integrating unrelated supported contributions.

When the inspected evidence does establish a resolution, write the supported
understanding into the integrated body as ordinary prose without source-meta
phrasings: no "Wang et al. (2018) report that...", no "contradicting Burges'
original characterization", no "while some sources say X, others say Y." The
run report records the correction and its evidence; the entry describes the
subject rather than the trail of sources that produced the wording (prose
principle 5(a) applies here too).

**Contested-topic exemption.** For entries on philosophical positions, historical interpretations, religious doctrines, schools of thought, or other topics where competing views legitimately coexist, present the major **source-supported** views as parallel rather than picking one. This is the one place where prose principle 5(a)'s "no source-meta phrasings" prohibition relaxes (the exemption itself is housed as prose principle 5(g)): phrasings like "the materialist reading argues X, while the dualist reading argues Y," or "historians disagree on whether the war's primary cause was economic or ideological," or "the Stoic and Epicurean traditions differ in their account of …" are appropriate here, because the disagreement is itself part of the subject. The exemption applies in two settings: (a) fresh entries on subjects where contested interpretation is intrinsic to what the subject *is*, and (b) merges where the new source's "conflict" with the existing body turns out to reflect a legitimate alternative view rather than an error to resolve. **Topics outside the exemption — scientific facts with unsettled disputes, or topics where one view may be well-established and another fringe — follow the evidence rule above.** Describe consensus or a fringe view only when the inspected sources establish that status; otherwise preserve and report the unresolved disagreement.

**Default-rule mechanics** (for non-contested topics — the Contested-topic exemption above governs contested ones):

- **Existing body supported, new contradiction unsupported** — keep the existing claim; the rest of the new source's net-new facts are still integrated, and the new source is still recorded in `sources:`. Note the filtered claim and evidence in the run report.
- **New claim supported, existing claim disproved** — replace the wrong claim with the corrected understanding in place. Note the correction and evidence in the run report.
- **Both partial** — write a synthesized claim only when the inspected sources jointly support it. Otherwise preserve the status quo and report the unresolved conflict.

In all cases, the entry reads as a single coherent description of its subject, not a transcript of who said what.

**Limitation: conflict detection is per-merge** — it triggers when a new source contradicts the existing body of an entry being merged into. Two existing wiki entries that contradict each other are not surfaced by this skill (no comparison is happening between them on any given run). If you happen to notice such a contradiction while reviewing or while writing related entries, flag it in the run report's *Notes for the user*. Resolution belongs to a separately requested, source-backed wiki-lint refactor rather than this source run.
